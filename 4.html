01 AI Application Architecture

۱.۱. معماری اپلیکیشن هوش مصنوعی چیست؟

معماری اپلیکیشن هوش مصنوعی به ساختار کلی اجزای یک نرم‌افزار هوشمند و نحوهٔ ارتباط آن‌ها با یکدیگر گفته می‌شود.

فرض کنید می‌خواهیم یک چت‌بات پشتیبانی مشتریان بسازیم. کاربر می‌پرسد: «سفارشم چه زمانی به دستم می‌رسد؟»

برای پاسخ به این سؤال، برنامه باید:

  1. پیام را از رابط کاربری دریافت کند.
  2. مشخص کند کاربر چه کسی است.
  3. مکالمهٔ فعلی را شناسایی کند.
  4. در صورت نیاز اطلاعات سفارش را از پایگاه داده بخواند.
  5. اطلاعات مرتبط را در اختیار مدل قرار دهد.
  6. پاسخ مدل را دریافت کند.
  7. پاسخ را ذخیره کند.
  8. آن را به کاربر نمایش دهد.

۱.۲. اجزای اصلی معماری

Frontend

رابط کاربری شامل صفحهٔ چت، کادر پیام، دکمهٔ ارسال و نمایش پاسخ.

HTML، CSS، JavaScript، React، Next.js

Backend

منطق اصلی برنامه، احراز هویت، مدیریت مکالمه، ارتباط با مدل و پردازش پاسخ.

Python، FastAPI، Node.js، Java، Go

LLM Provider

ارائه‌دهندهٔ مدل زبانی که درخواست را پردازش و پاسخ تولید می‌کند.

OpenAI، Anthropic، Google، Mistral

Database

نگهداری کاربران، پیام‌ها، مکالمات، تنظیمات و اطلاعات عملیاتی.

PostgreSQL، MySQL، MongoDB، Redis

External Tools

ابزارهای خارجی برای جست‌وجو، ارسال ایمیل، ثبت سفارش و دریافت اطلاعات.

۱.۴. جریان اجرای یک درخواست

کاربر می‌گوید: «وضعیت سفارش شمارهٔ ۱۲۳۴ چیست؟»

  1. Frontend پیام را دریافت می‌کند.
  2. Backend کاربر را احراز هویت می‌کند.
  3. مالکیت سفارش بررسی می‌شود.
  4. اطلاعات سفارش از دیتابیس دریافت می‌شود.
  5. اطلاعات مرتبط همراه پیام کاربر به مدل ارسال می‌شود.
  6. مدل پاسخ قابل‌فهم تولید می‌کند.
  7. Backend پاسخ را بررسی و ذخیره می‌کند.
  8. پاسخ برای کاربر ارسال می‌شود.
نکتهٔ امنیتی: صرفاً به دلیل وارد کردن شمارهٔ سفارش، نباید اطلاعات آن را به کاربر نمایش داد. مالکیت سفارش باید در Backend بررسی شود.

۱.۶. معماری RAG

RAG مخفف Retrieval-Augmented Generation است؛ یعنی تولید پاسخ با کمک بازیابی اطلاعات.

در این روش، به‌جای ارسال تمام اسناد به مدل، ابتدا بخش‌های مرتبط با سؤال کاربر پیدا می‌شوند و سپس فقط اطلاعات مناسب در اختیار مدل قرار می‌گیرند.

سؤال کاربر
↓
تبدیل سؤال به Embedding
↓
جست‌وجو در Vector Database
↓
بازیابی متن‌های مرتبط
↓
ارسال سؤال و متن‌ها به LLM
↓
پاسخ مستند به کاربر

مراحل پیاده‌سازی:

  1. تقسیم اسناد به بخش‌های کوچک.
  2. ساخت Embedding از هر بخش.
  3. ذخیرهٔ بردارها در Vector Database.
  4. تبدیل سؤال کاربر به بردار.
  5. بازیابی بخش‌های نزدیک از نظر معنایی.
  6. ارسال اطلاعات مرتبط به مدل.
  7. تولید پاسخ بر اساس اطلاعات بازیابی‌شده.

۱.۷. معماری Agent

Agent یا عامل هوشمند می‌تواند برای رسیدن به هدف، چند مرحله را اجرا کند.

مثال: کاربر می‌گوید «برای هفتهٔ آینده یک جلسه با تیم فروش تنظیم کن و خلاصهٔ آخرین گزارش فروش را هم برایشان بفرست.»

  1. بررسی تاریخ‌های مناسب.
  2. خواندن تقویم.
  3. پیشنهاد زمان جلسه.
  4. بازیابی گزارش فروش.
  5. ساخت خلاصه.
  6. دریافت تأیید لازم.
  7. ارسال دعوت‌نامه.
نکته: هرچه Agent اختیار بیشتری برای عملیات واقعی داشته باشد، کنترل مجوزها، محدودیت عملیات و تأیید انسانی اهمیت بیشتری پیدا می‌کند.

02 Working with LLM APIs

۲.۱. API چیست؟

API مخفف Application Programming Interface است. API روشی استاندارد برای ارتباط دو نرم‌افزار با یکدیگر است.

در توسعهٔ اپلیکیشن AI، برنامه از طریق API به سرور ارائه‌دهندهٔ مدل درخواست می‌فرستد و پاسخ را دریافت می‌کند.

۲.۶. API Key و امنیت

API Key مانند یک رمز دسترسی برای استفاده از سرویس است.

Authorization: Bearer YOUR_API_KEY
اشتباه امنیتی خطرناک: هرگز API Key را در کد Frontend، فایل JavaScript قابل‌مشاهده در مرورگر، مخزن عمومی Git یا اپلیکیشن موبایلی که کلید درون آن قرار گرفته منتشر نکنید.

روش مناسب، نگهداری کلید در Environment Variable یا Secret Manager است.

export OPENAI_API_KEY="your-secret-key"
import os

api_key = os.environ["OPENAI_API_KEY"]

۲.۷. اولین درخواست با Python

pip install openai
from openai import OpenAI

client = OpenAI()

response = client.responses.create(
    model="YOUR_MODEL_NAME",
    input="Explain what an API is in simple language."
)

print(response.output_text)

در این مثال:

  • OpenAI() یک Client می‌سازد.
  • responses.create() درخواست را ارسال می‌کند.
  • model مدل مورد استفاده را مشخص می‌کند.
  • input ورودی مدل است.
  • output_text متن خروجی را ارائه می‌کند.

۲.۸. درخواست با JavaScript

import OpenAI from "openai";

const client = new OpenAI({
  apiKey: process.env.OPENAI_API_KEY
});

const response = await client.responses.create({
  model: "YOUR_MODEL_NAME",
  input: "Explain machine learning in simple terms."

console.log(response.output_text);

۲.۹. مدیریت خطا

from openai import OpenAI, RateLimitError, APIConnectionError
import os

client = OpenAI(
    api_key=os.environ["OPENAI_API_KEY"],
    timeout=30.0,
    max_retries=2
)

try:
    response = client.responses.create(
        model="YOUR_MODEL_NAME",
        input="What is a database?"
    )

    print(response.output_text)

except RateLimitError:
    print("درخواست‌ها بیش از حد مجاز هستند.")

except APIConnectionError:
    print("ارتباط با سرویس برقرار نشد.")

except Exception as error:
    print("خطای غیرمنتظره:", error)

۲.۱۰. Retry و Exponential Backoff

Retry یعنی تلاش دوباره پس از شکست درخواست. اما ارسال فوری و مکرر درخواست ممکن است مشکل را تشدید کند.

در Exponential Backoff فاصلهٔ زمانی میان تلاش‌ها افزایش می‌یابد:

تلاش زمان انتظار فرضی
اول ۱ ثانیه
دوم ۲ ثانیه
سوم ۴ ثانیه
چهارم ۸ ثانیه
Retry را برای خطاهای موقت انجام دهید، نه برای تمام خطاها. خطای احراز هویت با تکرار همان درخواست و همان کلید اشتباه حل نمی‌شود.

03 OpenAI API and Other LLM Providers

۳.۱. ارائه‌دهندهٔ مدل چه کاری انجام می‌دهد؟

ارائه‌دهندهٔ مدل زیرساخت لازم برای اجرای مدل را فراهم می‌کند. وقتی درخواست API ارسال می‌کنید، سرویس درخواست را دریافت می‌کند، هویت را بررسی می‌کند، ورودی را پردازش می‌کند و خروجی را به برنامه برمی‌گرداند.

۳.۲. OpenAI API

Responses API یکی از رابط‌های اصلی OpenAI برای ساخت اپلیکیشن‌های مدل‌محور است.

از کاربردهای آن می‌توان به موارد زیر اشاره کرد:

  • دریافت ورودی متنی
  • پردازش ورودی تصویری
  • تولید پاسخ
  • مدیریت تعامل‌های چندمرحله‌ای
  • استفاده از ابزارها
  • تولید خروجی ساختاریافته
from openai import OpenAI

client = OpenAI()

response = client.responses.create(
    model="YOUR_MODEL_NAME",
    instructions="You are a helpful programming tutor.",
    input="Explain the difference between a list and a tuple in Python."
)

print(response.output_text)

۳.۳. Chat Completions و Responses

Chat Completions یک رابط شناخته‌شده برای مکالمه با پیام‌های دارای نقش است. Responses رابطی گسترده‌تر برای ساخت تعامل‌های مدل‌محور و استفاده از ابزارها ارائه می‌کند.

انتخاب API باید بر اساس نیاز پروژه و مستندات جاری انجام شود. نباید فرض کرد تمام امکانات و پارامترهای APIها یکسان‌اند.

۳.۴. Anthropic Claude API

Claude API از قالب پیام‌محور استفاده می‌کند. برنامه پیام‌ها را ارسال می‌کند و مدل پیام بعدی را تولید می‌کند. 

import anthropic

client = anthropic.Anthropic()

message = client.messages.create(
    model="YOUR_MODEL_NAME",
    max_tokens=1024,
    messages=[
        {
            "role": "user",
            "content": "Explain REST APIs."
        }
    ]
)

print(message.content)

۳.۵. Google Gemini API

Gemini API از محتوای متنی و انواع محتوای دیگر پشتیبانی می‌کند. برای مکالمات چندمرحله‌ای، محتوا به‌صورت مجموعه‌ای از پیام‌ها و بخش‌ها ارسال می‌شود.

قابلیت‌هایی مانند Function Calling و خروجی ساختاریافته نیز در اکوسیستم آن وجود دارند.

۳.۶. Mistral AI

Mistral نیز مدل‌های زبانی و APIهایی برای تولید متن و ساخت اپلیکیشن‌های هوشمند ارائه می‌کند.

۳.۷. مقایسهٔ ارائه‌دهندگان

ارائه‌دهنده رابط‌های توسعه نکتهٔ مهم
OpenAI Responses و سایر APIها تولید، ابزارها و ورودی‌های چندرسانه‌ای
Anthropic Messages API پیام‌محور و ابزارها
Google Gemini API محتوای چندبخشی و چندرسانه‌ای
Mistral Mistral API گزینه‌ای دیگر برای مدل‌های زبانی

۳.۸. انتخاب Provider مناسب

  1. Quality: کیفیت پاسخ در وظایف موردنیاز.
  2. Latency: زمان پاسخ‌گویی.
  3. Cost: هزینهٔ ورودی و خروجی.
  4. Context Window: ظرفیت متن ورودی.
  5. Multimodal Support: پشتیبانی از تصویر، صدا و ویدئو.
  6. Tool Calling: قابلیت استفاده از ابزارها.
  7. Structured Output: تولید خروجی مطابق Schema.
  8. Availability: دسترس‌پذیری سرویس.
  9. Privacy: سیاست نگهداری و پردازش داده.
  10. Regional Requirements: محدودیت‌های منطقه‌ای و قانونی.

۳.۹. Provider Abstraction

اگر تمام کد برنامه را به شکل اختصاصی برای یک ارائه‌دهنده بنویسید، تغییر Provider ممکن است دشوار شود. یک لایهٔ واسط می‌تواند این وابستگی را کاهش دهد. 

class LLMProvider:
    def generate(self, messages):
        raise NotImplementedError


class OpenAIProvider(LLMProvider):
    def generate(self, messages):
        # Call OpenAI API
        pass


class ClaudeProvider(LLMProvider):
    def generate(self, messages):
        # Call Anthropic API
        pass
یک Interface مشترک نباید قابلیت‌های اختصاصی و ارزشمند یک Provider را پنهان یا حذف کند.

04 Conversation and Chat History Management

۴.۱. چرا مدیریت تاریخچه مهم است؟

مدل زبانی معمولاً به‌طور خودکار از تمام مکالمات قبلی کاربران در اپلیکیشن شما اطلاع ندارد.

اگر کاربر بگوید «اسم من علی است» و سپس بپرسد «اسم من چیست؟»، مدل تنها در صورتی می‌تواند پاسخ مناسبی بدهد که پیام قبلی در زمینهٔ مکالمه قرار گرفته باشد یا اطلاعات لازم از حافظهٔ بیرونی بازیابی شود.

۴.۳. Stateless و Stateful

Stateless API

هر درخواست مستقل است. برنامه باید پیام‌های قبلی لازم را دوباره ارسال کند.

Stateful Interaction

سرویس می‌تواند با شناسهٔ مکالمه یا پاسخ قبلی، تعامل را ادامه دهد.

history = [
    {"role": "user", "content": "My name is Ali."},
    {"role": "assistant", "content": "Nice to meet you, Ali."}
]

history.append({
    "role": "user",
    "content": "What is my name?"
})
Stateful بودن API به معنی بی‌نیازی از طراحی حافظه و پایگاه داده نیست. محصول همچنان باید مالکیت داده، مجوزها و حذف اطلاعات را مدیریت کند.

۵.۱. Streaming چیست؟

در روش عادی، برنامه منتظر می‌ماند تا مدل کل پاسخ را تولید کند و سپس آن را یکجا دریافت می‌کند. در Streaming، پاسخ به‌صورت تدریجی ارسال می‌شود.

Non-Streaming

کاربر باید منتظر بماند تا کل پاسخ آماده شود.

درخواست ← انتظار ← پاسخ کامل

Streaming

بخش‌های پاسخ به‌تدریج نمایش داده می‌شوند.

درخواست ← بخش اول ← بخش دوم ← تکمیل

۵.۲. مزایای Streaming

  1. کاهش زمان انتظار ادراک‌شده.
  2. ایجاد تجربهٔ تعاملی بهتر.
  3. نمایش زندهٔ پیشرفت پاسخ.
  4. مناسب بودن برای پاسخ‌های طولانی.
  5. امکان نمایش وضعیت عملیات.
Streaming الزاماً زمان لازم برای تولید پاسخ کامل را کاهش نمی‌دهد؛ بلکه باعث می‌شود کاربر زودتر اولین بخش پاسخ را ببیند.

۵.۳. SSE چیست؟

06 Context and Token Management

۶.۱. Token چیست؟

مدل‌های زبانی متن را دقیقاً به همان شکلی که انسان می‌بیند پردازش نمی‌کنند. متن ابتدا به واحدهایی به نام Token تبدیل می‌شود.

Token ممکن است شامل این موارد باشد:

  • یک کلمه
  • بخشی از یک کلمه
  • نشانهٔ نگارشی
  • فاصله یا ترکیبی از کاراکترها

مثال مفهومی Tokenization

Input:

Artificial intelligence is useful.

Tokens:

["Artificial", " intelligence", " is", " useful", "."]

سپس هر Token به یک شناسهٔ عددی تبدیل می‌شود. این شناسه‌ها به Tokenizer مدل وابسته‌اند.

۶.۲. Tokenization چیست؟

Tokenization فرآیند تبدیل متن به توکن است. تعداد کلمات با تعداد توکن‌ها برابر نیست و زبان و نوع Tokenizer بر نتیجه تأثیر دارند.

۶.۳. Context Window چیست؟

Context Window حداکثر ظرفیت زمینه‌ای است که مدل می‌تواند در یک درخواست یا تعامل مشخص پردازش کند. این ظرفیت معمولاً با Token اندازه‌گیری می‌شود.

در Context باید موارد زیر را در نظر بگیریم:

  • دستورالعمل‌ها
  • تاریخچهٔ مکالمه
  • متن کاربر
  • اسناد بازیابی‌شده
  • خروجی ابزارها
  • فضای موردنیاز برای تولید پاسخ

۶.۴. Input Tokens و Output Tokens

نوع توضیح
Input Tokens توکن‌های ورودی به مدل
Output Tokens توکن‌های تولیدشده توسط مدل
Cached Input Tokens بخش ورودی پردازش‌شده با سازوکار Cache در شرایط پشتیبانی‌شده
Reasoning Tokens توکن‌های مرتبط با پردازش استدلالی در برخی مدل‌ها

  3. بازیابی هدفمند اسناد.
  4. محدود کردن طول خروجی.

۶.۷. مدیریت تاریخچه با Token Budget

MAX_CONTEXT_TOKENS = 12000
RESERVED_OUTPUT_TOKENS = 2000

available_input = (
    MAX_CONTEXT_TOKENS - RESERVED_OUTPUT_TOKENS
)

def build_context(system_prompt, history, user_message):
    selected_history = []

    for message in reversed(history):
        # در نسخه واقعی باید تعداد توکن محاسبه شود.
        if fits_budget(message, available_input):
            selected_history.insert(0, message)

    return [
        {"role": "system", "content": system_prompt},
        *selected_history,
        {"role": "user", "content": user_message}
    ]
تابع fits_budget در مثال فرضی است. در پروژهٔ واقعی باید از Tokenizer مناسب استفاده شود و مجموع توکن تمام بخش‌ها محاسبه شود.

۷.۵. Structured Outputs

در برخی APIها می‌توان Schema را به مدل ارائه کرد تا خروجی مطابق ساختار تعیین‌شده تولید شود. 

from pydantic import BaseModel
from openai import OpenAI

client = OpenAI()

class Person(BaseModel):
    name: str
    age: int
    city: str

response = client.responses.parse(
    model="YOUR_MODEL_NAME",
    input=(
        "Extract the person's information: "
        "Sara is 28 years old and lives in Berlin."
    ),
    text_format=Person
)

person = response.output_parsed

print(person.name)
print(person.age)
print(person.city)

۷.۸. Structured Extraction در برابر Function Calling

def get_order_status(order_id, user_id):

۹.۴. چرخهٔ Function Calling

  1. مدل درخواست استفاده از تابع را اعلام می‌کند.
  2. Backend نام تابع و آرگومان‌ها را دریافت می‌کند.
  3. آرگومان‌ها اعتبارسنجی می‌شوند.
  4. مجوز کاربر بررسی می‌شود.
  5. تابع اجرا می‌شود.
  6. نتیجه به مدل برگردانده می‌شود.
  7. مدل پاسخ نهایی را تولید می‌کند.
مدل می‌تواند پیشنهاد دهد که تابع اجرا شود، اما تصمیم نهایی دربارهٔ مجاز بودن و اجرای آن در اختیار Backend است.

۱۰.۲. Cost چیست؟

هزینهٔ استفاده از سرویس AI ممکن است به موارد زیر وابسته باشد:

  • تعداد توکن ورودی
  • تعداد توکن خروجی
  • نوع مدل
  • قابلیت‌های مورد استفاده
  • ورودی‌های تصویری یا صوتی
  • ابزارهای جانبی
  • سیاست قیمت‌گذاری سرویس

فرمول مفهومی هزینه:

Total Cost = Input Cost + Output Cost + Additional Costs

اگر قیمت به‌ازای هر یک میلیون توکن تعریف شده باشد:

C = (Tin / 1,000,000) × Pin
+
(Tout / 1,000,000) × Pout

که در آن:

  • T_in: تعداد توکن ورودی
  • T_out: تعداد توکن خروجی
  • P_in: قیمت هر یک میلیون توکن ورودی
  • P_out: قیمت هر یک میلیون توکن خروجی

۱۰.۳. مثال محاسبهٔ هزینه

فرض کنیم قیمت‌های فرضی یک مدل:

  • ورودی: ۲ دلار به‌ازای هر یک میلیون توکن
  • خروجی: ۸ دلار به‌ازای هر یک میلیون توکن

مصرف یک درخواست:

  • ورودی: ۱۰٬۰۰۰ توکن
  • خروجی: ۲٬۰۰۰ توکن
Input Cost =
(10,000 / 1,000,000) × 2
= 0.02 USD

Output Cost =
(2,000 / 1,000,000) × 8
= 0.016 USD

Total Cost =
0.02 + 0.016
= 0.036 USD
اگر این درخواست روزانه ۱۰٬۰۰۰ بار اجرا شود، هزینهٔ روزانهٔ فرضی برابر با ۳۶۰ دلار خواهد بود. قیمت‌های مثال آموزشی‌اند، نه قیمت واقعی یک مدل مشخص.

ساخت یک دستیار هوشمند پشتیبانی مشتریان

برای ترکیب تمام مفاهیم فصل، یک دستیار پشتیبانی مشتریان طراحی و پیاده‌سازی کنید.

قابلیت‌های موردنیاز

  1. کاربر بتواند ثبت‌نام کند و وارد سیستم شود.
  2. بتواند چند مکالمهٔ مستقل ایجاد کند.
  3. تاریخچهٔ مکالمات در دیتابیس ذخیره شود.
  4. پاسخ مدل به‌صورت Streaming نمایش داده شود.
  5. مدل بتواند اطلاعات سفارش را از Backend دریافت کند.
  6. مدل بتواند فایل PDF راهنمای محصولات را تحلیل کند.
  7. پاسخ‌های استخراج اطلاعات به‌صورت JSON ساختاریافته باشند.
  8. مصرف توکن و هزینهٔ هر درخواست ثبت شود.
  9. خطاها و درخواست‌های ناموفق مدیریت شوند.
  10. دسترسی کاربر به داده‌های دیگران غیرممکن باشد.
