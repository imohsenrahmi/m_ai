مقدمه: چرا به MCP و Agent Communication نیاز داریم؟

یک مدل زبانی به‌تنهایی فقط بر اساس اطلاعاتی که در اختیارش قرار گرفته پاسخ تولید می‌کند. اما یک Agent کاربردی باید بتواند اطلاعات تازه دریافت کند، ابزار اجرا کند، به سرویس‌های سازمانی وصل شود و در صورت نیاز با Agentهای دیگر همکاری کند.

تصور کنید یک Agent هوشمند برای مدیریت کسب‌وکار ساخته‌ایم. این Agent باید بتواند:
  • از پایگاه داده اطلاعات مشتری را بخواند.
  • در یک سامانه‌ی CRM جست‌وجو کند.
  • فاکتور ایجاد کند.
  • از یک Agent مالی درباره‌ی وضعیت پرداخت سؤال کند.
  • از یک Agent حقوقی بخواهد قرارداد را بررسی کند.
  • نتیجه‌ی چند منبع را جمع‌بندی و به کاربر ارائه کند.
اگر برای هر ابزار و هر Agent یک روش اختصاصی اتصال بسازیم، معماری به‌سرعت پیچیده می‌شود. MCP و A2A برای استاندارد کردن بخش‌هایی از این ارتباط طراحی شده‌اند.

MCP

استانداردی برای اتصال برنامه‌های AI به ابزارها، منابع داده و قابلیت‌های خارجی.

Agent ↔ Tools / Data

A2A

استانداردی برای کشف، درخواست کار، پیگیری و تبادل خروجی بین Agentهای مستقل.

Agent ↔ Agent

قبل از شروع: پروتکل دقیقاً چیست؟

پروتکل مجموعه‌ای از قواعد مشترک است که مشخص می‌کند دو سیستم چگونه با یکدیگر ارتباط برقرار کنند. این قواعد می‌توانند ساختار پیام، روش شناسایی طرف مقابل، قالب درخواست، قالب پاسخ، خطاها، احراز هویت و نحوه‌ی انتقال داده را تعریف کنند.

برای مثال، وقتی یک کلاینت می‌خواهد یک ابزار MCP را اجرا کند، باید مشخص باشد:

  1. نام ابزار چیست؟
  2. چه ورودی‌هایی نیاز دارد؟
  3. ساختار ورودی چگونه اعتبارسنجی می‌شود؟
  4. درخواست با چه متدی ارسال می‌شود؟
  5. پاسخ موفق یا خطا چه ساختاری دارد؟
نکته‌ی مهم: MCP خودش یک مدل زبانی، Agent Framework یا موتور تصمیم‌گیری نیست. MCP استاندارد تبادل context و قابلیت‌ها میان برنامه‌ی AI و Server است. اینکه مدل چه زمانی از ابزار استفاده کند و چطور نتیجه را تحلیل کند، به Host، Agent Runtime و مدل بستگی دارد.

۱. Introduction to MCP

۱.۱. MCP چیست؟

Model Context Protocol یک پروتکل باز است که ارتباط بین برنامه‌های هوش مصنوعی و سیستم‌های خارجی را استاندارد می‌کند. این سیستم‌های خارجی می‌توانند پایگاه داده، فایل‌ها، APIها، سرویس‌های سازمانی، ابزارهای توسعه، سامانه‌های مانیتورینگ یا منابع اطلاعاتی باشند.

ایده‌ی اصلی این است که به‌جای نوشتن یک Integration اختصاصی برای هر مدل و هر ابزار، یک قرارداد ارتباطی مشترک داشته باشیم. در این صورت یک MCP Server می‌تواند توسط Hostهای سازگار مختلف استفاده شود.

۱.۲. مشکل قبل از MCP

فرض کنید سه برنامه‌ی AI داریم و هر سه باید به پنج سرویس سازمانی متصل شوند. اگر هر اتصال به‌صورت اختصاصی پیاده‌سازی شود، تعداد Integrationها می‌تواند زیاد شود. 

AI App A ───── Custom CRM Integration
AI App A ───── Custom Database Integration

AI App B ───── Custom CRM Integration
AI App B ───── Custom Database Integration

AI App C ───── Custom CRM Integration
AI App C ───── Custom Database Integration

این معماری باعث تکرار کد، تفاوت در ساختار ورودی و خروجی، دشواری نگهداری، افزایش هزینه‌ی تست و وابستگی بیشتر به پیاده‌سازی هر برنامه می‌شود.

۱.۴. MCP چه چیزهایی را استاندارد می‌کند؟

  • ساختار پیام‌ها و درخواست‌ها.
  • کشف قابلیت‌های Server.
  • تعریف Toolها و Schema ورودی آن‌ها.
  • تعریف Resourceها برای ارائه‌ی داده و context.
  • تعریف Promptهای قابل استفاده‌ی مجدد.
  • انتقال پیام‌ها از طریق Transportهای استاندارد.
  • الگوهای Notification، پیشرفت عملیات و قابلیت‌های تکمیلی.
  • چارچوب‌های احراز هویت برای ارتباطات HTTP.

۱.۵. MCP چه چیزی را استاندارد نمی‌کند؟

  • مدل زبانی مورد استفاده را تعیین نمی‌کند.
  • معماری داخلی Agent را تعیین نمی‌کند.
  • نحوه‌ی استدلال مدل را تعیین نمی‌کند.
  • الزام نمی‌کند که Agent حتماً چندعاملی باشد.
  • به‌تنهایی تضمین نمی‌کند که خروجی یک ابزار درست یا امن است.
  • جایگزین سیستم Authorization و سیاست‌های امنیتی سازمان نیست.

۱.۶. یک مثال واقعی

کاربر می‌گوید: «وضعیت سفارش شماره ۱۲۳۴ را بررسی کن.» مدل تشخیص می‌دهد برای پاسخ به اطلاعات سفارش نیاز دارد. MCP Host ابزارهای در دسترس را می‌شناسد و درخواست اجرای ابزار را به MCP Server می‌فرستد. Server از طریق API داخلی سفارش را می‌خواند و نتیجه را برمی‌گرداند. 

Agent:
  User asks about order 1234

Host:
  Discovers available MCP tools

Model:
  Selects get_order_status

MCP Client:
  Sends tools/call request

MCP Server:
  Calls internal Order API

MCP Client:
  Receives result

Model:
  Explains the order status to the user
مزیت اصلی MCP این است که توسعه‌دهنده‌ی ابزار می‌تواند قابلیت را یک‌بار با یک قرارداد استاندارد ارائه کند و برنامه‌های مختلف، در صورت سازگاری، از همان قابلیت استفاده کنند.

۲.۲. MCP Host

Host برنامه‌ی اصلی هوش مصنوعی است؛ یعنی محیطی که مدل، رابط کاربر، منطق Agent، مدیریت context و اتصال به MCP Clientها در آن قرار می‌گیرند.

وظایف متداول Host:

  • مدیریت ارتباط با مدل زبانی.
  • ایجاد و مدیریت MCP Clientها.
  • اتصال به چند MCP Server.
  • مدیریت مجوزهای اتصال و تأیید کاربر.
  • انتخاب قابلیت‌های قابل ارائه به مدل.
  • ترکیب نتایج چند Server در context مدل.
  • کنترل سیاست‌های اجرای ابزارها.
  • مدیریت چرخه‌ی عمر اتصال‌ها و خطاها.

مثال Host می‌تواند یک IDE هوشمند، دستیار سازمانی، برنامه‌ی دسکتاپ AI یا یک Backend اختصاصی برای Agent باشد.

۲.۳. MCP Client

Client بخشی از Host است که با یک MCP Server ارتباط برقرار می‌کند. در معماری رایج، هر Client به یک Server مشخص متصل می‌شود. اگر Host به پنج Server نیاز داشته باشد، معمولاً پنج Client مستقل مدیریت می‌کند.

مسئولیت‌های Client شامل موارد زیر است:

  • برقراری اتصال با Server.
  • ارسال پیام‌های پروتکل.
  • کشف قابلیت‌ها و دریافت فهرست ابزارها.
  • ارسال درخواست اجرای Tool.
  • خواندن Resource و دریافت Prompt.
  • مدیریت پاسخ‌ها، خطاها و Notificationها.
  • رعایت نسخه و قابلیت‌های توافق‌شده.

۲.۴. MCP Server

Server قابلیت‌ها را در اختیار Client قرار می‌دهد. Server ممکن است روی همان ماشین Host اجرا شود یا روی یک ماشین و سرویس راه دور قرار داشته باشد.

یک Server می‌تواند این موارد را ارائه کند:

  • Tools: عملیات قابل فراخوانی.
  • Resources: اطلاعات و منابع قابل خواندن.
  • Prompts: قالب‌های تعاملی و دستورالعمل‌های آماده.

۲.۵. لایه‌های MCP

به‌صورت مفهومی دو لایه‌ی مهم وجود دارد:

Data Layer

تعریف معنای پیام‌ها، درخواست‌ها، پاسخ‌ها، قابلیت‌ها و Primitiveها.

پایه‌ی تبادل پیام در MCP، JSON-RPC 2.0 است.

Transport Layer

مشخص می‌کند پیام‌ها چگونه بین Client و Server منتقل شوند؛ مانند STDIO یا Streamable HTTP.

۲.۶. JSON-RPC 2.0 چیست؟

JSON-RPC یک قالب سبک برای فراخوانی متد از راه دور است. در آن یک طرف درخواست متدی را ارسال می‌کند و طرف دیگر پاسخ متناظر را برمی‌گرداند. 

{
  "jsonrpc": "2.0",
  "id": 1,
  "method": "tools/list",
  "params": {}
}

نمونه‌ی پاسخ:

{
  "jsonrpc": "2.0",
  "id": 1,
  "result": {
    "tools": [
      {
        "name": "get_order_status",
        "description": "Get an order status"
      }
    ]
  }
}

فیلد id برای تطبیق پاسخ با درخواست استفاده می‌شود. در Notification معمولاً پاسخ مستقلی انتظار نمی‌رود. در طراحی واقعی باید خطاها نیز با ساختار مناسب مدیریت شوند.

۲.۷. Capability Negotiation

Client و Server باید بدانند طرف مقابل چه قابلیت‌هایی را پشتیبانی می‌کند. این موضوع مانع آن می‌شود که یک طرف عملیاتی را درخواست کند که طرف دیگر قادر به انجام آن نیست.

برای مثال:

  • Server ممکن است Tool ارائه کند، اما Resource نداشته باشد.
  • Server ممکن است Subscription برای Resource را پشتیبانی کند.
  • Client ممکن است امکان دریافت درخواست Elicitation را داشته باشد.
نسخه‌ی پروتکل و SDK اهمیت دارد. MCP در نسخه‌های مختلف تغییر کرده است. برای نمونه، مستندات جدید در مسیر تکامل پروتکل، مدل stateless و روش کشف server/discover را معرفی کرده‌اند؛ در حالی که پیاده‌سازی‌های نسخه‌های قدیمی‌تر از چرخه‌ی initialize استفاده می‌کنند. بنابراین نمونه‌کدهای نسخه‌های مختلف را بدون بررسی سازگاری با هم ترکیب نکنید.

۳.۲. چرخه‌ی تعامل

در یک پیاده‌سازی معمولی، روند کلی چنین است:

  1. Host یک MCP Client می‌سازد.
  2. Client از طریق Transport به Server وصل می‌شود.
  3. قابلیت‌ها و نسخه‌ی قابل پشتیبانی مشخص می‌شوند.
  4. Client قابلیت‌های Server را کشف می‌کند.
  5. Host قابلیت‌های مجاز را به Agent یا مدل ارائه می‌کند.
  6. مدل یا منطق برنامه تصمیم می‌گیرد از کدام قابلیت استفاده کند.
  7. Client درخواست مربوط را ارسال می‌کند.
  8. Server درخواست را اعتبارسنجی و اجرا می‌کند.
  9. نتیجه به Client و سپس Host برمی‌گردد.

۳.۳. چرا Host را نباید با Client اشتباه بگیریم؟

Host کل برنامه‌ی AI است، اما Client فقط جزء ارتباطی آن با یک Server است. Host ممکن است چند Client، یک یا چند مدل، حافظه، سیاست امنیتی، UI و Agent Runtime داشته باشد.

۳.۴. جداسازی مسئولیت‌ها

یک اصل معماری مهم این است که Server نباید بی‌دلیل به کل مکالمه‌ی کاربر، حافظه‌ی Agent یا اطلاعات سایر Serverها دسترسی داشته باشد. Host باید فقط context ضروری را در اختیار هر Server قرار دهد.

هر MCP Server را مانند یک سرویس مستقل با مسئولیت مشخص طراحی کنید. Server مدیریت قابلیت‌های خودش را بر عهده دارد؛ Host مدیریت تجربه‌ی AI، سیاست‌ها و هماهنگی کلی را انجام می‌دهد.

۴. MCP Tools

۴.۱. Tool چیست؟

Tool یک عملیات قابل اجراست که MCP Server آن را در اختیار Client قرار می‌دهد. مدل می‌تواند با توجه به درخواست کاربر و توضیحات Tool تشخیص دهد چه زمانی باید آن را فراخوانی کند.

نمونه‌هایی از Tool:

  • جست‌وجوی مشتری در CRM.
  • خواندن وضعیت سفارش.
  • اجرای Query محدود روی دیتابیس.
  • ساخت تیکت پشتیبانی.
  • ارسال درخواست بازپرداخت.
  • محاسبه‌ی مالیات یا هزینه.
  • اجرای تست نرم‌افزار.

۴.۲. اجزای یک Tool

یک Tool معمولاً این اطلاعات را دارد:

  • Name: شناسه‌ی یکتای Tool در Server.
  • Description: توضیح روشن درباره‌ی عملکرد و کاربرد.
  • Input Schema: ساختار ورودی و نوع داده‌ها.
  • Handler: تابع یا منطق اجرای واقعی.
  • Output: نتیجه‌ی قابل بازگرداندن.
  • Error Behavior: رفتار در شرایط خطا.

۴.۳. مثال تعریف Tool

{
  "name": "get_order_status",
  "description": "Retrieve the current status of an order",
  "inputSchema": {
    "type": "object",
    "properties": {
      "order_id": {
        "type": "string",
        "description": "Unique order identifier"
      }
    },
    "required": ["order_id"],
    "additionalProperties": false
  }
}

در این مثال، مدل باید یک شناسه‌ی سفارش ارسال کند. اگر ورودی ناقص یا نامعتبر باشد، Server باید آن را رد کند.

۴.۴. فراخوانی Tool

در سطح مفهومی، درخواست اجرای Tool با متد tools/call انجام می‌شود:

{
  "jsonrpc": "2.0",
  "id": 42,
  "method": "tools/call",
  "params": {
    "name": "get_order_status",
    "arguments": {
      "order_id": "ORD-1234"
    }
  }
}

پاسخ نمونه:

{
  "jsonrpc": "2.0",
  "id": 42,
  "result": {
    "content": [
      {
        "type": "text",
        "text": "Order ORD-1234 is currently shipped."
      }
    ],
    "isError": false
  }
}

۴.۵. Tool با Resource چه تفاوتی دارد؟

Tool برای اجرای یک عملیات است؛ Resource برای ارائه‌ی محتوا یا داده. البته یک Tool می‌تواند داده برگرداند، اما هدف و مدل استفاده‌ی این دو متفاوت است.

Tool Resource
عملیات را اجرا می‌کند. محتوا را در اختیار Client می‌گذارد.
می‌تواند تغییردهنده‌ی وضعیت باشد. معمولاً برای خواندن داده استفاده می‌شود.
با tools/call اجرا می‌شود. با resources/read خوانده می‌شود.
مثال: ثبت سفارش. مثال: مستندات محصول.

۴.۶. طراحی درست Toolها

یک Tool خوب باید:

  • یک مسئولیت روشن داشته باشد.
  • نامی قابل فهم و مشخص داشته باشد.
  • ورودی‌های دقیق و محدود بگیرد.
  • از ورودی‌های اضافی و مبهم جلوگیری کند.
  • خروجی ساختاریافته و قابل تفسیر تولید کند.
  • خطاها را به‌صورت قابل مدیریت گزارش کند.
  • برای عملیات حساس، مجوز و تأیید مناسب داشته باشد.

۴.۷. طراحی بد در مقابل طراحی خوب

# Poor design:
execute_everything(input_text)

# Better design:
get_customer(customer_id)
get_order_status(order_id)
calculate_refund(order_id)
request_refund(order_id, reason)

Tool بسیار بزرگ با ورودی مبهم باعث می‌شود مدل اختیار بیش از حد داشته باشد، خطاها دشوارتر تشخیص داده شوند و کنترل امنیتی سخت‌تر شود.

۴.۸. Toolهای Read و Write

Toolهای خواندنی و تغییردهنده‌ی وضعیت را از نظر امنیتی جدا کنید. خواندن وضعیت سفارش با اجرای بازپرداخت یکسان نیست.

اجرای Tool به معنی مجاز بودن عملیات نیست. مدل ممکن است درخواست نامناسبی انتخاب کند؛ Server باید خودش مجوز، مالکیت داده، اعتبار ورودی و محدودیت عملیات را بررسی کند.

۵. MCP Resources

۵.۱. Resource چیست؟

Resource روشی برای ارائه‌ی داده و context به برنامه‌ی AI است. Resource معمولاً با یک URI شناسایی می‌شود و می‌تواند به فایل، سند، رکورد پایگاه داده، محتوای داخلی یا داده‌ی یک سرویس اشاره کند.

نمونه‌های Resource:

  • مستندات داخلی سازمان.
  • Schema پایگاه داده.
  • مشخصات محصول.
  • گزارش وضعیت سیستم.
  • محتوای یک فایل مشخص.
  • داده‌ی مرجع یا راهنمای فنی.

۵.۲. URI در Resource

URI شناسه‌ای برای دسترسی به Resource است. لازم نیست حتماً یک URL عمومی وب باشد. می‌تواند یک شناسه‌ی منطقی و اختصاصی باشد. 

file:///workspace/README.md
postgres://analytics/schema
company://policies/refund
docs://products/catalog

URIهای بالا صرفاً مثال هستند؛ قرارداد واقعی URI را Server تعریف می‌کند.

۵.۳. Resource List و Read

Client می‌تواند فهرست Resourceهای قابل دسترس را دریافت کند و سپس محتوای موردنیاز را بخواند. در Resourceهای پویا ممکن است Template نیز وجود داشته باشد. 

{
  "jsonrpc": "2.0",
  "id": 7,
  "method": "resources/list",
  "params": {}
}

نمونه‌ی درخواست خواندن:

{
  "jsonrpc": "2.0",
  "id": 8,
  "method": "resources/read",
  "params": {
    "uri": "company://policies/refund"
  }
}

۵.۴. Resource Template

گاهی Resourceها ثابت نیستند. مثلاً برای هر مشتری یک Resource جدا وجود دارد. در این شرایط Template می‌تواند الگوی URI را مشخص کند. 

customer://{customer_id}/profile
orders://{order_id}/details
documents://{document_id}

Template کمک می‌کند Client بداند چه الگوهایی از Resource قابل دسترسی هستند. با این حال، مجوز دسترسی به هر شناسه باید در Server بررسی شود.

۵.۵. Resource و RAG

MCP و RAG رقیب یکدیگر نیستند. RAG یک الگوی بازیابی اطلاعات برای بهبود پاسخ مدل است؛ MCP یک پروتکل ارتباطی برای ارائه‌ی قابلیت‌ها و منابع به برنامه‌ی AI است.

User Question
↓
AI Host
↓
MCP Resource Server
↓
Search / Vector DB / Documents
↓
Retrieved Context

یک MCP Server می‌تواند Resourceهایی از اسناد یا نتایج یک سیستم بازیابی ارائه کند. Host می‌تواند این داده را به مدل بدهد تا پاسخ مستند تولید شود. خود MCP الزاماً Vector Search یا الگوریتم RAG را تعریف نمی‌کند.

۵.۶. Subscription و تغییر Resource

برخی پیاده‌سازی‌ها قابلیت Subscription و Notification برای تغییر Resource را پشتیبانی می‌کنند. در این حالت Client می‌تواند از تغییر محتوای مورد علاقه‌ی خود مطلع شود.

موارد استفاده:

  • تغییر مستندات یک پروژه.
  • به‌روزرسانی وضعیت یک منبع داده.
  • تغییر یک فایل یا تنظیمات.
Resource را برای داده‌ای طراحی کنید که Host باید آن را بخواند و در context خود قرار دهد. اگر نیاز به اجرای یک عملیات یا تغییر وضعیت دارید، معمولاً Tool انتخاب مناسب‌تری است.

۶. MCP Prompts

۶.۱. Prompt چیست؟

Prompt در MCP یک قالب آماده و قابل استفاده‌ی مجدد برای هدایت تعامل با مدل است. Server می‌تواند Promptهایی با نام، توضیح و پارامترهای ورودی ارائه کند. Client می‌تواند Prompt مناسب را دریافت و در جریان تعامل با مدل استفاده کند.

مثال‌هایی از Prompt:

  • بررسی امنیتی کد.
  • تحلیل یک قرارداد.
  • خلاصه‌سازی گزارش مالی.
  • تولید گزارش incident.
  • بررسی کیفیت یک پاسخ پشتیبانی.

۶.۲. ساختار Prompt

یک Prompt معمولاً شامل موارد زیر است:

  • نام یکتا.
  • توضیح کاربرد.
  • پارامترهای موردنیاز.
  • محتوای Prompt یا پیام‌های قالب‌بندی‌شده.
{
  "name": "review_contract",
  "description": "Review a contract for key risks",
  "arguments": [
    {
      "name": "contract_text",
      "description": "Contract content",
      "required": true
    },
    {
      "name": "jurisdiction",
      "description": "Applicable jurisdiction",
      "required": false
    }
  ]
}

۶.۳. دریافت Prompt

درخواست مفهومی دریافت Prompt:

{
  "jsonrpc": "2.0",
  "id": 10,
  "method": "prompts/get",
  "params": {
    "name": "review_contract",
    "arguments": {
      "contract_text": "Example contract...",
      "jurisdiction": "Germany"
    }
  }
}

۶.۴. تفاوت Prompt با Tool و Resource

Primitive هدف مثال
Tool اجرای عملیات ایجاد تیکت
Resource ارائه‌ی داده متن سیاست بازپرداخت
Prompt قالب تعامل و هدایت مدل قالب تحلیل درخواست بازپرداخت

۶.۵. مثال ترکیبی

فرض کنید Agent باید یک قرارداد را تحلیل کند:

  1. از Resource، متن سیاست‌های حقوقی شرکت را دریافت می‌کند.
  2. از Prompt آماده‌ی review_contract برای ساختاردهی تحلیل استفاده می‌کند.
  3. در صورت نیاز، Tool مربوط به بررسی وضعیت قرارداد را فراخوانی می‌کند.
  4. خروجی را با منابع و محدودیت‌های مشخص جمع‌بندی می‌کند.
Prompt یک مکانیزم امنیتی نیست. نباید فرض کنیم چون یک دستورالعمل در Prompt نوشته شده، مدل یا Tool در همه‌ی شرایط آن را رعایت خواهد کرد. کنترل دسترسی و اعتبارسنجی باید در لایه‌های اجرایی و Server انجام شوند.

۷. MCP Transport Mechanisms

۷.۱. Transport چیست؟

Transport مشخص می‌کند پیام‌های MCP از چه کانالی و با چه روش انتقالی بین Client و Server جابه‌جا شوند. معنای پیام‌های MCP مستقل از Transport است؛ یعنی یک Tool Call می‌تواند از طریق Transportهای مختلف منتقل شود.

۷.۲. STDIO Transport

در STDIO، Client یک Process محلی را اجرا می‌کند و از ورودی و خروجی استاندارد آن برای تبادل پیام استفاده می‌کند. 

AI Host
  |
  +-- Starts local MCP Server process
          |
          +-- stdin  : Client -> Server
          |
          +-- stdout : Server -> Client

موارد استفاده:

  • ابزارهای محلی توسعه.
  • دسترسی به فایل‌های همان ماشین.
  • اتصال به ابزارهای خط فرمان.
  • محیط‌های دسکتاپ و IDE.

مزایا:

  • ساده برای راه‌اندازی محلی.
  • بدون نیاز به باز کردن پورت شبکه.
  • ارتباط مستقیم بین Processها.
  • مناسب برای ابزارهای محلی و توسعه.

محدودیت‌ها:

  • برای سرویس‌دهی به تعداد زیادی Client از راه دور طراحی اصلی مناسبی نیست.
  • مدیریت Process و محیط اجرا اهمیت دارد.
  • خروجی استاندارد باید برای پیام‌های پروتکل محفوظ بماند.
در Server مبتنی بر STDIO، پیام‌های عادی مانند Debug Print را روی stdout چاپ نکنید؛ چون ممکن است جریان پیام‌های پروتکل را خراب کنند. برای لاگ از stderr یا سیستم Logging مناسب استفاده کنید.

۷.۳. Streamable HTTP

Streamable HTTP برای ارتباط شبکه‌ای و Serverهای راه دور استفاده می‌شود. پیام‌ها از طریق HTTP ارسال می‌شوند و در صورت نیاز امکان دریافت پاسخ‌های جریانی با Server-Sent Events نیز وجود دارد. 

AI Host / MCP Client
       |
       | HTTP POST
       v
  MCP HTTP Endpoint
       |
       +---- JSON Response
       |
       +---- Optional SSE Stream

مزایا:

  • مناسب برای Serverهای راه دور.
  • قابل استفاده در معماری سرویس‌گرا.
  • سازگار با زیرساخت‌های HTTP.
  • امکان استفاده از مکانیزم‌های احراز هویت و کنترل شبکه.
  • پشتیبانی از الگوهای پاسخ جریانی در صورت پیاده‌سازی.

چالش‌ها:

  • مدیریت Authentication و Authorization.
  • مدیریت Timeout و قطع ارتباط.
  • کنترل تعداد درخواست‌ها و Rate Limit.
  • امنیت Endpoint و شبکه.
  • مدیریت Streaming و منابع اتصال.

۷.۴. SSE چیست؟

Server-Sent Events یک روش انتقال رویداد از Server به Client روی یک اتصال HTTP است. این روش برای ارسال تدریجی رویدادها مناسب است. SSE با WebSocket یکسان نیست؛ در SSE جریان اصلی رویداد از Server به Client است.

۷.۵. مقایسه‌ی Transportها

ویژگی STDIO Streamable HTTP
محل اجرا معمولاً Process محلی محلی یا راه دور از طریق HTTP
شبکه نیاز به شبکه ندارد از شبکه استفاده می‌کند
استقرار سازمانی برای ابزار محلی مناسب‌تر برای سرویس‌های راه دور مناسب‌تر
احراز هویت شبکه‌ای معمولاً در سطح Process و محیط محلی قابل استفاده با سازوکارهای HTTP و OAuth
Streaming بر اساس جریان استاندارد Process امکان SSE در چارچوب Transport

۷.۶. انتخاب Transport مناسب

  • ابزار محلی برای IDE: معمولاً STDIO.
  • Server سازمانی مشترک: معمولاً Streamable HTTP.
  • سرویس راه دور با چند مصرف‌کننده: HTTP گزینه‌ی طبیعی‌تری است.
  • محیط محدود و محلی: STDIO ممکن است ساده‌تر باشد.
Transport را بر اساس مدل استقرار، مرز امنیتی، مقیاس‌پذیری و نیازهای عملیاتی انتخاب کنید؛ نه صرفاً بر اساس اینکه کدام نمونه‌کد کوتاه‌تر است.

۸. MCP Server Development

۸.۱. اصول توسعه‌ی یک MCP Server

توسعه‌ی MCP Server یعنی ساخت سرویسی که قابلیت‌های مشخصی را از طریق MCP در اختیار Client قرار دهد. یک Server خوب باید کوچک، قابل تست، امن و دارای قرارداد روشن باشد.

پیش از کدنویسی این پرسش‌ها را پاسخ دهید:

  1. Server دقیقاً چه مسئولیتی دارد؟
  2. چه Toolهایی ارائه می‌کند؟
  3. چه Resourceهایی در دسترس‌اند؟
  4. آیا Promptهای تکرارپذیر لازم است؟
  5. چه هویت و مجوزی برای دسترسی نیاز است؟
  6. آیا Server محلی است یا راه دور؟
  7. چه محدودیت‌هایی برای ورودی، خروجی و نرخ درخواست وجود دارد؟

۸.۲. نصب SDK پایتون

SDK رسمی پایتون برای ساخت Client و Server قابل استفاده است. در مستندات فعلی SDK، شاخه‌ی نسخه‌ی ۲ به‌عنوان خط پایدار جدید معرفی شده است. نسخه‌ی SDK و نسخه‌ی پروتکل را هنگام شروع پروژه بررسی کنید. 

uv add "mcp[cli]"

# Or
pip install "mcp[cli]"

۸.۳. ساخت یک Server ساده با Python

مثال زیر یک الگوی آموزشی برای تعریف یک Tool است. API دقیق SDK ممکن است با نسخه‌های مختلف تفاوت داشته باشد؛ در پروژه‌ی واقعی آن را با مستندات نسخه‌ی نصب‌شده تطبیق دهید. 

from mcp.server.fastmcp import FastMCP

mcp = FastMCP("Order Service")

ORDERS = {
    "ORD-1001": {
        "status": "shipped",
        "total": 120.50
    },
    "ORD-1002": {
        "status": "processing",
        "total": 75.00
    }
}

@mcp.tool()
def get_order_status(order_id: str) -> dict:
    """
    Retrieve the current status of an order.
    """
    if order_id not in ORDERS:
        raise ValueError("Order not found")

    return {
        "order_id": order_id,
        **ORDERS[order_id]
    }

if __name__ == "__main__":
    mcp.run()

۸.۴. Server چه کاری انجام می‌دهد؟

  1. یک Server با نام مشخص ایجاد می‌کند.
  2. یک Tool به نام get_order_status ثبت می‌کند.
  3. ورودی Tool را دریافت می‌کند.
  4. داده‌ی سفارش را از منبع نمونه می‌خواند.
  5. در صورت نبود سفارش، خطا می‌دهد.
  6. در صورت موفقیت، نتیجه را برمی‌گرداند.

۸.۵. اضافه کردن Resource

فرض کنید می‌خواهیم سیاست بازپرداخت را نیز در اختیار Host قرار دهیم. می‌توانیم یک Resource برای آن تعریف کنیم. 

REFUND_POLICY = """
Customers may request a refund
within the applicable return window.
All refund requests must be checked
against the order status and policy.
"""

@mcp.resource("company://policies/refund")
def refund_policy() -> str:
    return REFUND_POLICY

۸.۶. اضافه کردن Prompt

برای مثال می‌توانیم یک Prompt برای تحلیل درخواست بازپرداخت تعریف کنیم. شکل دقیق API ثبت Prompt به نسخه‌ی SDK وابسته است. 

# Conceptual prompt definition

  arguments:

  template:
    1. Check the order status.

۸.۹. تست MCP Server

تست‌ها باید چند سطح داشته باشند:

  • تست واحد منطق Tool.
  • تست اعتبارسنجی ورودی.
  • تست مجوز دسترسی.
  • تست پاسخ موفق و خطا.
  • تست اتصال Client به Server.
  • تست قطع اتصال و Timeout.
  • تست رفتار در ورودی‌های مخرب.

۸.۱۰. MCP Inspector

برای توسعه و عیب‌یابی، ابزار MCP Inspector می‌تواند در بررسی قابلیت‌های Server، مشاهده‌ی Toolها و آزمایش فراخوانی‌ها کمک کند. این ابزار به‌ویژه زمانی مفید است که بخواهید مطمئن شوید تعریف Tool و رفتار واقعی آن با هم سازگارند.

۹. MCP Security

امنیت در MCP بسیار مهم است؛ زیرا Agent می‌تواند از طریق Toolها به داده‌ها و عملیات واقعی دسترسی پیدا کند. یک اشتباه در طراحی Server ممکن است به نشت اطلاعات، تغییر غیرمجاز داده یا اجرای عملیات خطرناک منجر شود.

۹.۱. اصل اول: مدل زبانی مرجع امنیتی نیست

مدل ممکن است تصمیم اشتباه بگیرد، Prompt Injection را دنبال کند یا Tool نامناسبی انتخاب کند. بنابراین نباید امنیت را صرفاً به Prompt سیستم یا دستورالعمل مدل واگذار کرد.

۹.۲. تهدیدهای اصلی

۱. Prompt Injection

محتوای یک فایل، وب‌سایت یا سند ممکن است شامل دستورهایی باشد که تلاش می‌کنند رفتار Agent را تغییر دهند؛ مثلاً از آن بخواهند اطلاعات محرمانه را ارسال کند.

۲. Excessive Tool Permissions

اگر Server دسترسی بیش از حد داشته باشد، یک Tool ظاهراً ساده ممکن است امکان خواندن یا تغییر داده‌های حساس را فراهم کند.

۳. Confused Deputy

Agent یا Server ممکن است از اعتبارنامه یا مجوزی استفاده کند که متعلق به کاربر یا درخواست فعلی نیست و ناخواسته به داده‌ی دیگری دسترسی پیدا کند.

۴. Data Exfiltration

اطلاعات حساس ممکن است از طریق خروجی Tool، لاگ‌ها، درخواست شبکه یا پاسخ مدل به مقصد غیرمجاز منتقل شوند.

۵. SSRF و دسترسی شبکه‌ای ناخواسته

اگر Tool یک URL دلخواه از ورودی مدل بگیرد و آن را باز کند، ممکن است به منابع داخلی یا سرویس‌هایی دسترسی پیدا کند که نباید در دسترس باشند.

۶. Cross-Tenant Data Leakage

در سیستم چندمستاجری، ضعف در کنترل Tenant ID یا فیلتر مجوز می‌تواند اطلاعات یک مشتری را به مشتری دیگر نشان دهد.

۹.۴. OAuth و ارتباط HTTP

در ارتباطات راه دور، از سازوکارهای استاندارد احراز هویت و Authorization استفاده کنید. MCP برای HTTP-based authorization چارچوبی مبتنی بر استانداردهای OAuth دارد. توکن‌ها باید از نظر مخاطب، صادرکننده، انقضا و Scope بررسی شوند.

نکات مهم:

  • از توکن‌های کوتاه‌عمر استفاده کنید.
  • Scopeها را به حداقل نیاز محدود کنید.
  • توکن را در Prompt یا متن خروجی مدل قرار ندهید.
  • اعتبار توکن را در Server بررسی کنید.
  • توکن یک سرویس را بدون طراحی درست به سرویس دیگر منتقل نکنید.

۹.۵. Least Privilege

هر Server و Tool باید حداقل مجوز لازم را داشته باشد. اگر یک Tool فقط باید وضعیت سفارش را بخواند، نباید مجوز حذف سفارش نیز داشته باشد. 

# Bad permission model:
order_service: full_access

# Better permission model:
get_order_status:
  permissions:
    - orders:read

request_refund:
  permissions:
    - refunds:request

approve_refund:
  permissions:
    - refunds:approve
  approval_required: true

۹.۶. اعتبارسنجی ورودی

Schema به‌تنهایی کافی نیست. Server باید ورودی را از نظر قواعد کسب‌وکار و مجوز نیز بررسی کند. 

def request_refund(order_id, amount, user):
    validate_order_id(order_id)
    validate_amount(amount)

    order = load_order(order_id)

    if order.customer_id != user.customer_id:
        raise PermissionError("Access denied")

    if amount > order.refundable_amount:
        raise ValueError("Amount exceeds refundable balance")

    return create_refund_request(order, amount)

عملیات برگشت‌ناپذیر یا پرریسک باید با کنترل اضافه انجام شوند. مثال: انتقال پول، حذف داده، ارسال ایمیل انبوه، انتشار عمومی یا تغییر سطح دسترسی.

یک الگوی مناسب:

  1. Agent عملیات پیشنهادی را آماده می‌کند.
  2. سیستم اثر عملیات را نشان می‌دهد.
  3. کاربر مجاز آن را تأیید می‌کند.
  4. Server مجوز را دوباره بررسی می‌کند.
  5. عملیات اجرا و ثبت می‌شود.

۹.۸. کنترل دسترسی به Resourceها

مخفی کردن Resource از فهرست، جایگزین کنترل دسترسی نیست. حتی اگر Client URI را بداند، Server باید هنگام خواندن Resource مجوز را بررسی کند.

۱۰. Agent-to-Agent (A2A) Protocol

۱۰.۱. A2A چیست؟

Agent2Agent یا A2A یک استاندارد باز برای ارتباط و همکاری بین Agentهای مستقل است. این Agentها ممکن است با زبان‌های برنامه‌نویسی، Frameworkها، مدل‌ها و ارائه‌دهندگان متفاوت ساخته شده باشند.

A2A تلاش می‌کند یک زبان مشترک برای کشف قابلیت‌ها، شروع Task، تبادل پیام، پیگیری پیشرفت و دریافت خروجی ایجاد کند.

۱۰.۲. چرا A2A لازم است؟

فرض کنید یک سازمان سه Agent مستقل دارد:

Research Agent
Finance Agent
Legal Agent
↕
A2A Protocol
↕
Main Orchestrator Agent

Orchestrator می‌خواهد از Agent مالی تحلیل هزینه و از Agent حقوقی تحلیل ریسک بگیرد. لازم نیست به حافظه، ابزارهای داخلی یا منطق خصوصی آن‌ها دسترسی پیدا کند. کافی است درخواست استانداردی ارسال کند و نتیجه‌ی تعریف‌شده‌ای دریافت کند.

۱۰.۳. تفاوت A2A با فراخوانی تابع

فراخوانی تابع معمولاً یک عملیات مشخص را در همان برنامه یا سرویس اجرا می‌کند. اما A2A برای تعامل با یک Agent مستقل طراحی شده است؛ Agentی که ممکن است کار را در چند مرحله انجام دهد، سؤال تکمیلی بپرسد یا خروجی را بعداً تحویل دهد.

Function Call A2A
فراخوانی یک تابع مشخص تعامل با یک Agent مستقل
معمولاً خروجی مستقیم ممکن است Task طولانی‌مدت باشد
قرارداد تابع قرارداد Agent، Task و Message
عموماً در محدوده‌ی سرویس یا برنامه مناسب همکاری بین سیستم‌های مستقل

۱۰.۴. مفاهیم اصلی A2A

Agent Card

Agent Card سندی است که هویت Agent، آدرس Endpoint، قابلیت‌ها، مهارت‌ها و الزامات امنیتی آن را توصیف می‌کند. Client از طریق این سند می‌تواند تشخیص دهد Agent موردنظر برای کار مناسب است یا نه. 

{
  "name": "Finance Analysis Agent",
  "description": "Analyzes financial reports and expenses",
  "url": "https://finance.example.com/a2a",
  "version": "1.0.0",
  "capabilities": {
    "streaming": true,
    "pushNotifications": false
  },
  "skills": [
    {
      "id": "expense-analysis",
      "name": "Expense Analysis",
      "description": "Analyze company expenses"
    },
    {
      "id": "budget-review",
      "name": "Budget Review",
      "description": "Review budget performance"
    }
  ]
}

این نمونه صرفاً نمایشی و خلاصه‌شده است؛ ساختار دقیق Agent Card را باید با نسخه‌ی مشخصات A2A مورد استفاده تطبیق داد.

Task

Task واحد اصلی کار در A2A است. هر Task شناسه‌ی مشخصی دارد و می‌تواند وضعیت اجرای خود را در طول زمان تغییر دهد.

نمونه‌ی وضعیت‌های مفهومی:

  • Submitted: درخواست ثبت شده است.
  • Working: Agent در حال انجام کار است.
  • Input Required: برای ادامه به اطلاعات بیشتری نیاز دارد.
  • Completed: کار با موفقیت تمام شده است.
  • Failed: کار با خطا مواجه شده است.
  • Canceled: کار لغو شده است.

وضعیت‌های دقیق و ساختارهای رسمی را باید در نسخه‌ی مشخصات A2A بررسی کرد.

Message

Message یک نوبت ارتباطی بین Client و Agent است. پیام می‌تواند درخواست اولیه، سؤال تکمیلی، اطلاعات جدید یا به‌روزرسانی وضعیت باشد.

Part

Part کوچک‌ترین واحد محتوایی داخل Message یا Artifact است. می‌تواند متن، فایل یا داده‌ی ساختاریافته باشد.

Artifact

Artifact خروجی ملموس Task است؛ مانند گزارش، فایل، تصویر یا داده‌ی ساختاریافته. در طراحی A2A، پیام و Artifact مفاهیم متفاوتی دارند: Message برای ارتباط است و Artifact برای تحویل نتیجه.

۱۰.۵. جریان کلی A2A

1. Agent Discovery
   Client discovers the remote Agent Card

2. Capability Inspection
   Client checks skills and capabilities

3. Authentication
   Client obtains required credentials

4. Send Message
   Client submits a task request

5. Task Processing
   Remote Agent performs the task

6. Status Updates
   Client receives progress or checks task status

7. Artifact Delivery
   Agent returns the result

8. Completion
   Client consumes the artifact

۱۰.۶. ارتباط هم‌زمان و غیرهم‌زمان

بعضی درخواست‌ها سریع تمام می‌شوند؛ بعضی ممکن است چند دقیقه یا بیشتر زمان ببرند. A2A برای الگوهای مختلف پیگیری کار طراحی شده است.

روش شرح مناسب برای
Request / Response درخواست و پاسخ مستقیم کارهای کوتاه و سریع
Polling Client در فواصل مشخص وضعیت Task را بررسی می‌کند کارهای طولانی با نیاز به پیاده‌سازی ساده
Streaming رویدادها و پیشرفت به‌صورت جریانی دریافت می‌شوند نمایش زنده‌ی پیشرفت
Push Notification Server تغییر مهم را به Webhook اعلام می‌کند کارهای طولانی یا Clientهای غیرمتصل

۱۰.۷. مثال درخواست A2A

فرض کنید Agent اصلی از Agent مالی می‌خواهد هزینه‌های سه‌ماهه را تحلیل کند. 

{
  "jsonrpc": "2.0",
  "id": "req-100",
  "method": "SendMessage",
  "params": {
    "message": {
      "role": "user",
      "parts": [
        {
          "kind": "text",
          "text": "Analyze Q3 expenses and identify major cost increases."
        }
      ]
    }
  }
}

ساختار دقیق RPC و نام‌گذاری متدها ممکن است با Binding و نسخه‌ی A2A متفاوت باشد. مثال بالا برای فهم الگوی درخواست است، نه تضمین یک پیاده‌سازی خاص.

۱۰.۸. چرا Task از Message مهم‌تر است؟

در یک سیستم ساده ممکن است ارسال پیام و دریافت پاسخ کافی باشد. اما Agentهای واقعی می‌توانند کارهایی انجام دهند که چند مرحله دارند. Task به Client امکان می‌دهد کار را دنبال کند، وضعیت را بررسی کند، اطلاعات تکمیلی بفرستد یا نتیجه‌ی نهایی را دریافت کند.

۱۰.۹. Agent Card و Discovery

در یک اکوسیستم چندعاملی، Client باید بداند کدام Agent چه مهارتی دارد. Agent Card این اطلاعات را به شکلی قابل کشف و قابل تفسیر ارائه می‌کند.

یک فرآیند انتخاب Agent می‌تواند چنین باشد:

  1. دریافت Agent Card.
  2. خواندن توضیح و فهرست Skillها.
  3. بررسی قابلیت‌های Streaming یا Push.
  4. بررسی روش احراز هویت.
  5. انتخاب Agent مناسب بر اساس نوع Task.
  6. ارسال درخواست و مدیریت چرخه‌ی Task.

۱۰.۱۰. امنیت A2A

  • Agent Card را از منبع قابل اعتماد دریافت کنید.
  • Endpoint و هویت Agent را بررسی کنید.
  • برای ارتباط HTTP از TLS استفاده کنید.
  • توکن‌ها را به‌صورت امن مدیریت کنید.
  • مجوز Taskها را محدود کنید.
  • محتوای Agent خارجی را داده‌ی قابل اعتماد فرض نکنید.
  • برای Webhookها اعتبارسنجی و محدودیت شبکه اعمال کنید.
  • خروجی Agent را پیش از استفاده در عملیات حساس اعتبارسنجی کنید.
A2A به معنی اعتماد کامل به Agent مقابل نیست. پروتکل، قالب تعامل را استاندارد می‌کند؛ اما اعتبار پاسخ، کیفیت تحلیل، مجوزها و امنیت اجرای عملیات همچنان باید در سطح سیستم بررسی شوند.

۱۱. Agent Interoperability

۱۱.۱. Interoperability چیست؟

Interoperability یا قابلیت همکاری به این معناست که سیستم‌های مستقل بتوانند بدون نیاز به یکسان بودن زبان برنامه‌نویسی، Framework، مدل زبانی یا زیرساخت داخلی، با یکدیگر کار کنند.

فرض کنید یک Agent با Python و LangGraph ساخته شده، Agent دوم با TypeScript، Agent سوم با یک Framework اختصاصی و Agent چهارم توسط یک شرکت دیگر ارائه می‌شود. اگر همه‌ی آن‌ها قرارداد مشترک ارتباطی را پشتیبانی کنند، امکان همکاری بین آن‌ها فراهم می‌شود.

۱۱.۲. چرا Interoperability مهم است؟

  • کاهش وابستگی به یک Framework.
  • امکان استفاده از Agentهای تخصصی شرکت‌های مختلف.
  • جایگزینی تدریجی اجزای سیستم.
  • استفاده‌ی مجدد از قابلیت‌های سازمانی.
  • تقسیم مسئولیت میان تیم‌ها و سرویس‌ها.
  • امکان توسعه‌ی اکوسیستم Agentها.

۱۱.۳. تفاوت Interoperability فنی و معنایی

صرفاً اینکه دو سیستم بتوانند JSON ردوبدل کنند، به معنی همکاری کامل نیست.

Technical Interoperability

آیا دو سیستم می‌توانند پیام را منتقل و ساختار آن را parse کنند؟

Semantic Interoperability

آیا دو سیستم از معنای داده، واحدها، شناسه‌ها و قواعد کسب‌وکار برداشت یکسانی دارند؟

برای مثال، یک Agent مبلغی را به یورو و Agent دیگر همان فیلد را به دلار تفسیر کند، ارتباط از نظر فنی موفق است ولی از نظر معنایی شکست خورده است.

۱۱.۴. قراردادهای داده

برای همکاری قابل اعتماد، ساختار داده باید روشن باشد:

  • نام فیلدها.
  • نوع داده.
  • واحد اندازه‌گیری.
  • منطقه‌ی زمانی.
  • شناسه‌ی یکتا.
  • نسخه‌ی Schema.
  • قواعد اعتبارسنجی.
  • معنای مقادیر Null و Missing.

۱۱.۵. Versioning

پروتکل‌ها و قراردادها تغییر می‌کنند. اگر یک Agent فیلدی را حذف کند یا معنای آن را عوض کند، مصرف‌کنندگان قدیمی ممکن است خراب شوند.

راهکارها:

  • نسخه‌گذاری API و Schema.
  • تغییرات سازگار تا حد امکان.
  • مستندسازی Breaking Changes.
  • تست سازگاری Client و Server.
  • تعیین دوره‌ی پشتیبانی از نسخه‌های قبلی.

۱۱.۶. مدیریت هویت و اعتماد بین Agentها

در سیستم‌های چندسازمانی، صرف دانستن URL یک Agent کافی نیست. باید مشخص شود Agent متعلق به چه سازمانی است، چه هویتی دارد، چه Scopeهایی دارد و چه داده‌ای مجاز است دریافت کند.

۱۱.۷. Observability در همکاری چند Agent

۱۱.۸. خطاهای متداول Interoperability

  • تفاوت در نسخه‌ی پروتکل.
  • تفاوت در Schema ورودی و خروجی.
  • تفاوت در معنای داده‌ها.
  • ناسازگاری در Authentication.
  • تفاوت در مدل مدیریت Task.
  • عدم پشتیبانی از Streaming یا قابلیت‌های اختیاری.
  • اعتماد بیش از حد به خروجی Agent مقابل.
  • نداشتن قرارداد برای خطا و Timeout.

۱۱.۹. اصول طراحی Agentهای قابل همکاری

  1. قابلیت‌های خود را دقیق توصیف کنید.
  2. ورودی و خروجی ساختاریافته داشته باشید.
  3. از Schemaهای نسخه‌گذاری‌شده استفاده کنید.
  4. خطاها را قابل تشخیص برگردانید.
  5. وضعیت Taskهای طولانی را مدیریت کنید.
  6. هویت و مجوز را مستقل از متن Prompt بررسی کنید.
  7. منبع و سطح اطمینان داده را حفظ کنید.
  8. از قابلیت‌های اختیاری فقط در صورت توافق استفاده کنید.

  2. از طریق A2A از Agent مالی تحلیل هزینه می‌خواهد.
  3. از طریق A2A از Agent حقوقی تحلیل قرارداد می‌خواهد.
  4. Agent مالی از MCP برای خواندن داده‌های مالی استفاده می‌کند.
  5. Agent حقوقی از MCP برای خواندن اسناد و سیاست‌ها استفاده می‌کند.
  6. هر دو Agent خروجی خود را به شکل Artifact تحویل می‌دهند.
  7. Agent اصلی نتایج را اعتبارسنجی و ترکیب می‌کند.
  8. گزارش نهایی به کاربر ارائه می‌شود.
الگوی ذهنی پیشنهادی: MCP را برای «اتصال به قابلیت‌ها و داده‌ها» و A2A را برای «درخواست و مدیریت کار از Agentهای مستقل» در نظر بگیرید.

۱۳.۶. شبه‌کد Orchestrator

قطعه‌کد زیر منطق معماری را نشان می‌دهد و یک پیاده‌سازی کامل و قابل اجرای مستقیم نیست. جزئیات SDK، احراز هویت و ساختار دقیق RPC باید با ابزار انتخابی تطبیق داده شوند. 

async def handle_support_request(request):

    # 1. Validate the request
    customer = authenticate_customer(request)
    order_id = validate_order_reference(request.order_id)

    # 2. Read order information through MCP
    order = await mcp.call_tool(
        server="orders",
        tool="get_order_status",
        arguments={"order_id": order_id}
    )

    # 3. Read policy through MCP Resource
    policy = await mcp.read_resource(
        server="policies",
        uri="company://policies/refund"
    )

    # 4. Evaluate basic eligibility
    preliminary = evaluate_policy(order, policy)

    # 5. Delegate complex financial analysis via A2A
    if preliminary.requires_finance_review:

        task = await a2a.send_message(
            agent="finance-agent",
            message={
                "order_id": order_id,
                "objective": "Analyze refund implications"
            }
        )

        finance_result = await a2a.wait_for_task(task.id)

    else:
        finance_result = None

    # 6. Validate the results
    result = verify_evidence(
        order=order,
        policy=policy,
        finance=finance_result
    )

    # 7. Human approval for high-impact actions
    if result.requires_approval:
        return await request_human_approval(result)

    # 8. Compose a response
    return compose_customer_response(result)

  • سفارش وجود ندارد.
  • کاربر مالک سفارش نیست.
  • سیاست بازپرداخت در دسترس نیست.
  • Agent مالی پاسخ نمی‌دهد.
  • Agent مالی خروجی نامعتبر می‌دهد.
  • مبلغ بازپرداخت از حد مجاز بیشتر است.
  • درخواست نیاز به تأیید انسانی دارد.

۱۷. تمرین‌های عملی برای تسلط بیشتر

تمرین ۱: طراحی MCP Server

یک Server برای مدیریت کتابخانه طراحی کنید. حداقل سه Tool برای جست‌وجو، امانت دادن و بازگرداندن کتاب تعریف کنید. مشخص کنید کدام عملیات نیازمند مجوز است.

تمرین ۲: Resource Design

برای یک سازمان، Resourceهایی برای سیاست مرخصی، راهنمای منابع انسانی و Schema پایگاه داده تعریف کنید. URI و سطح دسترسی هرکدام را مشخص کنید.

تمرین ۳: Prompt Design

یک Prompt استاندارد برای تحلیل گزارش خطای نرم‌افزار بسازید. ورودی‌ها، خروجی مورد انتظار و محدودیت‌های آن را تعریف کنید.

تمرین ۴: انتخاب Transport

سه سناریو طراحی کنید: ابزار محلی IDE، Server سازمانی و سرویس عمومی راه دور. برای هرکدام Transport مناسب را انتخاب و دلیل آن را توضیح دهید.

تمرین ۵: طراحی Agent Card

برای یک Agent متخصص تحلیل داده، Agent Card طراحی کنید. نام، توضیح، Endpoint، Skillها، قابلیت‌های Streaming و روش احراز هویت را مشخص کنید.

تمرین ۶: A2A Task Lifecycle

یک Task طولانی برای تولید گزارش طراحی کنید. مشخص کنید Client چگونه Task را ایجاد، وضعیت را پیگیری، اطلاعات تکمیلی ارسال و Artifact نهایی را دریافت می‌کند.

تمرین ۷: امنیت

سناریویی طراحی کنید که یک سند حاوی Prompt Injection به Agent داده می‌شود. نشان دهید چگونه مرز داده‌ی غیرقابل اعتماد، کنترل Tool و تأیید انسانی مانع عملیات غیرمجاز می‌شوند.

۱۸. جمع‌بندی نهایی و مسیر یادگیری

برای تسلط بر MCP و Agent Communication باید سه سطح را یاد بگیرید:

سطح اول: Protocol Fundamentals

درک Host، Client، Server، Tool، Resource، Prompt، JSON-RPC و Transport.

سطح دوم: Implementation

ساخت Server، اتصال Client، طراحی Schema، تست و مدیریت خطا.

سطح سوم: Production Architecture

امنیت، چندمستاجری، Observability، A2A، مدیریت Task و Interoperability.

سطح چهارم: Ecosystem Design

ساخت اکوسیستم Agentهای مستقل که با قراردادهای مشترک با هم همکاری می‌کنند.

ترتیب پیشنهادی یادگیری

  1. یک MCP Server ساده بسازید.
  2. یک Tool و یک Resource به آن اضافه کنید.
  3. با یک Client واقعی به Server وصل شوید.
  4. ورودی و خروجی‌ها را Schema-based کنید.
  5. Authentication و Authorization را اضافه کنید.
  6. یک Agent مستقل بسازید که MCP را مصرف کند.
  7. Agent دوم را با A2A در دسترس قرار دهید.
  8. Taskهای طولانی و Streaming را پیاده‌سازی کنید.
  9. Tracing، Logging و تست‌های امنیتی را اضافه کنید.
توصیه‌ی مهندسی: از یک MCP Server کوچک و یک Agent ساده شروع کنید. سپس A2A را فقط زمانی اضافه کنید که واقعاً به استقلال، مالکیت جداگانه، همکاری بین سیستم‌ها یا واگذاری Task به Agentهای مستقل نیاز دارید. پیچیدگی بیشتر لزوماً به معنی معماری بهتر نیست.
