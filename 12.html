مقدمه: از مدل زبانی تا عامل هوشمند پیشرفته

نسل جدید هوش مصنوعی فقط برای تولید متن، پاسخ دادن به سؤال یا خلاصه‌سازی اطلاعات طراحی نشده است. سیستم‌های پیشرفته‌تر می‌توانند هدفی را دریافت کنند، آن را به وظایف کوچک‌تر تقسیم کنند، ابزارهای مناسب را انتخاب کنند، محیط را مشاهده کنند، تصمیم بگیرند، اقدام انجام دهند و نتیجه را ارزیابی کنند.

این تغییر، حرکت از AI به‌عنوان یک ابزار پاسخ‌گو به AI به‌عنوان یک سیستم اجرایی و تصمیم‌گیرنده است. به چنین سیستم‌هایی معمولاً Agent یا Agentic System گفته می‌شود.

در یک سیستم Agentic، مدل زبانی می‌تواند نقش مغز تصمیم‌گیرنده را داشته باشد؛ اما برای انجام کار واقعی به اجزای دیگری نیز نیاز دارد: حافظه، ابزارها، محیط اجرایی، دسترسی‌های کنترل‌شده، سیستم ارزیابی، مدیریت خطا و سازوکار نظارت انسانی.

نکته کلیدی: هوشمند بودن یک مدل به‌تنهایی به معنی خودمختار بودن یک سیستم نیست. خودمختاری واقعی از ترکیب مدل، ابزار، حافظه، حلقه اجرا، مشاهده محیط، کنترل دسترسی و ارزیابی نتیجه به وجود می‌آید.

1. AI Coding Agents

AI Coding Agent یک عامل هوشمند است که می‌تواند در یک محیط توسعه نرم‌افزار فعالیت کند، کد را بررسی کند، نیازمندی را بفهمد، فایل ایجاد یا اصلاح کند، تست اجرا کند و برای رسیدن به نتیجه تلاش کند.

1.1. تعریف AI Coding Agent

در برنامه‌نویسی سنتی، توسعه‌دهنده مسئول تمام مراحل است: فهم مسئله، پیدا کردن فایل مناسب، نوشتن کد، اجرای تست، تحلیل خطا و اصلاح برنامه. یک دستیار هوش مصنوعی ساده ممکن است فقط پیشنهاد کد بدهد. اما Coding Agent می‌تواند بخشی از این زنجیره را خودش اجرا کند.

برای مثال، توسعه‌دهنده می‌گوید: «در صفحه ثبت‌نام، امکان ورود با حساب Google اضافه کن و تست‌های مربوط به آن را هم بنویس.» عامل باید ابتدا ساختار پروژه را بفهمد، فایل‌های مرتبط را شناسایی کند، معماری احراز هویت را بررسی کند، تغییرات لازم را اعمال کند و سپس صحت پیاده‌سازی را بسنجد.

بنابراین تفاوت اصلی Coding Agent با تولیدکننده کد این است که Coding Agent در یک چرخه اجرایی قرار دارد و می‌تواند نتیجه اقدامات خود را مشاهده کند.

هـ) Validation

مهم‌ترین اصل در Coding Agent این است که تولید کد پایان کار نیست. عامل باید بررسی کند که کد تولیدشده واقعاً کار می‌کند یا نه. اجرای تست، بررسی نوع داده‌ها، lint، build و بررسی تغییرات بخشی از این مرحله‌اند.

1.4. Context Engineering در Coding Agents

یکی از دشوارترین مسائل در توسعه نرم‌افزار با مدل‌های زبانی، مدیریت Context است. یک پروژه ممکن است هزاران فایل و میلیون‌ها خط کد داشته باشد. ارسال تمام پروژه به مدل نه عملی است و نه همیشه مفید.

بنابراین Coding Agent باید تصمیم بگیرد کدام اطلاعات برای کار فعلی مهم‌اند. این فرایند را می‌توان نوعی Context Engineering دانست.

  • Repository Context: ساختار و معماری کلی پروژه.
  • Task Context: درخواست فعلی و معیارهای پذیرش.
  • Code Context: فایل‌ها و توابع مرتبط با تغییر.
  • Execution Context: خروجی تست‌ها، خطاها و وضعیت اجرا.
  • Historical Context: تصمیمات و تغییرات قبلی مرتبط.
چالش مهم: اگر عامل Context اشتباه یا ناقص دریافت کند، ممکن است کد ظاهراً درست ولی ناسازگار با معماری پروژه تولید کند. به همین دلیل بازیابی دقیق اطلاعات از مخزن کد اهمیت زیادی دارد.

1.5. چرخه کاری یک Coding Agent

while not task_completed:

    observe_project()
    understand_current_state()

    if context_is_insufficient:
        inspect_more_files()

    plan_next_action()

    action = select_tool()

    result = execute(action)

    inspect_result(result)

    if tests_fail:
        diagnose_failure()
        revise_plan()
    else:
        validate_changes()

return final_summary

این کد یک نمایش مفهومی از چرخه عامل است و به یک SDK خاص وابسته نیست. نکته مهم این است که عامل پس از هر اقدام، نتیجه را مشاهده می‌کند و بر اساس آن تصمیم بعدی را می‌گیرد.

2. Autonomous Software Engineering

Autonomous Software Engineering به استفاده از سیستم‌های هوشمند برای مدیریت بخش قابل‌توجهی از چرخه عمر توسعه نرم‌افزار گفته می‌شود؛ از فهم نیازمندی تا طراحی، پیاده‌سازی، تست و نگهداری.

2.1. مفهوم مهندسی نرم‌افزار خودمختار

در توسعه سنتی، انسان مسئول تصمیم‌گیری و اجرای تقریباً تمام مراحل است. ابزارهای اتوماسیون می‌توانند بخشی از کارها را انجام دهند، اما معمولاً بر اساس دستورالعمل‌های ثابت و از پیش تعریف‌شده عمل می‌کنند.

در Autonomous Software Engineering، عامل هوشمند می‌تواند با دریافت یک هدف سطح بالا، وظایف لازم را شناسایی کند، ترتیب آن‌ها را مشخص کند، ابزارهای مناسب را انتخاب کند و با توجه به نتایج، برنامه خود را تغییر دهد.

برای مثال، هدف می‌تواند این باشد: «یک سرویس مدیریت سفارش بساز که کاربران بتوانند سفارش ایجاد کنند، وضعیت آن را ببینند و پس از پرداخت، اعلان دریافت کنند.»

چنین درخواستی فقط یک تابع یا فایل را مشخص نمی‌کند؛ بلکه یک قابلیت نرم‌افزاری نسبتاً کامل است. سیستم باید آن را به نیازمندی‌ها، اجزای معماری، APIها، مدل داده، تست‌ها و مراحل توسعه تبدیل کند.

2.3. چرخه عمر توسعه نرم‌افزار خودمختار

Business Goal | v Requirements Analysis | v Architecture Design | v Implementation Planning | v Code Generation | v Automated Testing | v Review and Approval | v Deployment | v Monitoring and Feedback | +------> New Improvement Cycle

مرحله اول: Requirements Analysis

سیستم باید درخواست تجاری را به نیازمندی‌های قابل پیاده‌سازی تبدیل کند. در این مرحله ابهام‌ها، محدودیت‌ها، کاربران هدف و معیارهای پذیرش شناسایی می‌شوند.

مرحله دوم: Architecture Design

عامل می‌تواند معماری پیشنهادی ارائه کند؛ برای مثال، تشخیص دهد که پروژه به API، پایگاه داده، سیستم احراز هویت، صف پیام و سرویس اعلان نیاز دارد. اما انتخاب معماری باید با محدودیت‌های سازمان، امنیت و مقیاس‌پذیری هماهنگ باشد.

مرحله سوم: Implementation

عامل کد را تولید یا اصلاح می‌کند. بهتر است تغییرات به واحدهای کوچک، قابل تست و قابل بازبینی تقسیم شوند.

مرحله چهارم: Verification

تست‌ها اجرا می‌شوند، خطاها تحلیل می‌شوند و عامل در صورت مجاز بودن، اصلاحات جدید انجام می‌دهد.

مرحله پنجم: Deployment and Monitoring

در سیستم‌های پیشرفته، عامل ممکن است در فرایند انتشار و پایش نیز مشارکت کند. با این حال، اقدامات حساس مانند انتشار به محیط Production باید به مجوزها و سیاست‌های مشخص وابسته باشند.

2.5. چرا Autonomous Engineering دشوار است؟

توسعه نرم‌افزار فقط تولید کد نیست. تصمیم‌های معماری، امنیت، تجربه کاربری، سازگاری با سیستم‌های موجود و پیامدهای تجاری نیز اهمیت دارند. یک عامل ممکن است کدی تولید کند که تست‌های ساده را پشت سر بگذارد، اما در شرایط واقعی با مشکل مواجه شود.

  • Ambiguous Requirements: نیازمندی‌های مبهم یا ناقص.
  • Architectural Consistency: حفظ هماهنگی میان اجزای سیستم.
  • Long-term Maintainability: جلوگیری از ایجاد بدهی فنی.
  • Security: کنترل آسیب‌پذیری‌های کد و زنجیره وابستگی‌ها.
  • Verification: اثبات اینکه خروجی واقعاً نیازمندی را برآورده می‌کند.
  • Accountability: مشخص بودن مسئول تصمیم‌ها و تغییرات.
اصل مهندسی: هرچه اختیار عامل بیشتر می‌شود، کیفیت محدودیت‌ها، ارزیابی‌ها، ثبت رویدادها و امکان بازگشت به وضعیت قبلی نیز باید بیشتر شود.

3. Computer Use Agents

Computer Use Agent عاملی است که به‌جای تعامل صرفاً از طریق API، می‌تواند با رابط گرافیکی کامپیوتر مانند یک کاربر انسانی تعامل کند.

3.1. مفهوم Computer Use

بسیاری از نرم‌افزارها API عمومی ندارند یا دسترسی API آن‌ها محدود است. با این حال، کاربران می‌توانند از طریق صفحه‌نمایش، ماوس و صفحه‌کلید با آن‌ها کار کنند. Computer Use Agent تلاش می‌کند همین نوع تعامل را به شکل کنترل‌شده انجام دهد.

یک عامل ممکن است صفحه را مشاهده کند، دکمه‌ای را تشخیص دهد، روی آن کلیک کند، متن وارد کند، پنجره جدیدی باز کند و نتیجه اقدام خود را بررسی کند.

3.2. اجزای اصلی

Perception

درک وضعیت صفحه، متن‌ها، پنجره‌ها، آیکون‌ها و عناصر رابط کاربری.

Reasoning

تشخیص اینکه برای رسیدن به هدف، کدام اقدام باید انجام شود.

Action Execution

State Verification

الف) Screenshot-based Interaction

عامل از صفحه‌نمایش تصویر دریافت می‌کند و با استفاده از قابلیت‌های بینایی ماشین، محل عناصر را تشخیص می‌دهد. سپس مختصات موردنظر را برای کلیک یا تایپ انتخاب می‌کند.

مزیت این روش آن است که تقریباً به ساختار داخلی برنامه وابسته نیست. اما اگر اندازه پنجره، مقیاس صفحه، موقعیت عناصر یا ظاهر رابط تغییر کند، مختصات قبلی ممکن است دیگر معتبر نباشند.

ب) Accessibility Tree

برخی محیط‌ها ساختار معنایی رابط کاربری را در اختیار سیستم قرار می‌دهند. در این حالت عامل به‌جای تشخیص صرفاً تصویری، می‌تواند نام، نقش و وضعیت عناصر را بخواند. برای مثال، به‌جای کلیک روی مختصات یک دکمه، دکمه‌ای با نام «Save» را پیدا کند.

ج) DOM-based Interaction

در محیط‌های مبتنی بر وب، ممکن است دسترسی به DOM وجود داشته باشد. این روش از نظر معنایی غنی‌تر از مختصات خام است؛ اما همچنان باید در برابر تغییرات ساختار صفحه و محتوای غیرقابل اعتماد مقاوم باشد.

روش مزیت محدودیت
Screenshot سازگاری با طیف گسترده‌ای از برنامه‌ها حساسیت به تغییرات بصری و مختصات
Accessibility Tree درک معنایی عناصر وابسته به کیفیت پشتیبانی برنامه
DOM دسترسی به ساختار وب محدود به محیط‌های قابل دسترسی و قابل اعتماد

3.5. کاربردهای Computer Use Agents

  • کار با نرم‌افزارهای اداری و سازمانی
  • تکمیل فرم‌های چندمرحله‌ای
  • انتقال داده میان برنامه‌های مختلف
  • کار با نرم‌افزارهای قدیمی فاقد API مناسب
  • انجام عملیات تکراری در محیط دسکتاپ
  • کمک به تست رابط کاربری
  • تعامل با داشبوردهای مدیریتی

3.6. محدودیت‌ها و ریسک‌ها

  • تغییر ناگهانی رابط کاربری
  • اشتباه در تشخیص عناصر مشابه
  • از دست رفتن وضعیت در پنجره‌های متعدد
  • اجرای دوباره عملیات غیرقابل بازگشت
  • تعامل ناخواسته با محتوای مخرب روی صفحه
  • افشای اطلاعات در زمان مشاهده یا ثبت صفحه
نکته امنیتی: عامل نباید صرفاً به دلیل مشاهده یک دکمه، مجاز به فشردن آن باشد. عملیات مالی، حذف داده، ارسال پیام، تغییر دسترسی و اقدامات حساس باید سیاست مجوز و تأیید متناسب داشته باشند.

این مثال شبه‌کد است. نام توابع و شیوه اجرای عملیات به محیط و ابزار Computer Use وابسته است.

4. Browser Automation Agents

Browser Automation Agent عاملی است که می‌تواند در محیط مرورگر وب حرکت کند، صفحات را بخواند، فرم‌ها را تکمیل کند، اطلاعات را استخراج کند و جریان‌های کاری تحت وب را انجام دهد.

4.1. تفاوت Browser Automation با Computer Use

Browser Automation بر تعامل با وب‌سایت‌ها و برنامه‌های تحت وب تمرکز دارد. Computer Use دامنه وسیع‌تری دارد و می‌تواند با نرم‌افزارهای دسکتاپ نیز تعامل کند.

Browser Agent ممکن است از DOM، Accessibility Tree یا APIهای مرورگر استفاده کند. در مقابل، Computer Use Agent ممکن است صرفاً با مشاهده صفحه و کلیک روی مختصات کار کند.

4.2. معماری Browser Agent

User Goal | v Browser Agent | +---- Browser Controller | +---- Page Observer | +---- DOM / Accessibility Reader | +---- Navigation Manager | +---- Action Executor | +---- Session and Cookie Manager | +---- Verification Layer | v Web Application

4.3. قابلیت‌های اصلی

Navigation

عامل باید بتواند بین صفحات حرکت کند، لینک‌ها را دنبال کند، تب‌ها را مدیریت کند و مسیر رسیدن به هدف را تشخیص دهد.

Information Extraction

استخراج اطلاعات از صفحات وب می‌تواند شامل عنوان‌ها، قیمت‌ها، جدول‌ها، وضعیت سفارش، داده‌های فرم یا محتوای یک صفحه باشد. عامل باید میان اطلاعات قابل اعتماد، تبلیغات و محتوای نامرتبط تمایز قائل شود.

Form Interaction

پر کردن فرم فقط وارد کردن متن نیست. عامل باید نوع فیلد، الزامی بودن آن، قالب داده و پیام‌های اعتبارسنجی را تشخیص دهد.

Session Management

برخی عملیات نیازمند ورود کاربر هستند. کوکی‌ها، نشست‌ها و Tokenها باید به شکل امن مدیریت شوند و نباید در گزارش‌ها یا Context عمومی مدل افشا شوند.

4.4. ابزارهای متداول در Browser Automation

در اکوسیستم توسعه، ابزارهایی مانند Playwright، Selenium و Puppeteer برای کنترل مرورگر استفاده می‌شوند. این ابزارها به‌خودی‌خود Agent نیستند؛ بلکه می‌توانند لایه اجرای اقدامات یک Agent باشند.

ابزار کاربرد معمول نقش در سیستم Agentic
Playwright کنترل مرورگر و تست وب اجرای Navigation، کلیک و بررسی وضعیت
Selenium اتوماسیون مرورگر تعامل با صفحات و فرم‌ها
Puppeteer کنترل Chrome و Chromium اجرای عملیات مرورگر از طریق کد

4.5. Browser Agent در برابر Web Scraper

Web Scraper معمولاً داده را بر اساس قواعد مشخص استخراج می‌کند. Browser Agent می‌تواند هدف را تفسیر کند و تصمیم بگیرد کدام صفحات، فیلترها یا مراحل برای رسیدن به نتیجه لازم‌اند.

برای مثال، Scraper ممکن است قیمت تمام محصولات یک صفحه را استخراج کند. اما Browser Agent می‌تواند هدفی مانند «سه محصول مناسب با بودجه مشخص پیدا کن که با ویژگی‌های موردنظر من سازگار باشند» را دنبال کند.

4.6. نمونه جریان کاری

  1. دریافت هدف: پیدا کردن یک سند در پرتال سازمانی.
  2. باز کردن وب‌سایت و بررسی وضعیت ورود.
  3. در صورت نیاز، درخواست ورود امن از کاربر.
  4. جست‌وجوی سند با کلیدواژه‌های مناسب.
  5. بررسی نتایج و انتخاب سند درست.
  6. باز کردن سند و بررسی عنوان و تاریخ.
  7. استخراج اطلاعات موردنیاز.
  8. ارائه نتیجه همراه با منبع و وضعیت اطمینان.

4.7. چالش‌های امنیتی و پایداری

  • محتوای صفحه ممکن است حاوی Prompt Injection باشد.
  • صفحات ممکن است ساختار خود را تغییر دهند.
  • وب‌سایت ممکن است Rate Limit اعمال کند.
  • فرم‌ها ممکن است داده حساس دریافت کنند.
  • کلیک روی دکمه اشتباه ممکن است عملیات مالی یا حقوقی ایجاد کند.
  • عامل ممکن است اطلاعاتی را از یک کاربر به کاربر دیگر منتقل کند.
قاعده طراحی: برای هر عملیات Browser Agent، مشخص کن آیا فقط خواندنی است، داده‌ای را تغییر می‌دهد، اطلاعاتی را منتشر می‌کند یا تعهدی برای کاربر ایجاد می‌کند. سطح کنترل باید متناسب با پیامد عملیات باشد.

5. Deep Research Agents

Deep Research Agent عاملی است که برای پاسخ‌گویی به پرسش‌های پیچیده، چندمرحله‌ای و نیازمند شواهد طراحی می‌شود. این عامل صرفاً جست‌وجو نمی‌کند؛ بلکه سؤال را تحلیل، تحقیق را برنامه‌ریزی، منابع را ارزیابی، اطلاعات را ترکیب و نتیجه را مستند می‌کند.

5.1. تفاوت Search و Deep Research

جست‌وجوی معمولی غالباً با پیدا کردن چند صفحه مرتبط به پایان می‌رسد. اما تحقیق عمیق به یک فرایند منظم نیاز دارد. برای مثال، پرسش «آیا استفاده از معماری Microservices برای یک سامانه جدید مناسب است؟» ممکن است به بررسی هزینه عملیاتی، تیم توسعه، پیچیدگی دامنه، مقیاس‌پذیری، قابلیت اطمینان و تجربه‌های صنعتی نیاز داشته باشد.

جست‌وجوی معمولی تحقیق عمیق
پیدا کردن صفحات مرتبط تبدیل پرسش به مجموعه‌ای از پرسش‌های فرعی
خواندن چند نتیجه جمع‌آوری و ارزیابی شواهد متنوع
خلاصه‌سازی محتوا مقایسه، ترکیب و تحلیل یافته‌ها
پاسخ سریع گزارش ساختارمند با ارجاع و محدودیت‌ها

5.2. معماری Deep Research Agent

Research Question | v +----------------------+ | Query Decomposition | +----------------------+ | v +----------------------+ | Research Planning | +----------------------+ | v +----------------------+ | Search and Retrieval | +----------------------+ | v +----------------------+ | Source Evaluation | +----------------------+ | v +----------------------+ | Evidence Extraction | +----------------------+ | v +----------------------+ | Synthesis and Compare| +----------------------+ | v +----------------------+ | Citation Validation | +----------------------+ | v Research Report

5.3. Query Decomposition

اولین مرحله تبدیل یک سؤال پیچیده به چند سؤال قابل تحقیق است. فرض کنیم سؤال اصلی این باشد:

«بهترین معماری برای ساخت یک پلتفرم Agentic AI سازمانی چیست؟»

عامل می‌تواند آن را به پرسش‌های زیر تقسیم کند:

  • چه نوع معماری برای Orchestration مناسب است؟
  • چگونه باید Tool Execution مدیریت شود؟
  • چه راهکاری برای Memory و State Management وجود دارد؟
  • چگونه امنیت و مجوزها اعمال می‌شوند؟
  • چه روش‌هایی برای Monitoring و Evaluation مناسب‌اند؟
  • چه هزینه‌هایی در مقیاس بالا ایجاد می‌شود؟

5.4. Source Evaluation

یکی از مهم‌ترین قابلیت‌های Deep Research Agent ارزیابی کیفیت منابع است. تعداد زیاد نتایج به معنی کیفیت بالای تحقیق نیست. عامل باید به اعتبار، تاریخ، ارتباط، استقلال و کیفیت شواهد توجه کند.

  • Authority: منبع چه میزان اعتبار تخصصی دارد؟
  • Freshness: اطلاعات چه زمانی منتشر یا به‌روزرسانی شده‌اند؟
  • Relevance: آیا منبع دقیقاً به سؤال پاسخ می‌دهد؟
  • Evidence: آیا ادعا با داده یا سند پشتیبانی شده است؟
  • Independence: آیا چند منبع مستقل همان نتیجه را تأیید می‌کنند؟
  • Bias: آیا منبع انگیزه تجاری یا جانبداری مشخصی دارد؟

5.5. Evidence Extraction

به‌جای ذخیره صرفاً متن صفحات، بهتر است یافته‌ها به شکل واحدهای شواهدی ثبت شوند. هر واحد شواهد می‌تواند شامل ادعا، منبع، بخش پشتیبان، تاریخ، نوع داده و سطح اطمینان باشد. 

{
  "claim": "The system supports asynchronous execution",
  "source": "official_documentation",
  "evidence": "Relevant section describing task execution",
  "published_at": "2026-01-10",
  "source_type": "official",
  "confidence": "high"
}

این JSON صرفاً نمونه‌ای از ساختار داده پیشنهادی است. در سیستم واقعی باید URL دقیق، بخش سند و شناسه منبع نیز نگهداری شوند.

5.6. Synthesis

در مرحله ترکیب، عامل باید یافته‌ها را کنار هم قرار دهد. این کار نباید به کنار هم گذاشتن خلاصه صفحات محدود شود. باید اختلاف‌ها، توافق‌ها، شرایط اعتبار و محدودیت هر نتیجه مشخص شوند.

برای مثال، دو منبع ممکن است درباره مزایای Microservices نظرات متفاوتی داشته باشند. به‌جای انتخاب تصادفی یکی از آن‌ها، عامل باید بررسی کند که آیا تفاوت نتیجه ناشی از اندازه تیم، پیچیدگی دامنه یا میزان ترافیک سیستم است.

5.7. Citation Validation

در تحقیق حرفه‌ای، هر ادعای مهم باید به منبع قابل بررسی متصل باشد. عامل باید مطمئن شود که منبع واقعاً ادعای موردنظر را پشتیبانی می‌کند. صرفاً قرار دادن یک لینک کنار یک جمله کافی نیست.

5.8. کاربردهای Deep Research

  • تحلیل بازار و رقبا
  • تحقیق فناوری و مقایسه معماری‌ها
  • بررسی استانداردها و مستندات فنی
  • تحلیل سیاست‌ها و مقررات
  • آماده‌سازی گزارش‌های مدیریتی
  • بررسی مقالات علمی
  • جمع‌آوری شواهد برای تصمیم‌های محصول

5.9. محدودیت‌های Deep Research

  • منابع نامعتبر یا قدیمی
  • توهم در خلاصه‌سازی یا نسبت دادن ادعا به منبع
  • تکرار چند منبع که همگی از یک منبع اولیه کپی کرده‌اند
  • نادیده گرفتن شواهد مخالف
  • برداشت نادرست از داده‌های آماری
  • نتیجه‌گیری بیش از حد قطعی از شواهد محدود
اصل طلایی تحقیق عمیق: عامل باید بتواند نشان دهد هر نتیجه از کدام شواهد به دست آمده، چه شواهد مخالفی وجود داشته و کدام بخش‌ها هنوز نامطمئن‌اند.

6. Voice Agents

Voice Agent عاملی است که از طریق گفتار با انسان تعامل می‌کند. این سیستم می‌تواند صدای کاربر را دریافت کند، گفتار را بفهمد، تصمیم بگیرد، ابزار اجرا کند و پاسخ صوتی تولید کند.

6.1. معماری سنتی Voice Agent

در معماری کلاسیک، پردازش صوت معمولاً به چند مرحله جداگانه تقسیم می‌شود:

User Speech | v Microphone / Audio Input | v Speech-to-Text (ASR) | v Language Understanding / LLM | v Agent Reasoning and Tools | v Response Generation | v Text-to-Speech (TTS) | v Audio Output

6.2. اجزای اصلی

Automatic Speech Recognition (ASR)

ASR گفتار را به متن تبدیل می‌کند. کیفیت این بخش به لهجه، نویز محیط، سرعت صحبت، کیفیت میکروفون و مدل تشخیص گفتار وابسته است.

Natural Language Understanding

متن تشخیص داده‌شده باید از نظر معنا تحلیل شود. عامل باید قصد کاربر، موجودیت‌ها، محدودیت‌ها و اطلاعات موردنیاز را استخراج کند.

Dialogue Manager

این بخش مدیریت گفت‌وگو را بر عهده دارد: اینکه چه چیزی قبلاً گفته شده، چه اطلاعاتی هنوز لازم است، آیا باید سؤال تکمیلی پرسیده شود و چه زمانی مکالمه پایان یابد.

Text-to-Speech (TTS)

TTS متن پاسخ را به صدا تبدیل می‌کند. کیفیت طبیعی صدا، مکث‌ها، آهنگ گفتار، تلفظ نام‌ها و سرعت پاسخ در تجربه کاربر تأثیر زیادی دارند.

6.3. معماری Speech-to-Speech

در سیستم‌های جدیدتر، امکان استفاده از معماری‌های مستقیم صوت‌به‌صوت نیز وجود دارد. در این حالت، سیستم می‌تواند ورودی صوتی را دریافت کند و خروجی صوتی تولید کند بدون اینکه الزاماً تمام مکالمه به یک متن میانی قابل مشاهده تبدیل شود.

این معماری می‌تواند تأخیر را کاهش دهد و بخشی از ویژگی‌های صوتی مانند لحن و مکث را بهتر حفظ کند. با این حال، مشاهده‌پذیری، کنترل و ارزیابی آن ممکن است پیچیده‌تر باشد.

6.4. Latency در Voice Agents

در مکالمه صوتی، تأخیر اهمیت بسیار زیادی دارد. اگر کاربر صحبت کند و چندین ثانیه برای دریافت پاسخ منتظر بماند، تجربه مکالمه طبیعی از بین می‌رود.

اجزای اصلی تأخیر عبارت‌اند از:

  • زمان دریافت و انتقال صدا
  • زمان تشخیص گفتار
  • زمان تحلیل درخواست توسط مدل
  • زمان اجرای ابزارهای خارجی
  • زمان تولید صوت
  • زمان انتقال و پخش خروجی

برای کاهش تأخیر می‌توان از Streaming، پردازش هم‌زمان بخش‌های صوتی، پاسخ‌های کوتاه اولیه، مدل‌های سریع‌تر و ابزارهای کم‌تأخیر استفاده کرد.

6.5. مدیریت مکالمه و نوبت‌گیری

Voice Agent باید تشخیص دهد که کاربر هنوز در حال صحبت است یا نوبت او تمام شده. این مسئله با مفهومی به نام Turn-taking ارتباط دارد.

همچنین باید امکان Interrupt یا قطع کردن پاسخ وجود داشته باشد. برای مثال، اگر عامل در حال صحبت باشد و کاربر بگوید «صبر کن، منظورم چیز دیگری بود»، سیستم باید بتواند پاسخ جاری را متوقف کند و ورودی جدید را پردازش کند.

6.6. Voice Agent با قابلیت استفاده از ابزار

یک Voice Agent پیشرفته فقط به سؤال‌های گفتاری پاسخ نمی‌دهد؛ می‌تواند عملیات انجام دهد. مثلاً کاربر بگوید: «وضعیت آخرین سفارش من را بررسی کن.»

عامل باید درخواست را بفهمد، ابزار بررسی سفارش را انتخاب کند، اطلاعات را از سیستم سفارش دریافت کند و نتیجه را به شکل صوتی توضیح دهد. 

user_audio = capture_audio()

transcript = recognize_speech(user_audio)

intent = understand_request(transcript)

if intent.requires_external_data:
    result = call_authorized_tool(intent)

response = generate_response(
    user_request=transcript,
    tool_result=result
)

stream_audio(synthesize_speech(response))

  • پشتیبانی مشتریان
  • دستیار صوتی سازمانی
  • رزرو و مدیریت نوبت
  • پاسخ‌گویی به تماس‌های ورودی
  • کمک به اپراتورهای مرکز تماس
  • تعامل صوتی با سیستم‌های صنعتی
  • دستیارهای آموزشی و تمرین مکالمه

6.8. امنیت و حریم خصوصی

  • دریافت رضایت برای ضبط یا ذخیره مکالمه
  • محدود کردن دسترسی به داده‌های صوتی
  • رمزنگاری انتقال و ذخیره‌سازی
  • جلوگیری از افشای اطلاعات حساس در پاسخ صوتی
  • تشخیص مناسب هویت در عملیات حساس
  • ثبت دقیق اقداماتی که عامل از طرف کاربر انجام داده است
نکته مهم: صدای طبیعی به معنی درک درست نیست. Voice Agent باید علاوه بر کیفیت مکالمه، از نظر صحت پاسخ، اجرای درست ابزار، کنترل دسترسی و مدیریت خطا نیز ارزیابی شود.

7. Multimodal Agents

Multimodal Agent عاملی است که می‌تواند با چند نوع داده و ورودی مختلف مانند متن، تصویر، صدا، ویدئو و داده‌های ساختاریافته کار کند.

7.1. مفهوم Multimodality

در سیستم‌های متنی، ورودی و خروجی اصلی زبان است. اما در دنیای واقعی اطلاعات فقط در قالب متن وجود ندارد. یک کاربر ممکن است تصویر یک نمودار را ارسال کند، درباره آن سؤال بپرسد و بخواهد نتیجه در یک فایل ساختاریافته ذخیره شود.

سیستم چندوجهی باید بتواند اطلاعات هر رسانه را پردازش کند و میان آن‌ها ارتباط معنایی برقرار سازد.

7.2. انواع Modalities

Audio گفتار، موسیقی، صدای محیط تشخیص گفتار و تحلیل صوت

7.4. Perception و Reasoning

Perception به معنی استخراج اطلاعات از ورودی است. برای مثال، سیستم باید بتواند اشیای موجود در تصویر را تشخیص دهد، متن داخل عکس را بخواند یا گفتار موجود در صوت را تحلیل کند.

Reasoning مرحله‌ای است که در آن اطلاعات استخراج‌شده برای پاسخ به هدف استفاده می‌شوند. مثلاً سیستم پس از خواندن نمودار باید بتواند روند آن را توضیح دهد، نه اینکه فقط متن برچسب‌های نمودار را بازگو کند.

7.5. Cross-modal Reasoning

یکی از قابلیت‌های مهم عامل‌های چندوجهی، استدلال بین رسانه‌هاست. فرض کنیم کاربر یک ویدئو، یک فایل متنی و یک جدول ارسال کرده است. عامل باید بتواند اطلاعات هر سه را در کنار هم بررسی کند.

مثال:

  • از ویدئو زمان وقوع یک رویداد را استخراج کند.
  • از سند متنی، دستورالعمل مرتبط را پیدا کند.
  • از جدول، مقدار عددی مربوط به همان زمان را بخواند.
  • سپس یک گزارش ترکیبی ارائه دهد.

7.6. مدیریت هم‌ترازی داده‌ها

در کاربردهای چندوجهی، اطلاعات باید به یکدیگر متصل شوند. برای مثال، صوت و ویدئوی یک جلسه باید از نظر زمانی هم‌تراز باشند. اگر زمان‌بندی اشتباه باشد، عامل ممکن است جمله‌ای را به شخص یا رویداد اشتباهی نسبت دهد.

همچنین در تحلیل اسناد اسکن‌شده، ترتیب صفحات، جایگاه جدول‌ها و ارتباط متن با تصویر اهمیت دارند.

7.7. کاربردهای Multimodal Agents

  • تحلیل تصاویر پزشکی با رعایت محدودیت‌های تخصصی و نظارتی
  • تحلیل ویدئوی آموزشی
  • خواندن اسناد و فرم‌های اسکن‌شده
  • تحلیل نمودارهای مالی و عملیاتی
  • کنترل کیفیت بصری در تولید
  • ربات‌های دارای دوربین و میکروفون
  • دستیارهای چندرسانه‌ای برای کاربران

7.8. چالش‌های Multimodal AI

  • هزینه پردازش تصویر، صوت و ویدئو
  • حجم بالای داده
  • تأخیر در پردازش رسانه‌های طولانی
  • خطای تشخیص و برداشت معنایی
  • مشکل هم‌ترازی زمانی و معنایی
  • ریسک‌های حریم خصوصی در تصاویر و صدا
  • دشواری ارزیابی خروجی‌های چندوجهی
جمع‌بندی: Multimodal Agent باید بتواند اطلاعات رسانه‌های مختلف را نه فقط جداگانه، بلکه در ارتباط با یکدیگر درک و تحلیل کند.

8. Long-running Agents

Long-running Agent عاملی است که برای انجام وظایفی طراحی می‌شود که ممکن است چند دقیقه، چند ساعت، چند روز یا حتی بیشتر طول بکشند.

8.1. چرا به Long-running Agents نیاز داریم؟

بسیاری از وظایف واقعی با یک فراخوانی مدل تمام نمی‌شوند. برای مثال، بررسی هزاران سند، اجرای یک پروژه تحقیقاتی، پیگیری یک فرایند تأیید سازمانی یا مدیریت یک پروژه توسعه نرم‌افزار ممکن است به تعاملات متعدد و انتظار برای رویدادهای خارجی نیاز داشته باشد.

در چنین مواردی نمی‌توان تمام وضعیت کار را فقط در Context یک درخواست مدل نگه داشت. سیستم به State Persistence، زمان‌بندی، بازیابی پس از خطا و مدیریت اجرای مجدد نیاز دارد.

8.2. معماری اصلی

User Goal | v Agent Orchestrator | +---- Persistent State Store | +---- Task Queue | +---- Scheduler | +---- Tool Executor | +---- Checkpoint Manager | +---- Retry / Recovery Manager | +---- Monitoring | v Task Completion

8.3. State Persistence

در عامل‌های کوتاه‌مدت، بخشی از وضعیت ممکن است در حافظه موقت فرایند قرار گیرد. اما اگر فرایند متوقف شود، اطلاعات از دست می‌رود. Long-running Agent باید وضعیت مهم خود را به شکل پایدار ذخیره کند.

نمونه اطلاعاتی که باید ذخیره شوند:

  • هدف اصلی و محدودیت‌های آن
  • وضعیت فعلی وظیفه
  • مراحل تکمیل‌شده
  • نتایج ابزارهای قبلی
  • شناسه درخواست‌های خارجی
  • زمان آخرین اجرا
  • تعداد تلاش‌های مجدد
  • نیازمندی‌های تأیید انسانی

8.4. Checkpointing

Checkpoint یعنی ذخیره یک وضعیت قابل بازیابی در طول اجرای کار. فرض کنیم عامل در حال تحلیل ۱۰۰۰ سند است. اگر پس از پردازش ۷۰۰ سند متوقف شود، نباید مجبور باشد همه ۷۰۰ سند را دوباره پردازش کند.

با ذخیره Checkpoint، سیستم می‌تواند از نقطه‌ای که آخرین بار با موفقیت ثبت شده ادامه دهد.

8.5. Retry و Recovery

در کارهای طولانی، خطا اجتناب‌ناپذیر است: سرویس خارجی ممکن است در دسترس نباشد، اتصال شبکه قطع شود یا یک ابزار پاسخ نامعتبر برگرداند.

سیستم باید میان خطاهای موقت و دائمی تفاوت بگذارد. برای خطاهای موقت می‌توان از Retry با تأخیر افزایشی استفاده کرد. اما تکرار بی‌قیدوشرط یک عملیات ممکن است باعث اجرای دوباره تراکنش شود.

8.6. Idempotency

Idempotency به این معناست که اجرای مجدد یک عملیات، در صورت رعایت قرارداد آن، اثر تکراری ناخواسته ایجاد نکند. این ویژگی برای عملیات مالی، ایجاد سفارش، ارسال پیام و تغییر وضعیت اهمیت زیادی دارد. 

operation_id = create_stable_operation_id(task)

result = execute_operation(
    operation_id=operation_id,
    payload=payload
)

save_checkpoint(
    task_id=task.id,
    last_completed_operation=operation_id,
    result=result
)

8.7. مدیریت زمان و انتظار

عامل ممکن است لازم باشد منتظر پاسخ یک سرویس خارجی یا تأیید انسان بماند. بهتر است در چنین شرایطی سیستم به‌جای اشغال دائمی یک فرایند، وضعیت کار را ذخیره کند و پس از دریافت رویداد مناسب دوباره ادامه دهد.

8.8. کاربردها

  • پروژه‌های تحقیقاتی طولانی
  • فرایندهای سازمانی چندمرحله‌ای
  • تحلیل حجم زیاد اسناد
  • مدیریت چرخه توسعه نرم‌افزار
  • پایش مداوم داده‌ها
  • هماهنگی میان چند عامل
  • اجرای Workflowهای نیازمند تأیید انسانی

8.9. چالش‌ها

  • حفظ State در طول زمان
  • تغییر نیازمندی در میانه اجرا
  • مدیریت عملیات تکراری
  • بازیابی از شکست‌های جزئی
  • کنترل هزینه مدل در اجرای طولانی
  • جلوگیری از ادامه کار بر اساس Context قدیمی
  • مدیریت زمان انقضای مجوزها و نشست‌ها
اصل مهم: Long-running Agent باید مانند یک سیستم توزیع‌شده قابل اعتماد طراحی شود، نه مانند یک گفت‌وگوی طولانی که فقط متن‌های قبلی را در حافظه نگه می‌دارد.

9. Self-improving Agents

Self-improving Agent به سیستمی گفته می‌شود که از نتایج اجرا، بازخوردها و ارزیابی‌ها برای بهبود عملکرد آینده استفاده می‌کند.

9.1. مفهوم بهبود خودکار

فرض کنیم یک عامل بارها وظیفه تحلیل درخواست‌های پشتیبانی را انجام می‌دهد. در ابتدا ممکن است بعضی درخواست‌ها را اشتباه دسته‌بندی کند. اگر سیستم بتواند خطاها را ثبت کند، الگوهای آن‌ها را تشخیص دهد و دستورالعمل‌ها یا ابزارهای خود را اصلاح کند، عملکرد آینده ممکن است بهتر شود.

نکته مهم این است که Self-improvement الزاماً به معنی تغییر خودکار وزن‌های مدل نیست. بهبود می‌تواند در سطح Prompt، حافظه، ابزار، Workflow، قواعد تصمیم‌گیری یا حتی نسخه مدل اتفاق بیفتد.

9.2. سطوح مختلف Self-improvement

سطح نوع بهبود مثال

Level 2 اصلاح Prompt بهبود دستورالعمل عامل
Level 3 اصلاح Workflow تغییر ترتیب مراحل اجرای کار
Level 4 اصلاح ابزارها و سیاست‌ها اضافه کردن اعتبارسنجی جدید

9.3. Feedback Loop

Task Execution | v Outcome Collection | v Evaluation | v Failure Analysis | v Improvement Proposal | v Controlled Validation | v Approved Update | +------> Future Executions

9.4. انواع Feedback

Explicit Feedback

بازخورد مستقیم کاربر است؛ مانند امتیاز دادن، تأیید پاسخ یا گزارش اشتباه.

Implicit Feedback

بازخوردی است که از رفتار سیستم یا کاربر استنباط می‌شود؛ مانند اینکه کاربر پاسخ را اصلاح کند یا یک عملیات چند بار تکرار شود. این نوع بازخورد ممکن است مبهم باشد و نباید بدون بررسی به‌عنوان حقیقت قطعی تلقی شود.

Execution Feedback

نتایج واقعی اجرای ابزارها و تست‌ها نیز می‌توانند بازخورد باشند. مثلاً اگر کد تولیدشده تست را رد کند، سیستم شواهدی درباره ضعف راهکار در اختیار دارد.

9.5. Reflection

Reflection یعنی عامل عملکرد قبلی خود را بررسی کند و درباره نقاط قوت و ضعف آن نتیجه‌گیری کند. برای مثال، پس از تکمیل یک وظیفه می‌تواند به این سؤال‌ها پاسخ دهد:

  • کدام مرحله بیشترین خطا را داشت؟
  • آیا ابزار مناسبی انتخاب شد؟
  • آیا Context کافی وجود داشت؟
  • آیا مسیر اجرای کار بیش از حد پیچیده بود؟
  • برای اجرای بعدی چه تغییری می‌تواند مفید باشد؟

Reflection به‌تنهایی تضمین‌کننده یادگیری نیست. عامل ممکن است درباره عملکرد خود تحلیل نادرست ارائه دهد. بنابراین پیشنهادهای حاصل از Reflection باید با معیارهای بیرونی اعتبارسنجی شوند.

9.6. Memory-based Improvement

یکی از ساده‌ترین روش‌های بهبود عامل، استفاده از حافظه است. عامل می‌تواند تجربه‌های مفید را به شکل اطلاعات ساختاریافته ذخیره کند.

برای مثال:

{
  "task_type": "generate_api_tests",
  "lesson": "Include authorization failure cases",
  "evidence": "Previous test suite missed an access-control bug",
  "confidence": 0.91,
  "scope": "projects_using_role_based_access"
}

حافظه نباید به انبار نامحدود تجربه‌ها تبدیل شود. اطلاعات قدیمی، نادرست یا وابسته به یک پروژه خاص ممکن است در پروژه دیگری مضر باشند. حافظه باید تاریخ، منبع، دامنه اعتبار و امکان حذف یا اصلاح داشته باشد.

9.7. Self-improvement و Fine-tuning

در برخی سیستم‌ها، داده‌های جمع‌آوری‌شده می‌توانند برای Fine-tuning استفاده شوند. اما این کار باید با انتخاب داده مناسب، حذف اطلاعات حساس، بررسی کیفیت برچسب‌ها و ارزیابی قبل و بعد از آموزش انجام شود.

تغییر وزن‌های مدل در محیط Production به شکل خودکار و بدون ارزیابی می‌تواند رفتار سیستم را غیرقابل پیش‌بینی کند. به همین دلیل بهتر است چرخه آموزش و انتشار مدل از اجرای روزمره عامل جدا باشد.

9.8. خطرات Self-improvement

  • یادگیری از بازخورد اشتباه یا دستکاری‌شده
  • تقویت سوگیری‌های موجود
  • فراموشی توانایی‌های قبلی
  • تغییر ناخواسته رفتار سیستم
  • بهینه‌سازی یک معیار و آسیب به معیارهای دیگر
  • ذخیره اطلاعات محرمانه در حافظه بلندمدت
  • ایجاد چرخه‌های بازخورد ناپایدار
اصل ایمنی: عامل می‌تواند بهبود را پیشنهاد دهد؛ اما هر تغییری که روی رفتار، مجوزها، ابزارها یا مدل Production اثر می‌گذارد باید از مسیر اعتبارسنجی و انتشار کنترل‌شده عبور کند.

10. Agentic AI Design Patterns

Design Patternهای Agentic AI الگوهای تکرارشونده‌ای برای طراحی، سازمان‌دهی و کنترل سیستم‌های مبتنی بر عامل هستند. هدف آن‌ها حل مسائل معماری مانند تقسیم وظایف، مدیریت ابزارها، کنترل جریان، اعتبارسنجی و همکاری چند عامل است.

10.1. چرا به Design Pattern نیاز داریم؟

طراحی یک Agent فقط انتخاب مدل و نوشتن Prompt نیست. باید مشخص شود چه کسی تصمیم می‌گیرد، چه کسی ابزار اجرا می‌کند، وضعیت کجا ذخیره می‌شود، خطا چگونه مدیریت می‌شود و چه زمانی انسان باید وارد فرایند شود.

Design Patternها به ما کمک می‌کنند به‌جای طراحی تصادفی، از راهکارهای معماری قابل فهم و قابل تکرار استفاده کنیم.

10.2. Pattern اول: ReAct (Reasoning and Acting)

در الگوی ReAct، عامل میان تحلیل مسئله و انجام اقدام جابه‌جا می‌شود. به‌جای اینکه فقط یک پاسخ نهایی تولید کند، اطلاعات لازم را از محیط دریافت می‌کند، اقدام انجام می‌دهد و نتیجه را برای تصمیم بعدی به کار می‌گیرد.

Goal | v Reason | v Choose Action | v Observe Result | v Reason Again | v Final Response

این الگو برای کارهایی مناسب است که اطلاعات لازم از ابتدا در اختیار عامل نیست. با این حال، باید تعداد گام‌ها، نوع ابزارها و شرایط توقف محدود شوند.

10.3. Pattern دوم: Tool Calling

در Tool Calling، مدل بر اساس درخواست تصمیم می‌گیرد از یک ابزار استفاده کند. ابزار می‌تواند یک API، پایگاه داده، سیستم جست‌وجو یا عملیات داخلی باشد. 

{
  "tool": "get_order_status",
  "arguments": {
    "order_id": "ORD-1042"
  }
}

این مثال صرفاً یک ساختار مفهومی برای فراخوانی ابزار است. سیستم اجرایی باید ورودی را اعتبارسنجی کند، مجوز را بررسی کند و خروجی ابزار را به عامل برگرداند.

10.4. Pattern سوم: Planner–Executor

در این الگو، یک بخش مسئول برنامه‌ریزی است و بخش دیگر وظایف برنامه را اجرا می‌کند. Planner هدف را به مراحل کوچک‌تر تبدیل می‌کند. Executor هر مرحله را انجام می‌دهد و نتیجه را برمی‌گرداند.

User Goal | v +----------------+ | Planner Agent | +----------------+ | v Task Plan | v +----------------+ | Executor | +----------------+ | v Execution Result | v Planner Review | +----> Replan if needed

مزیت این الگو جداسازی تصمیم‌گیری سطح بالا از اجرای جزئیات است. نقطه ضعف آن می‌تواند هزینه بیشتر، تأخیر و وابستگی به کیفیت برنامه‌ریزی باشد.

10.5. Pattern چهارم: Router

Router ابتدا نوع درخواست را تشخیص می‌دهد و سپس آن را به عامل یا ابزار مناسب می‌فرستد. برای مثال، درخواست‌های مالی به عامل مالی، درخواست‌های برنامه‌نویسی به Coding Agent و درخواست‌های تحقیقاتی به Research Agent هدایت می‌شوند. 

request = classify(user_input)

switch request.category:

    case "coding":
        return coding_agent.run(request)

    case "research":
        return research_agent.run(request)

    case "data_analysis":
        return analytics_agent.run(request)

    default:
        return general_agent.run(request)

10.6. Pattern پنجم: Supervisor

در معماری Supervisor، یک عامل مرکزی وظایف را میان چند عامل تخصصی توزیع می‌کند. Supervisor مسئول انتخاب عامل، مدیریت وابستگی‌ها و ترکیب نتایج است.

برای مثال، در یک پروژه تولید گزارش:

  • Research Agent اطلاعات بیرونی را جمع‌آوری می‌کند.
  • Data Agent داده‌های داخلی را تحلیل می‌کند.
  • Writing Agent گزارش را می‌نویسد.
  • Reviewer Agent کیفیت و سازگاری گزارش را بررسی می‌کند.
  • Supervisor نتیجه نهایی را تجمیع می‌کند.

10.7. Pattern ششم: Sequential Pipeline

در Pipeline، خروجی هر مرحله به ورودی مرحله بعد تبدیل می‌شود. این الگو زمانی مناسب است که ترتیب مراحل مشخص باشد.

Input | v Research | v Analysis | v Draft | v Review | v Final Output

10.8. Pattern هفتم: Parallel Agents

در این الگو چند عامل به‌صورت هم‌زمان روی بخش‌های مستقل یک مسئله کار می‌کنند. سپس نتایج آن‌ها ترکیب می‌شود.

برای مثال، سه عامل می‌توانند یک موضوع را از دیدگاه امنیت، عملکرد و هزینه بررسی کنند.

اجرای موازی می‌تواند زمان را کاهش دهد؛ اما هزینه، پیچیدگی هماهنگی و احتمال اختلاف نتایج را افزایش می‌دهد.

10.9. Pattern هشتم: Critic–Reviewer

یک عامل خروجی تولید می‌کند و عامل دیگری آن را نقد یا اعتبارسنجی می‌کند. Reviewer باید معیارهای مشخصی داشته باشد؛ مثلاً صحت، کامل بودن، رعایت نیازمندی‌ها، امنیت و سازگاری.

صرفاً استفاده از دو مدل به معنی تضمین کیفیت نیست. اگر هر دو مدل از یک فرض اشتباه پیروی کنند، ممکن است خروجی غلط یکدیگر را تأیید کنند. تست‌های مستقل و شواهد بیرونی همچنان ضروری‌اند.

10.10. Pattern نهم: Human-in-the-Loop

در این الگو، انسان در نقاط حساس فرایند حضور دارد. سیستم ممکن است بخش‌های کم‌ریسک را خودکار انجام دهد، اما برای عملیات مهم تأیید بخواهد.

نمونه نقاط تأیید:

  • تأیید قبل از انتشار کد
  • تأیید قبل از پرداخت
  • تأیید قبل از حذف داده
  • تأیید قبل از ارسال پیام به مشتری
  • تأیید تغییر سیاست یا مجوزهای دسترسی

10.11. Pattern دهم: Blackboard

در الگوی Blackboard، چند عامل یا جزء سیستم روی یک فضای مشترک اطلاعاتی کار می‌کنند. هر عامل می‌تواند بخشی از مسئله را تکمیل کند و نتیجه خود را در فضای مشترک قرار دهد.

این الگو برای مسائل پیچیده‌ای مفید است که حل آن‌ها به اطلاعات تولیدشده توسط چند تخصص نیاز دارد. اما باید مشخص باشد چه کسی مجاز به تغییر هر بخش است و تعارض‌ها چگونه حل می‌شوند.

10.12. Pattern یازدهم: Reflection Loop

عامل خروجی خود را بررسی می‌کند، ضعف‌ها را پیدا می‌کند و نسخه اصلاح‌شده تولید می‌کند. برای جلوگیری از تکرار بی‌پایان، باید تعداد دورها و معیار توقف مشخص باشند.

10.13. Pattern دوازدهم: Map-Reduce

مسئله به بخش‌های مستقل تقسیم می‌شود، هر بخش جداگانه پردازش می‌شود و سپس نتایج با هم ترکیب می‌شوند. این روش برای تحلیل مجموعه‌های بزرگ سند یا داده مناسب است.

11. Future of Agentic AI

آینده Agentic AI احتمالاً به سمت سیستم‌هایی حرکت می‌کند که توانایی بیشتری در برنامه‌ریزی، استفاده از ابزار، تعامل با محیط، همکاری میان عامل‌ها و مدیریت وظایف پیچیده دارند. اما مسیر پیشرفت فقط افزایش هوش مدل‌ها نیست؛ قابلیت اعتماد، امنیت، هزینه و کنترل نیز تعیین‌کننده‌اند.

11.1. حرکت از Chatbot به سیستم‌های اجرایی

Chatbot معمولاً در قالب مکالمه با کاربر تعامل دارد. Agentic System می‌تواند مکالمه را به مجموعه‌ای از عملیات تبدیل کند. برای مثال، به‌جای توضیح دادن نحوه تهیه گزارش، داده‌ها را دریافت کند، تحلیل را انجام دهد، نمودار بسازد و گزارش آماده کند.

این تحول به معنی حذف رابط گفت‌وگویی نیست؛ بلکه مکالمه به یکی از راه‌های تعریف هدف و کنترل سیستم تبدیل می‌شود.

11.2. افزایش همکاری میان عامل‌ها

با رشد سیستم‌های چندعاملی، احتمالاً نیاز به استانداردهای مشترک برای شناسایی عامل‌ها، کشف قابلیت‌ها، ارسال وظایف و تبادل نتایج بیشتر خواهد شد.

در چنین معماری‌هایی، یک عامل ممکن است از عامل دیگری برای تحلیل داده، جست‌وجوی اطلاعات، توسعه نرم‌افزار یا اجرای یک وظیفه تخصصی کمک بگیرد.

برای این همکاری، پروتکل‌هایی مانند Agent-to-Agent (A2A) اهمیت پیدا می‌کنند. همچنین پروتکل‌هایی مانند Model Context Protocol (MCP) می‌توانند دسترسی عامل به ابزارها و منابع را استانداردتر کنند.

11.3. عامل‌های دارای حافظه پیشرفته‌تر

یکی از مسیرهای مهم توسعه، بهبود حافظه عامل‌هاست. سیستم‌ها به‌جای اتکا به Context یک مکالمه، می‌توانند اطلاعات مرتبط را در حافظه کوتاه‌مدت، بلندمدت و حافظه مخصوص وظیفه نگهداری کنند.

چالش اصلی فقط ذخیره اطلاعات نیست؛ بلکه تشخیص این است که چه چیزی ارزش ذخیره دارد، چه زمانی باید بازیابی شود و چگونه اطلاعات قدیمی یا اشتباه اصلاح شوند.

11.4. افزایش توانایی استفاده از کامپیوتر

Computer Use و Browser Automation می‌توانند دامنه کاربرد عامل‌ها را گسترش دهند. عامل‌ها ممکن است در آینده بتوانند با طیف بیشتری از نرم‌افزارها، رابط‌های کاربری و ابزارهای سازمانی تعامل کنند.

با این حال، قابلیت کنترل رابط کاربری باید همراه با تشخیص خطا، محدودیت مجوز، تأیید عملیات حساس و ثبت رویدادها توسعه یابد.

11.5. عامل‌های چندوجهی و محیط‌محور

عامل‌های چندوجهی می‌توانند متن، تصویر، صوت و ویدئو را در کنار هم پردازش کنند. این قابلیت در سیستم‌های رباتیک، دستیارهای محیطی، آموزش، صنعت و کنترل کیفیت اهمیت دارد.

در آینده ممکن است تعامل با عامل‌ها از صفحه چت فراتر رود: کاربر صحبت کند، تصویر نشان دهد، یک محیط را به اشتراک بگذارد و عامل بر اساس ترکیب این ورودی‌ها اقدام کند.

11.6. افزایش اهمیت Agent Governance

هرچه عامل‌ها اختیار بیشتری پیدا کنند، مدیریت آن‌ها نیز اهمیت بیشتری خواهد داشت. سازمان‌ها باید بدانند هر عامل چه کاری می‌تواند انجام دهد، به چه داده‌هایی دسترسی دارد، چه ابزارهایی را اجرا می‌کند و چه کسی مسئول نتیجه اقدامات آن است.

موضوعات کلیدی Governance عبارت‌اند از:

  • هویت و احراز هویت عامل
  • مجوزهای دقیق و حداقلی
  • ثبت اقدامات و تصمیم‌ها
  • محدودیت‌های هزینه و زمان اجرا
  • سیاست‌های تأیید انسانی
  • مدیریت داده و حریم خصوصی
  • قابلیت توقف و لغو عملیات
  • بررسی و ممیزی رفتار عامل

11.7. اقتصاد عامل‌ها و Cost-aware Agents

در سیستم‌های Agentic، هزینه فقط هزینه یک درخواست مدل نیست. ممکن است یک وظیفه شامل چندین فراخوانی مدل، جست‌وجو، اجرای ابزار، پردازش فایل، تولید صوت یا تحلیل تصویر باشد.

بنابراین عامل‌های آینده باید نسبت به هزینه و زمان حساس‌تر باشند. برای مثال، برای یک سؤال ساده از مدل کوچک‌تر استفاده کنند و فقط در مسائل پیچیده به مدل قوی‌تر مراجعه کنند.

همچنین باید بدانند چه زمانی ادامه تحقیق یا اجرای ابزار دیگر ارزش افزوده کافی ندارد.

11.8. حرکت به سمت سیستم‌های قابل اعتماد

در کاربردهای واقعی، توانایی انجام کار بدون تضمین صحت کافی نیست. یک سیستم قابل اعتماد باید خروجی خود را بررسی کند، در صورت نبود شواهد مناسب عدم قطعیت را بیان کند و برای عملیات حساس کنترل‌های مناسب داشته باشد.

ویژگی‌های مهم یک Agent قابل اعتماد:

  • قابلیت توضیح مسیر اجرای کار
  • ثبت منبع اطلاعات و نتیجه ابزارها
  • مدیریت خطا و بازیابی
  • کنترل دسترسی و مجوز
  • ارزیابی مستمر کیفیت
  • امکان مداخله و توقف انسانی
  • سازگاری با تغییر نسخه‌ها و ابزارها

11.9. محدودیت‌هایی که احتمالاً همچنان مهم خواهند بود

حتی با پیشرفت مدل‌ها، تعدادی از چالش‌ها از بین نمی‌روند:

  • ابهام در نیازمندی‌های انسانی
  • کمبود اطلاعات قابل اعتماد
  • پیامدهای پیش‌بینی‌نشده اقدامات
  • محدودیت منابع محاسباتی
  • تعارض میان اهداف و سیاست‌ها
  • امنیت در محیط‌های باز و غیرقابل اعتماد
  • مسئولیت‌پذیری در تصمیم‌های خودکار

11.10. یک سناریوی آینده‌نگرانه

تصور کن یک شرکت برای توسعه یک محصول جدید از یک سیستم Agentic استفاده می‌کند. کاربر فقط هدف تجاری را تعریف می‌کند: «یک پلتفرم مدیریت اشتراک برای مشتریان سازمانی بساز.»

سیستم می‌تواند مجموعه‌ای از عامل‌های تخصصی داشته باشد:

  • Product Agent: تحلیل نیازمندی‌های محصول.
  • Research Agent: بررسی بازار و محصولات مشابه.
  • Architecture Agent: پیشنهاد معماری نرم‌افزار.
  • Coding Agent: پیاده‌سازی بخش‌های نرم‌افزاری.
  • Testing Agent: طراحی و اجرای تست‌ها.
  • Security Agent: بررسی ریسک‌ها و کنترل‌های امنیتی.
  • Deployment Agent: آماده‌سازی فرایند انتشار.
  • Monitoring Agent: بررسی عملکرد پس از انتشار.

این عامل‌ها ممکن است از طریق پروتکل‌های استاندارد با یکدیگر ارتباط برقرار کنند، به ابزارهای سازمانی متصل شوند و وضعیت کار را در یک سیستم هماهنگ‌کننده نگه دارند. با این حال، تصمیم‌های مهم معماری، انتشار و تغییرات حساس همچنان باید در چارچوب سیاست‌های سازمان و نظارت انسانی انجام شوند.

جمع‌بندی نهایی: آینده Agentic AI صرفاً ساخت مدل‌های بزرگ‌تر نیست. بخش مهمی از پیشرفت در معماری عامل‌ها، همکاری میان آن‌ها، حافظه، تعامل با محیط، استفاده از ابزار، ارزیابی، امنیت و مدیریت چرخه عمر سیستم‌های هوشمند اتفاق خواهد افتاد.
