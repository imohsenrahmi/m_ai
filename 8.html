مقدمه: چرا به AI Framework نیاز داریم؟

یک مدل زبانی به‌تنهایی یک محصول هوش مصنوعی کامل نیست. برای تبدیل مدل به یک سیستم نرم‌افزاری واقعی، باید ورودی‌ها، حافظه، ابزارها، داده‌ها، کنترل اجرای مراحل، مدیریت خطا، امنیت، ارزیابی و مانیتورینگ را هم طراحی کنیم.

فرض کن می‌خواهی یک دستیار هوشمند بسازی که بتواند اسناد شرکت را بخواند، اطلاعات را از پایگاه داده استخراج کند، با چند API ارتباط بگیرد، در صورت نیاز کار را به Agent متخصص واگذار کند و در نهایت گزارشی قابل استناد تولید کند. نوشتن همه این اجزا از صفر ممکن است، اما زمان‌بر و مستعد خطاست.

فریم‌ورک‌ها مجموعه‌ای از abstractionها، ابزارها و الگوهای آماده ارائه می‌کنند تا توسعه‌دهنده به‌جای پیاده‌سازی تمام جزئیات زیرساختی، روی منطق کسب‌وکار و کیفیت سیستم تمرکز کند.

۱. LangChain

LLM Application Framework

LangChain مجموعه‌ای از abstractionها و integrationها برای ساخت برنامه‌های مبتنی بر LLM است. تمرکز آن روی ساده‌کردن ارتباط مدل، Prompt، ابزارها، پیام‌ها، Retrieverها و Agent loop است.

LangChain چه مشکلی را حل می‌کند؟

در توسعه مستقیم با API یک مدل، معمولاً باید خودت درخواست‌ها را بسازی، پیام‌ها را مدیریت کنی، ابزارها را تعریف کنی، خروجی ابزار را به مدل برگردانی، خطاها را مدیریت کنی و بین Providerهای مختلف جابه‌جا شوی. LangChain بسیاری از این اجزا را به abstractionهای قابل ترکیب تبدیل می‌کند.

مفاهیم اصلی LangChain

Models

لایه ارتباط با مدل زبانی. هدف این است که بخش‌های مختلف برنامه به‌جای وابستگی مستقیم به جزئیات یک API، از interface مشخصی استفاده کنند.

Messages

پیام‌های system، human، assistant و پیام‌های مرتبط با tool call که مکالمه و زمینه اجرای مدل را تشکیل می‌دهند.

Prompt Templates

قالب‌هایی برای ساخت Prompt با متغیرهای ورودی. این کار مدیریت Promptهای تکرارشونده را ساده می‌کند.

Tools

توابع یا قابلیت‌هایی که Agent می‌تواند درخواست اجرای آن‌ها را مطرح کند؛ مانند جست‌وجو، محاسبه یا خواندن اطلاعات از API.

Retrievers

اجزایی برای بازیابی اسناد یا قطعه‌های مرتبط با سؤال کاربر از یک منبع داده.

Agents

Agent می‌تواند با توجه به ورودی و نتیجه ابزارها تصمیم بگیرد گام بعدی چیست. پیاده‌سازی Agentهای LangChain بر زیرساخت LangGraph بنا شده است.

اگر مدل به اطلاعات یا اقدام دیگری نیاز داشته باشد، چرخه ادامه پیدا می‌کند.

نمونه کد مفهومی: Agent دارای ابزار

# Illustrative Python-style example
from langchain.agents import create_agent

def get_order_status(order_id: str) -> str:
    """Return the status of an order."""
    return f"Order {order_id}: shipped"

agent = create_agent(
    model="provider:model-name",
    tools=[get_order_status],
    system_prompt=(
        "You are a customer support assistant. "
        "Use the order tool when an order status is requested."
    )
)

result = agent.invoke({
    "messages": [
        {"role": "user", "content": "Where is order 1234?"}
    ]
})

print(result)

این نمونه برای نمایش الگوی استفاده است؛ نام Provider، مدل، importها و جزئیات API باید با نسخه فعلی نصب‌شده هماهنگ شوند.

چه زمانی LangChain انتخاب خوبی است؟

  • وقتی می‌خواهی سریع یک LLM application یا Agent اولیه بسازی.
  • وقتی به integrationهای متعدد برای مدل‌ها و ابزارها نیاز داری.
  • وقتی می‌خواهی اجزای مختلف را به‌صورت modular کنار هم قرار دهی.
  • وقتی قصد داری ابتدا با abstraction سطح بالاتر شروع کنی و بعداً بخش‌های پیچیده را سفارشی‌سازی کنی.

محدودیت‌ها و ریسک‌ها

  • Abstraction زیاد می‌تواند فهم دقیق جریان اجرای برنامه را دشوار کند.
  • تغییر نسخه‌ها ممکن است باعث تغییر importها، APIها یا الگوهای پیشنهادی شود.
  • استفاده بی‌رویه از زنجیره‌ها و اجزای آماده می‌تواند debugging را دشوار کند.
  • Framework جایگزین طراحی معماری، امنیت ابزارها یا ارزیابی کیفیت نمی‌شود.
توصیه: برای ساخت Agentهای معمولی و اتصال ابزارها، LangChain نقطه شروع مناسبی است. اگر به کنترل دقیق روی state، چرخه‌های پیچیده، وقفه و ادامه اجرا نیاز داری، LangGraph را جدی بررسی کن.

۲. LangGraph

Stateful Agent Orchestration

LangGraph یک فریم‌ورک سطح پایین‌تر برای طراحی و اجرای Workflowها و Agentهای حالت‌مند، طولانی‌مدت و قابل کنترل است. به‌جای اینکه فقط یک زنجیره خطی از عملیات بسازی، می‌توانی سیستم را به‌صورت گرافی از Nodeها و Edgeها مدل کنی.

چرا به LangGraph نیاز داریم؟

در برنامه‌های ساده، یک درخواست به مدل و یک پاسخ نهایی کافی است. اما در سیستم واقعی ممکن است Agent لازم باشد چند بار ابزار اجرا کند، نتیجه را بررسی کند، به مرحله قبلی برگردد، منتظر تأیید انسان بماند، بعد از خطا ادامه دهد یا بر اساس وضعیت فعلی مسیر متفاوتی انتخاب کند.

مدل گرافی LangGraph برای چنین رفتارهایی مناسب است. طبق مستندات رسمی، LangGraph روی orchestration، اجرای پایدار، streaming، human-in-the-loop و persistence تمرکز دارد. برای استفاده از آن الزاماً مجبور نیستی LangChain را هم به کار ببری.

نمونه کد مفهومی: تعریف گراف

# Illustrative LangGraph-style example
from typing import TypedDict
from langgraph.graph import StateGraph, START, END

class ResearchState(TypedDict):
    question: str
    evidence: list
    answer: str

def retrieve(state: ResearchState):
    # Retrieve documents from a knowledge source
    docs = search_knowledge_base(state["question"])
    return {"evidence": docs}

def compose(state: ResearchState):
    answer = generate_answer(
        question=state["question"],
        evidence=state["evidence"]
    )
    return {"answer": answer}

builder = StateGraph(ResearchState)
builder.add_node("retrieve", retrieve)
builder.add_node("compose", compose)

builder.add_edge(START, "retrieve")
builder.add_edge("retrieve", "compose")
builder.add_edge("compose", END)

graph = builder.compile()
result = graph.invoke({
    "question": "What is our refund policy?",
    "evidence": [],
    "answer": ""
})

Persistence و Checkpointing

یکی از قابلیت‌های مهم LangGraph ذخیره وضعیت اجرا در checkpointها است. این قابلیت برای ادامه گفتگو، بازیابی پس از خطا، workflowهای طولانی و تعامل انسانی مفید است.

  • Thread-scoped state: وضعیت یک مکالمه یا اجرای مشخص را نگه می‌دارد.
  • Long-term store: برای داده‌هایی که باید میان چند Thread باقی بمانند مناسب است.
  • Resume: پس از توقف یا وقفه، اجرای گراف می‌تواند ادامه یابد.
  • Time travel: در محیط‌های پشتیبانی‌شده می‌توان وضعیت‌های قبلی را بررسی و مسیر را بازسازی کرد.

چه زمانی LangGraph انتخاب مناسبی است؟

  • وقتی Workflow دارای branching و loopهای پیچیده است.
  • وقتی باید اجرای Agent بعد از وقفه یا خطا ادامه پیدا کند.
  • وقتی تأیید انسانی بخشی از فرآیند است.
  • وقتی می‌خواهی مراحل deterministic و تصمیم‌های LLM را ترکیب کنی.
  • وقتی لازم است state و مسیر اجرای Agent دقیقاً قابل بررسی باشند.
LangGraph صرفاً یک ابزار برای ساخت Agentهای چندگانه نیست. ارزش اصلی آن کنترل دقیق جریان اجرا و مدیریت state است. اگر فقط یک Agent ساده با یک Tool می‌خواهی، ممکن است abstraction سطح بالاتر ساده‌تر باشد.

۳. LlamaIndex

Data Framework / RAG / Agents

LlamaIndex یک ابزار مهم برای ساخت برنامه‌های LLMمحور بر پایه داده‌های اختصاصی است. تمرکز شاخص آن روی اتصال به منابع داده، پردازش اسناد، indexing، retrieval، query engineها، RAG و ساخت Agentهایی است که با داده کار می‌کنند.

مسئله اصلی LlamaIndex چیست؟

مدل زبانی لزوماً به اطلاعات داخلی سازمان، فایل‌های PDF، اسناد فنی، قراردادها، پایگاه داده یا دانش به‌روز شرکت دسترسی ندارد. LlamaIndex کمک می‌کند این منابع را وارد برنامه کنی، ساختار بدهی، index بسازی و هنگام پاسخ‌گویی اطلاعات مرتبط را بازیابی کنی.

اجزای کلیدی LlamaIndex

Documents و Nodes

Document نماینده داده ورودی است و Node معمولاً قطعه یا واحد پردازش‌شده‌ای از داده محسوب می‌شود.

Data Connectors

اتصال به فایل‌ها، پایگاه‌های داده و منابع بیرونی را ساده می‌کنند.

Ingestion Pipeline

فرآیند دریافت، تبدیل، قطعه‌بندی، افزودن metadata و آماده‌سازی داده را مدیریت می‌کند.

Index

ساختار سازمان‌دهی اطلاعات برای بازیابی کارآمد است؛ مانند Vector Index یا ساختارهای مبتنی بر گراف.

Retriever

بخش بازیابی اطلاعات مرتبط با query کاربر است.

Query Engine

یک مسیر end-to-end برای دریافت سؤال، بازیابی context و تولید پاسخ فراهم می‌کند.

Agents و Tools

Agent می‌تواند از query engine یا سایر قابلیت‌ها به‌عنوان ابزار استفاده کند.

Workflows

برای طراحی جریان‌های event-driven، چندمرحله‌ای، شاخه‌دار و پیچیده کاربرد دارد.

نمونه کد ساده RAG

# Illustrative LlamaIndex-style example
from llama_index.core import VectorStoreIndex, SimpleDirectoryReader

documents = SimpleDirectoryReader("./company_docs").load_data()

index = VectorStoreIndex.from_documents(documents)

query_engine = index.as_query_engine()

response = query_engine.query(
    "What is the company's annual leave policy?"
)

print(response)

این مثال ساده است و برای Production کافی نیست. در یک سیستم واقعی باید سیاست chunking، metadata، دسترسی کاربران، به‌روزرسانی index، حذف اسناد، ارزیابی retrieval، citation و کنترل نسخه داده را طراحی کنی.

LlamaIndex و Agentها

LlamaIndex فقط برای RAG ساده نیست. Agent می‌تواند چند ابزار داشته باشد و بر اساس سؤال، تصمیم بگیرد از کدام ابزار استفاده کند. برای مثال:

  • ابزار اول: جست‌وجو در اسناد سیاست‌های شرکت.
  • ابزار دوم: query روی پایگاه داده فروش.
  • ابزار سوم: محاسبه KPI.
  • ابزار چهارم: تولید گزارش از نتایج.

همچنین می‌توان Agentهای تخصصی را در یک AgentWorkflow کنار هم قرار داد یا با Workflows سطح پایین‌تر، جریان اجرایی سفارشی ساخت.

چه زمانی LlamaIndex را انتخاب کنیم؟

  • وقتی داده اختصاصی و اسناد سازمانی هسته اصلی محصول هستند.
  • وقتی به ingestion و retrieval پیشرفته نیاز داری.
  • وقتی کیفیت بازیابی و grounding پاسخ اهمیت بالایی دارد.
  • وقتی می‌خواهی Agentها به Query Engineها و داده‌های ساختاریافته دسترسی داشته باشند.
  • وقتی می‌خواهی pipeline داده و Agent را در یک اکوسیستم منسجم طراحی کنی.
قاعده تجربی: اگر مسئله تو «چطور به مدل اجازه بدهم دانش داخلی سازمان را به‌درستی پیدا کند؟» باشد، LlamaIndex یکی از گزینه‌های جدی است. اگر مسئله اصلی «چطور اجرای یک Agent پیچیده را کنترل کنم؟» باشد، LangGraph را نیز بررسی کن.

۴. Semantic Kernel

Enterprise AI SDK

Semantic Kernel یک SDK از مایکروسافت برای ادغام قابلیت‌های مدل‌های زبانی با برنامه‌های نرم‌افزاری متعارف است. این پروژه به‌ویژه برای تیم‌هایی که در اکوسیستم .NET، C#، Python یا Java کار می‌کنند و به ساختار سازمانی، Pluginها و ادغام با سیستم‌های موجود اهمیت می‌دهند، قابل توجه است.

فلسفه Semantic Kernel

فرض کن یک سامانه سازمانی قدیمی داری که شامل سرویس حسابداری، CRM، پایگاه داده و سرویس احراز هویت است. نمی‌خواهی این منطق را کنار بگذاری و همه‌چیز را به یک Agent آزاد بسپاری. می‌خواهی قابلیت زبان طبیعی را به سیستم موجود اضافه کنی، بدون اینکه کنترل برنامه و منطق تجاری از دست توسعه‌دهنده خارج شود.

Semantic Kernel به تو کمک می‌کند سرویس‌ها و توابع برنامه را به شکلی سازمان‌یافته در اختیار قابلیت‌های AI قرار دهی.

Plugin یعنی چه؟

# Conceptual example
class OrderPlugin:
    def __init__(self, order_service):
        self.order_service = order_service

    def get_customer_orders(self, customer_id: str):
        """

        return self.order_service.find_orders(customer_id)

۵. AutoGen

Multi-Agent Conversation

AutoGen یک پروژه مایکروسافت برای ساخت برنامه‌های مبتنی بر Agent و هماهنگی چند Agent از طریق تعاملات پیام‌محور بود. از نظر آموزشی و تاریخی، نقش مهمی در رواج معماری‌های multi-agent مبتنی بر مکالمه داشته است.

ایده اصلی AutoGen

به‌جای اینکه تمام کار را به یک Agent بسپاری، چند Agent با نقش‌های متفاوت تعریف می‌کنی. آن‌ها می‌توانند پیام ردوبدل کنند، خروجی یکدیگر را بررسی کنند، ابزار اجرا کنند و برای رسیدن به هدف مشترک همکاری داشته باشند.

Core

Teams

Extensions

الگوهای همکاری

# Historical / illustrative AutoGen-style pattern
import asyncio
from autogen_agentchat.agents import AssistantAgent
from autogen_agentchat.teams import RoundRobinGroupChat
from autogen_ext.models.openai import OpenAIChatCompletionClient

async def main():
    model_client = OpenAIChatCompletionClient(
        model="your-supported-model"
    )

    researcher = AssistantAgent(
        name="researcher",
        model_client=model_client,
        system_message="Collect relevant evidence."
    )

    reviewer = AssistantAgent(
        name="reviewer",
        model_client=model_client,
        system_message="Critique the evidence and identify gaps."
    )

    team = RoundRobinGroupChat(
        participants=[researcher, reviewer],
        max_turns=4
    )

    result = await team.run(
        task="Analyze the benefits and risks of RAG."
    )
    print(result)

asyncio.run(main())

وضعیت فعلی AutoGen: نکته حیاتی برای انتخاب

وضعیت پروژه را جدی بگیر: مستندات فعلی AutoGen اعلام می‌کنند که پروژه آرشیو شده و دیگر به‌صورت فعال توسط Microsoft نگه‌داری نمی‌شود؛ یعنی انتظار رفع اشکال امنیتی، قابلیت جدید یا پشتیبانی رسمی مستمر نباید داشته باشی. برای پروژه‌های جدید، Microsoft پیشنهاد می‌کند از Microsoft Agent Framework شروع شود. کاربران فعلی نیز می‌توانند مسیر مهاجرت را بررسی کنند.

چه زمانی AutoGen را بررسی کنیم؟

  • برای آزمایش و مقایسه الگوهای همکاری، با درنظرگرفتن وضعیت پشتیبانی پروژه.

۶. CrewAI

Role-Based Multi-Agent Framework

CrewAI فریم‌ورکی برای ساخت سیستم‌های چندعاملی است که در آن Agentها با نقش‌ها، هدف‌ها و مسئولیت‌های مشخص تعریف می‌شوند. ایده اصلی آن این است که کارهای پیچیده را به یک تیم از Agentهای تخصصی بسپاری.

دو مفهوم مهم: Crew و Flow

Crew = تیم متخصصان

یک گروه از Agentها که برای انجام یک کار پیچیده با هم همکاری می‌کنند. هر Agent می‌تواند نقش، هدف، ابزار و تنظیمات خودش را داشته باشد.

Flow = کنترل‌کننده فرآیند

جریان اصلی برنامه را تعریف می‌کند؛ State، ترتیب مراحل، branching، eventها و تصمیم‌گیری درباره مرحله بعد را مدیریت می‌کند.

در معماری مناسب Production، Flow معمولاً اسکلت اصلی برنامه است و Crew در مرحله‌ای استفاده می‌شود که واقعاً به همکاری و استقلال Agentها نیاز داریم.

مثال: تیم تولید گزارش بازار

# Illustrative CrewAI-style example
from crewai import Agent, Task, Crew, Process

researcher = Agent(
    role="Market Researcher",
    goal="Collect relevant market evidence",
    backstory="You are a careful research analyst.",
    tools=[search_tool]
)

analyst = Agent(
    role="Market Analyst",
    goal="Identify trends and compare competitors",
    backstory="You analyze evidence and quantify uncertainty."
)

writer = Agent(
    role="Report Writer",
    goal="Produce a clear executive report",
    backstory="You write concise evidence-based reports."
)

research_task = Task(
    description="Research the target market and cite sources.",
    expected_output="A structured evidence summary.",
    agent=researcher
)

analysis_task = Task(
    description="Analyze the evidence and identify trends.",
    expected_output="A structured analysis with caveats.",
    agent=analyst,
    context=[research_task]
)

writing_task = Task(
    description="Write an executive report.",
    expected_output="A concise report with recommendations.",
    agent=writer,
    context=[analysis_task]
)

crew = Crew(
    agents=[researcher, analyst, writer],
    tasks=[research_task, analysis_task, writing_task],
    process=Process.sequential
)

result = crew.kickoff()
print(result)

چه زمانی CrewAI مناسب است؟

  • وقتی مسئله به چند نقش تخصصی قابل تفکیک است.
  • وقتی می‌خواهی یک تیم Agent را با تعریف Role، Goal و Task بسازی.
  • وقتی برای تحقیق، تحلیل، بازبینی و تولید محتوا به همکاری Agentها نیاز داری.
  • وقتی می‌خواهی در کنار همکاری خودمختار، با Flow کنترل ساختاریافته داشته باشی.

محدودیت‌ها و ملاحظات

  • تعریف تعداد زیادی Agent بدون تقسیم کار واقعی، هزینه و پیچیدگی را بالا می‌برد.
  • Role و Backstory خوب به‌تنهایی تضمین‌کننده خروجی دقیق نیستند.
  • باید ورودی و خروجی Taskها، محدودیت ابزارها و معیار پذیرش مشخص باشند.
  • برای عملیات حساس، Flow و کنترل‌های deterministic را جایگزین اعتماد کامل به تصمیم Agent کن.
برای CrewAI یک الگوی ذهنی مفید این است: Flow برای کنترل؛ Crew برای همکاری.

۷. OpenAI Agents SDK

Agent SDK

OpenAI Agents SDK یک SDK سبک برای ساخت Agentهایی است که دستورالعمل، مدل، ابزار، Guardrail و امکان واگذاری کار به Agentهای دیگر دارند. این SDK روی ساخت Agentهای قابل ترکیب و مدیریت اجرای آن‌ها تمرکز می‌کند.

چه چیزی در آن مهم است؟

Agent

یک واحد اجرایی با نام، دستورالعمل، مدل و قابلیت‌های مشخص.

Tools

توابع، ابزارهای میزبانی‌شده یا اتصال به قابلیت‌های بیرونی.

Handoffs

انتقال کنترل از یک Agent به Agent متخصص دیگر.

Agents as Tools

یک Agent می‌تواند Agent دیگری را مانند یک ابزار فراخوانی کند و کنترل را نزد خود نگه دارد.

Guardrails

کنترل ورودی و خروجی و متوقف‌کردن اجرای نامعتبر با سازوکارهای مشخص.

Sessions

مدیریت تاریخچه و زمینه گفتگو میان اجرای Agentها.

Tracing

ثبت اجرای Agent، فراخوانی ابزارها، handoffها و Guardrailها برای debugging.

Human in the Loop

امکان واردکردن انسان در فرآیند برای بررسی یا تأیید اقدامات حساس.

دو الگوی مهم: Handoff و Manager

الگو نحوه کار چه زمانی مفید است؟
Handoff Agent فعلی کنترل را به Agent متخصص دیگری منتقل می‌کند. وقتی مالکیت ادامه مکالمه باید به متخصص جدید منتقل شود.
Manager / Agents as Tools Agent اصلی Agentهای تخصصی را فراخوانی می‌کند و خودش کنترل پاسخ نهایی را نگه می‌دارد. وقتی یک مدیر باید خروجی چند متخصص را جمع‌بندی و ترکیب کند.

Tracing چه ارزشی دارد؟

در سیستم Agentic فقط پاسخ نهایی کافی نیست. باید بدانی Agent چه تصمیمی گرفت، چه ابزاری را فراخواند، چه handoffی انجام شد، کدام Guardrail فعال شد و هر مرحله چقدر زمان و هزینه مصرف کرد. SDK دارای tracing داخلی است که برای بررسی این رخدادها کاربرد دارد.

چه زمانی OpenAI Agents SDK را انتخاب کنیم؟

  • وقتی به یک SDK سبک برای تعریف Agent و ابزارها نیاز داری.
  • وقتی می‌خواهی الگوهای handoff و manager را پیاده‌سازی کنی.
  • وقتی Guardrail و tracing یکپارچه برایت مهم است.
  • وقتی برنامه می‌خواهد کنترل اصلی روی storage، ابزارها و منطق تجاری را در اختیار خودش نگه دارد.
  • وقتی می‌خواهی از abstractionهای Agent آماده استفاده کنی، بدون ساختن یک سیستم orchestration کامل از صفر.

# Architecture-oriented pseudocode.
# This is not a drop-in implementation.

async def handle_request(request):
    trace = start_trace(request.request_id)

    identity = authenticate(request.user_id)
    permissions = load_permissions(identity)

    intent = classify_intent(request.question)

    if intent.requires_documents:
        evidence = await retrieve_documents(
            query=request.question,
            permissions=permissions,
            domains=request.allowed_domains
        )
    else:
        evidence = []

    if intent.requires_business_data:
        business_data = await call_authorized_api(
            intent=intent,
            identity=identity
        )
    else:
        business_data = None

    verification = verify_evidence(
        question=request.question,
        evidence=evidence,
        business_data=business_data
    )

    if verification.insufficient:
        return ask_for_clarification_or_escalate()

    draft = compose_answer(
        question=request.question,
        evidence=evidence,
        business_data=business_data
    )

    result = validate_citations_and_policy(draft)

    record_trace(trace, result)

    return result

جمع‌بندی نهایی

فریم‌ورک خوب، فریم‌ورکی نیست که بیشترین قابلیت را داشته باشد؛ فریم‌ورکی است که با کمترین پیچیدگی لازم، مسئله واقعی تو را حل کند.

  • LangChain: برای ساخت LLM Application و Agent با ابزارها و integrationهای متنوع.
  • LangGraph: برای کنترل دقیق Workflow، State، Checkpoint و اجرای پیچیده Agent.
  • LlamaIndex: برای داده، اسناد، Retrieval و RAG.
  • Semantic Kernel: برای ادغام AI با برنامه‌ها و قابلیت‌های نرم‌افزاری سازمانی؛ با توجه به مسیر Microsoft Agent Framework.
  • AutoGen: برای فهم الگوهای multi-agent و کار با پروژه‌های موجود؛ با توجه به آرشیوشدن پروژه.
  • CrewAI: برای تعریف تیم‌های Agent نقش‌محور و ترکیب آن‌ها با Flowهای کنترل‌شده.
  • OpenAI Agents SDK: برای ساخت Agent، Tool، Handoff و Guardrail با یک SDK سبک.
مهم‌ترین توصیه مهندسی: با ساده‌ترین معماری‌ای شروع کن که مسئله را حل می‌کند. ابتدا یک Workflow deterministic یا یک Agent ساده بساز. سپس فقط وقتی اندازه‌گیری‌ها نشان دادند که چند Agent یا orchestration پیچیده‌تر ارزش واقعی ایجاد می‌کند، معماری را گسترش بده.
