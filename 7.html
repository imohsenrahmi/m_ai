مقدمه: مهندسی پیشرفته سیستم‌های Agentic AI چیست؟

در سطح مقدماتی، معمولاً یک Agent را سیستمی می‌دانیم که هدفی دریافت می‌کند، درباره آن تصمیم می‌گیرد، از ابزارها استفاده می‌کند و نتیجه را ارائه می‌دهد. اما در پروژه‌های واقعی، مسئله به همین سادگی نیست.

وقتی وظیفه‌ای پیچیده می‌شود، ممکن است یک Agent به‌تنهایی نتواند تمام مراحل را با کیفیت، سرعت، دقت و قابلیت اطمینان مناسب انجام دهد. برای مثال، ساخت یک گزارش تحلیلی سازمانی می‌تواند به جمع‌آوری داده، تحلیل آماری، بررسی منابع، کنترل کیفیت، نگارش و تأیید نهایی نیاز داشته باشد.

در چنین شرایطی، معماری پیشرفته Agentic AI مطرح می‌شود: مجموعه‌ای از Agentها، ابزارها، Workflowها، حافظه‌ها و سازوکارهای کنترلی که با یکدیگر برای رسیدن به یک هدف همکاری می‌کنند.

نکته کلیدی: پیشرفته‌تر بودن یک سیستم به معنی داشتن تعداد Agent بیشتر نیست. یک سیستم خوب، کمترین پیچیدگی لازم را برای دستیابی به کیفیت، کنترل‌پذیری و قابلیت نگهداری مناسب انتخاب می‌کند.

چه مسائلی در این سطح حل می‌شوند؟

  • تقسیم یک مسئله بزرگ به چند وظیفه تخصصی و قابل مدیریت.
  • اجرای هم‌زمان چند کار مستقل برای کاهش زمان پاسخ.
  • هماهنگی Agentهای مختلف با نقش‌ها و توانایی‌های متفاوت.
  • کنترل تصمیم‌گیری‌های خودکار و محدود کردن اقدامات پرریسک.
  • تشخیص خطا، تلاش مجدد و اصلاح برنامه در صورت تغییر شرایط.
  • اندازه‌گیری کیفیت، هزینه، سرعت و قابلیت اطمینان سیستم.

مثال: ساخت یک سیستم هوشمند تحلیل بازار

فرض کنید کاربر درخواست می‌کند:

«بازار نرم‌افزارهای مدیریت پروژه را بررسی کن، رقبا را مقایسه کن، فرصت‌های بازار را پیدا کن و یک گزارش مدیریتی تهیه کن.»

این کار را می‌توان به چند مسئولیت تقسیم کرد:

Research Agent

جست‌وجو و جمع‌آوری اطلاعات بازار و رقبا.

Data Analyst Agent

تحلیل داده‌ها، مقایسه و استخراج الگوها.

Strategy Agent

شناسایی فرصت‌ها، تهدیدها و پیشنهادهای استراتژیک.

Writer Agent

تبدیل یافته‌ها به گزارش قابل ارائه.

Supervisor / Orchestrator

تخصیص وظایف، کنترل پیشرفت، بررسی خروجی‌ها و جمع‌بندی نهایی.

این مثال نقطه شروعی برای فهم معماری‌های چندعاملی است. در ادامه، هر یک از این الگوها را به‌صورت مستقل بررسی می‌کنیم.

۱. Multi-Agent Systems

۱.۱ سیستم چندعاملی چیست؟

Multi-Agent System یا MAS معماری‌ای است که در آن چند Agent مستقل یا نیمه‌مستقل برای دستیابی به یک هدف مشترک یا مجموعه‌ای از اهداف مرتبط با یکدیگر تعامل دارند. هر Agent می‌تواند نقش، ابزار، دستورالعمل، حافظه و محدوده مسئولیت مشخصی داشته باشد.

تفاوت اصلی MAS با یک چت‌بات معمولی این است که مسئولیت‌ها بین چند واحد تصمیم‌گیرنده تقسیم می‌شوند. این واحدها می‌توانند اطلاعات را مبادله کنند، کارها را به یکدیگر بسپارند، خروجی همدیگر را بررسی کنند یا برای رسیدن به یک نتیجه مشترک مذاکره کنند.

۱.۳ استقلال Agentها به چه معناست؟

استقلال به این معنا نیست که هر Agent بدون هیچ محدودیتی عمل می‌کند. استقلال معمولاً در محدوده یک وظیفه تعریف می‌شود. برای مثال، Agent تحلیلگر می‌تواند روش تحلیل را انتخاب کند، اما اجازه ندارد بدون مجوز به دیتابیس تولیدی اطلاعات بنویسد.

استقلال می‌تواند در چند بُعد متفاوت تعریف شود:

  • استقلال تصمیم‌گیری: انتخاب روش اجرای وظیفه.
  • استقلال اجرایی: استفاده از ابزارهای مجاز بدون تأیید هر مرحله.
  • استقلال زمانی: ادامه کار تا رسیدن به شرط پایان یا محدودیت.
  • استقلال اطلاعاتی: داشتن context و حافظه اختصاصی.

Multi-Agent به‌طور خودکار دقت را افزایش نمی‌دهد. چند Agent ممکن است اشتباه مشابهی را تکرار کنند، یکدیگر را تأیید اشتباه کنند یا با تبادل پیام زیاد هزینه و زمان را بالا ببرند.

۲. Supervisor and Worker Architecture

۲.۱ معماری Supervisor چیست؟

در این الگو یک Agent مرکزی به نام Supervisor یا Manager وظیفه کنترل و هماهنگی سایر Agentها را بر عهده دارد. Agentهای دیگر که Worker نامیده می‌شوند، مسئول اجرای وظایف مشخص هستند.

Supervisor معمولاً خودش همه کارها را انجام نمی‌دهد؛ بلکه درخواست را تحلیل می‌کند، آن را به وظایف کوچک‌تر می‌شکند، Worker مناسب را انتخاب می‌کند، نتیجه را دریافت می‌کند و درباره مرحله بعد تصمیم می‌گیرد.

User Request
↓
Supervisor Agent
↓
Research Worker
Analysis Worker
Writing Worker
↓
Supervisor Review
↓
Final Response

۲.۲ مسئولیت‌های Supervisor

  1. Task Decomposition: تبدیل هدف بزرگ به وظایف کوچک.
  2. Worker Selection: انتخاب Agent مناسب برای هر وظیفه.
  3. Task Assignment: تعیین ورودی، خروجی و محدودیت کار.
  4. Progress Monitoring: بررسی وضعیت اجرای وظایف.
  5. Result Validation: ارزیابی خروجی Workerها.
  6. Conflict Resolution: مدیریت خروجی‌های متناقض.
  7. Final Synthesis: ترکیب نتایج و تولید پاسخ نهایی.

۲.۳ قرارداد کاری بین Supervisor و Worker

یکی از اشتباهات رایج این است که Supervisor فقط یک توضیح متنی مبهم به Worker بدهد. در معماری مهندسی‌شده، بهتر است هر وظیفه قرارداد مشخصی داشته باشد. 

{
  "task_id": "research-001",
  "assigned_agent": "research_agent",
  "objective": "Find competitor pricing information",
  "inputs": {
    "market": "project management software",
    "region": "Europe"
  },
  "constraints": {
    "max_sources": 10,
    "require_source_urls": true,
    "do_not_guess_missing_prices": true
  },
  "expected_output": {
    "type": "structured_json",
    "fields": [
      "competitor",
      "pricing_model",
      "price",
      "source_url"
    ]
  }
}

این قرارداد باعث می‌شود Worker بداند دقیقاً چه چیزی باید تحویل دهد و Supervisor نیز بتواند خروجی را به‌صورت ساختاریافته بررسی کند.

۲.۴ مزیت و محدودیت این معماری

مزیت محدودیت
کنترل متمرکز و قابل فهم Supervisor می‌تواند گلوگاه شود
تخصیص واضح مسئولیت‌ها وابستگی زیاد به کیفیت تصمیم Supervisor
مدیریت ساده‌تر جریان کار نیاز به مدیریت خطای Workerها

۲.۵ نمونه منطق Supervisor

async def supervisor(user_request):
    plan = await planner.create_plan(user_request)

    results = []

    for task in plan.tasks:
        worker = select_worker(task.type)

        result = await worker.execute(
            task=task,
            context=results
        )

        validation = await validator.check(
            task=task,
            result=result
        )

        if not validation.passed:
            result = await worker.revise(
                task=task,
                feedback=validation.feedback
            )

        results.append(result)

    return await synthesizer.combine(
        request=user_request,
        results=results
    )
در سیستم واقعی، اجرای ترتیبی بالا لزوماً بهترین انتخاب نیست. اگر دو وظیفه وابستگی نداشته باشند، می‌توان آن‌ها را موازی اجرا کرد. همچنین باید timeout، retry، cancellation و محدودیت تعداد فراخوانی‌ها به این منطق اضافه شود.

۳. Hierarchical Agent Architecture

۳.۱ معماری سلسله‌مراتبی چیست؟

در معماری Hierarchical، Agentها در چند سطح سازمان‌دهی می‌شوند. به‌جای اینکه یک Supervisor تمام Workerها را مستقیماً مدیریت کند، ممکن است چند مدیر میانی وجود داشته باشد که هر کدام مسئول یک حوزه باشند.

این معماری از نظر مفهومی شبیه ساختار سازمانی است: یک Agent سطح بالا هدف کلی را مدیریت می‌کند، مدیران حوزه‌ای وظایف تخصصی را هماهنگ می‌کنند و Agentهای اجرایی کارهای جزئی را انجام می‌دهند.

↓

۳.۲ چرا به چند سطح نیاز داریم؟

فرض کنید یک Agent مرکزی باید ۳۰ وظیفه را مدیریت کند. با افزایش تعداد Workerها، حجم context، تعداد پیام‌ها، تصمیم‌های مسیریابی و پیچیدگی کنترل افزایش می‌یابد.

می‌توان مسئولیت‌ها را به چند مدیر تخصصی تقسیم کرد. مدیر تحقیق فقط Workerهای تحقیق را می‌شناسد و مدیر تحلیل فقط مسئول هماهنگی وظایف تحلیلی است. Agent سطح بالا تنها با مدیران حوزه‌ای تعامل دارد.

۳.۳ سه سطح متداول

سطح نقش نوع تصمیم
Strategic تعیین هدف و اولویت‌ها چه چیزی باید انجام شود؟
Tactical تبدیل هدف به برنامه‌های حوزه‌ای چگونه حوزه خود را مدیریت کنیم؟
Operational اجرای وظایف مشخص این عملیات دقیقاً چگونه انجام شود؟

۳.۴ مشکل Propagation of Errors

در معماری سلسله‌مراتبی، اشتباه یک سطح ممکن است به سطوح پایین‌تر منتقل شود. اگر مدیر سطح بالا مسئله را اشتباه تجزیه کند، مدیران میانی و Workerها ممکن است با کیفیت بالا وظایف اشتباهی را اجرا کنند.

برای کاهش این ریسک، باید خروجی هر سطح شامل هدف، فرضیات، محدودیت‌ها و معیار پذیرش باشد. همچنین نقاط کنترل و تأیید بین سطوح تعریف شوند.

۳.۵ چه زمانی این معماری مناسب است؟

  • پروژه‌های بزرگ با چند حوزه تخصصی مستقل.
  • فرآیندهای سازمانی با مسئولیت‌های تفکیک‌شده.
  • سیستم‌هایی که تعداد زیادی Worker دارند.
  • وظایفی که هر بخش به برنامه‌ریزی داخلی نیاز دارد.
سلسله‌مراتب عمیق، هزینه هماهنگی را افزایش می‌دهد. برای بسیاری از پروژه‌ها دو سطح کافی است. تعداد سطوح باید بر اساس نیاز واقعی تعیین شود، نه صرفاً برای پیچیده‌تر نشان دادن معماری.

۴. Agent Communication

۴.۱ ارتباط بین Agentها

Agent Communication به روش‌هایی گفته می‌شود که Agentها با استفاده از آن‌ها اطلاعات، درخواست‌ها، نتایج، رویدادها و تصمیم‌ها را مبادله می‌کنند. کیفیت ارتباط نقش مستقیمی در کیفیت کل سیستم چندعاملی دارد.

اگر Agentها پیام‌های مبهم، طولانی یا ناقص دریافت کنند، احتمال برداشت اشتباه افزایش می‌یابد. به همین دلیل، ارتباط Agentها باید مانند ارتباط بین سرویس‌های نرم‌افزاری، قرارداد و ساختار مشخص داشته باشد.

۴.۲ الگوهای ارتباطی

الگو توضیح کاربرد
Direct Messaging ارسال پیام مستقیم به Agent دیگر درخواست تخصصی
Request / Response ارسال درخواست و انتظار برای پاسخ فراخوانی Worker
Publish / Subscribe انتشار رویداد و دریافت توسط مشترک‌ها سیستم رویدادمحور
Shared State خواندن و نوشتن در وضعیت مشترک هماهنگی وظایف
Message Queue ارسال پیام از طریق صف کارهای طولانی و غیرهم‌زمان

۴.۳ ارتباط مستقیم

در روش Direct Messaging، یک Agent پیام را مستقیماً برای Agent دیگری ارسال می‌کند. این روش برای سیستم‌های کوچک و ارتباطات مشخص مناسب است. 

message = {
    "message_id": "msg-102",
    "sender": "research_agent",
    "receiver": "analyst_agent",
    "message_type": "research_result",
    "correlation_id": "project-42",
    "payload": {
        "market_size": 1200000,
        "currency": "EUR",
        "source_count": 8
    }
}

await communication.send(message)

۴.۴ Publish / Subscribe

در این الگو، Agent منتشرکننده یک رویداد را در یک کانال منتشر می‌کند. Agentهای مشترک بدون نیاز به ارتباط مستقیم با منتشرکننده، رویداد را دریافت می‌کنند. 

# Producer
await event_bus.publish(
    topic="research.completed",
    event={
        "project_id": "project-42",
        "result_id": "result-900"
    }
)

# Consumer
async def on_research_completed(event):
    await analyst_agent.process(
        research_result_id=event["result_id"]
    )

۴.۵ قرارداد پیام (Message Contract)

یک پیام استاندارد بهتر است این فیلدها را داشته باشد:

  • message_id: شناسه یکتا برای ردیابی پیام.
  • sender: شناسه Agent فرستنده.
  • receiver: مقصد پیام یا گروه دریافت‌کنندگان.
  • message_type: نوع پیام.
  • correlation_id: شناسه درخواست یا اجرای اصلی.
  • timestamp: زمان ایجاد پیام.
  • payload: محتوای ساختاریافته.
  • status: وضعیت پردازش.
  • deadline: مهلت معتبر برای پاسخ.

۴.۶ پیام متنی یا داده ساختاریافته؟

پیام متنی انعطاف‌پذیر است، اما پردازش و اعتبارسنجی آن دشوارتر می‌شود. پیام ساختاریافته مانند JSON برای ارتباطات ماشینی قابل اطمینان‌تر است. در سیستم‌های جدی، بهتر است خروجی Agentها با Schema مشخص اعتبارسنجی شود.

پیام بین Agentها باید تا حد امکان کوتاه، هدفمند و قابل اعتبارسنجی باشد. انتقال کل تاریخچه مکالمه به تمام Agentها معمولاً باعث افزایش هزینه، نویز و احتمال افشای اطلاعات غیرضروری می‌شود.

۵. Agent Collaboration

۵.۱ همکاری Agentها چیست؟

همکاری زمانی اتفاق می‌افتد که چند Agent برای رسیدن به یک هدف مشترک، منابع، اطلاعات یا توانایی‌های خود را ترکیب کنند. این همکاری می‌تواند شامل تقسیم وظیفه، تبادل یافته‌ها، بررسی متقابل یا ترکیب نتایج باشد.

تفاوت Communication و Collaboration این است که Communication درباره انتقال پیام است، اما Collaboration درباره هماهنگی فعالیت‌ها برای رسیدن به نتیجه مشترک است.

۵.۲ الگوهای همکاری

الف) تقسیم کار (Task Decomposition)

مسئله به بخش‌های مستقل تقسیم می‌شود و هر Agent بخشی از کار را انجام می‌دهد. در پایان، خروجی‌ها ترکیب می‌شوند.

ب) همکاری مکمل (Complementary Collaboration)

Agentها مهارت‌های متفاوت دارند و خروجی آن‌ها مکمل یکدیگر است. مثلاً Agent تحلیل داده یافته‌های عددی را تولید می‌کند و Agent استراتژی آن‌ها را به پیشنهاد تجاری تبدیل می‌کند.

ج) بررسی متقابل (Peer Review)

یک Agent خروجی تولید می‌کند و Agent دیگر آن را از نظر صحت، کامل بودن یا رعایت محدودیت‌ها بررسی می‌کند.

د) اجماع (Consensus)

چند Agent درباره یک تصمیم یا نتیجه نظر می‌دهند و سیستم با استفاده از یک قاعده مشخص، نتیجه نهایی را انتخاب می‌کند.

۵.۳ مثال همکاری تحلیلی

↓

↓

↓

↓

۵.۴ اجماع چگونه ایجاد می‌شود؟

اجماع لزوماً به معنی رأی‌گیری ساده نیست. روش انتخاب باید متناسب با نوع تصمیم باشد. برای نمونه:

  • اکثریت آرا برای انتخاب میان گزینه‌های مشخص.
  • امتیازدهی وزنی بر اساس تخصص و کیفیت شواهد.
  • داوری Agent مستقل بر اساس معیارهای از پیش تعیین‌شده.
  • الزام به ارائه شواهد برای هر ادعا و انتخاب گزینه مستندتر.
  • ارجاع به انسان در صورت اختلاف جدی یا پیامد پرریسک.
توافق چند Agent الزاماً به معنی درست بودن پاسخ نیست. اگر همه Agentها از یک مدل، داده یا فرض اشتباه استفاده کنند، ممکن است یک خطای مشترک را با اطمینان بالا تأیید کنند.

۶. Agent Delegation

۶.۱ مفهوم Delegation

Delegation یا واگذاری وظیفه یعنی یک Agent بخشی از مسئولیت خود را به Agent یا سرویس دیگری منتقل کند. واگذاری صرفاً ارسال یک پیام نیست؛ بلکه باید مشخص شود چه مسئولیتی منتقل شده، چه اختیاراتی داده شده و چه خروجی‌ای انتظار می‌رود.

۶.۲ چه چیزهایی باید واگذار شوند؟

  • هدف دقیق وظیفه.
  • ورودی‌ها و اطلاعات زمینه‌ای لازم.
  • محدودیت‌های اجرایی و امنیتی.
  • ابزارهایی که Agent مجاز به استفاده از آن‌هاست.
  • فرمت و Schema خروجی.
  • مهلت انجام و حداکثر بودجه.
  • معیار پذیرش و نحوه گزارش خطا.

۶.۳ الگوی واگذاری

async def delegate_task(parent_agent, worker, task):
    delegated_task = {
        "task_id": task.id,
        "objective": task.objective,
        "input": task.input,
        "constraints": task.constraints,
        "deadline": task.deadline,
        "output_schema": task.output_schema
    }

    result = await worker.run(delegated_task)

    if not validate_schema(
        result,
        task.output_schema
    ):
        raise InvalidWorkerOutput()

    return result

۶.۵ Delegation امن

Agent دریافت‌کننده نباید صرفاً به دلیل دریافت یک وظیفه، به تمام ابزارها و داده‌های Agent واگذارکننده دسترسی پیدا کند. اصل Least Privilege باید رعایت شود؛ یعنی هر Worker فقط به منابع موردنیاز وظیفه دسترسی داشته باشد.

۷. Agent Routing

۷.۱ Routing چیست؟

Routing فرآیند انتخاب Agent، ابزار یا مسیر اجرایی مناسب برای یک درخواست است. در سیستم‌های بزرگ، تمام درخواست‌ها نباید به یک Agent ارسال شوند. ابتدا باید نوع درخواست تشخیص داده شود و سپس مسیر مناسب انتخاب شود.

۷.۲ انواع Routing

نوع شرح مثال
Rule-based انتخاب بر اساس قواعد ثابت درخواست مالی ← Finance Agent

Capability-based انتخاب بر اساس توانایی‌ها Agent دارای دسترسی SQL
Hybrid Routing ترکیب قواعد و مدل فیلتر امنیتی سپس انتخاب معنایی

۷.۵ Routing مبتنی بر قابلیت

در این روش به‌جای اینکه فقط نام Agent را بررسی کنیم، قابلیت‌های آن را در نظر می‌گیریم. ممکن است چند Agent بتوانند یک نوع وظیفه را انجام دهند، اما تنها یکی از آن‌ها دسترسی لازم یا کیفیت مناسب را داشته باشد. 

agent_registry = {
    "data_agent": {
        "capabilities": ["sql", "statistics"],
        "max_cost": 0.10
    },
    "research_agent": {
        "capabilities": ["web_search", "source_analysis"],
        "max_cost": 0.15
    }
}

def find_agent(required_capabilities):
    candidates = []

    for name, info in agent_registry.items():
        if set(required_capabilities).issubset(
            set(info["capabilities"])
        ):
            candidates.append(name)

    return candidates

۷.۶ نکات مهم در Routing

  • ابتدا محدودیت‌های امنیتی را اعمال کنید.
  • در صورت ابهام، امکان درخواست توضیح بیشتر وجود داشته باشد.
  • برای درخواست‌های ناشناخته، مسیر fallback تعریف کنید.
  • انتخاب Agent و دلیل انتخاب آن را ثبت کنید.
  • Routing نباید بر اساس توضیحات غیرقابل اعتماد داخل اسناد، مجوزهای امنیتی را تغییر دهد.

۸. Workflow vs Agent

۸.۱ تفاوت اصلی

Workflow یک جریان اجرای از پیش تعریف‌شده است. مراحل، ترتیب اجرا، شرط‌های انشعاب و نحوه پایان آن معمولاً توسط توسعه‌دهنده مشخص می‌شوند. در مقابل، Agent می‌تواند با توجه به هدف و اطلاعات جدید درباره قدم بعدی تصمیم بگیرد.

ویژگی Workflow Agent
مسیر اجرا عموماً مشخص و از پیش تعریف‌شده ممکن است پویا باشد
تصمیم‌گیری بر اساس قواعد و شرط‌ها ممکن است با مدل انجام شود
پیش‌بینی‌پذیری معمولاً بیشتر معمولاً کمتر
کنترل‌پذیری بالا در مسیرهای مشخص نیازمند محدودیت و نظارت
کاربرد پرداخت، تأیید، پردازش فرم تحقیق، حل مسئله باز
هزینه اجرا اغلب قابل پیش‌بینی‌تر ممکن است متغیرتر باشد

در یک فرآیند تأیید سفارش، مراحل مشخص‌اند: بررسی موجودی، محاسبه مبلغ، دریافت تأیید پرداخت و ثبت سفارش. این فرآیند معمولاً نیازی به Agent کاملاً خودمختار ندارد.

۸.۳ مثال Agent

در مقابل، درخواست «تحلیل کن چرا فروش این ماه کاهش یافته و چند راهکار پیشنهاد بده» مسیر کاملاً ثابتی ندارد. Agent ممکن است ابتدا داده‌های فروش را بررسی کند، سپس به تفکیک منطقه برسد، بعد اطلاعات کمپین‌ها را درخواست کند و در نهایت چند فرضیه را مقایسه کند.

۸.۴ معماری Hybrid: ترکیب Workflow و Agent

در سیستم‌های حرفه‌ای، معمولاً ترکیب این دو رویکرد نتیجه بهتری دارد. Workflow مراحل حساس و قطعی را کنترل می‌کند و Agent در بخش‌هایی که به تفسیر، تحلیل یا تصمیم‌گیری انعطاف‌پذیر نیاز دارند استفاده می‌شود. 

async def customer_onboarding(customer):
    # Deterministic workflow step
    identity = await verify_identity(customer)

    if not identity.valid:
        return "Identity verification failed"

    # Agentic reasoning step
    risk_report = await risk_agent.analyze(
        customer_profile=identity.profile
    )

    # Deterministic policy gate
    decision = apply_risk_policy(risk_report)

    if decision.requires_human:
        return await request_human_review(risk_report)

    return await complete_onboarding(decision)
یک قاعده کاربردی: هر جا مسیر قطعی و قابل تعریف است، Workflow را ترجیح دهید. هر جا مسئله باز، مبهم یا نیازمند انتخاب پویا است، از Agent استفاده کنید. در بسیاری از محصولات، بهترین طراحی ترکیبی از هر دو است.

۹. Sequential, Parallel and Conditional Execution

۹.۱ اجرای ترتیبی (Sequential Execution)

در اجرای ترتیبی، هر مرحله بعد از تکمیل مرحله قبلی آغاز می‌شود. این الگو زمانی مناسب است که خروجی یک مرحله، ورودی مرحله بعد باشد.

→

→

→

research = await research_agent.run(task)
analysis = await analysis_agent.run(research)

final = await reviewer_agent.run(draft)

مزایا: ترتیب روشن، اشکال‌زدایی ساده‌تر و انتقال context مشخص.

محدودیت: زمان کل اجرا ممکن است به مجموع زمان تمام مراحل نزدیک شود.

۹.۲ اجرای موازی (Parallel Execution)

وقتی چند وظیفه مستقل هستند، می‌توان آن‌ها را هم‌زمان اجرا کرد. مثلاً برای بررسی یک بازار، جست‌وجوی رقبا، تحلیل نظرات مشتریان و استخراج روندهای فناوری می‌توانند به‌صورت موازی انجام شوند.

↓

import asyncio

async def run_parallel():
    tasks = [
        competitor_agent.run(),
        customer_agent.run(),
        trend_agent.run()
    ]

    results = await asyncio.gather(*tasks)

    return await synthesis_agent.combine(results)

اجرای موازی فقط زمانی مفید است که وابستگی واقعی بین وظایف وجود نداشته باشد. اگر وظیفه B برای شروع به خروجی وظیفه A نیاز داشته باشد، اجرای موازی آن‌ها ممکن است بی‌فایده یا نادرست باشد.

۹.۳ اجرای شرطی (Conditional Execution)

در اجرای شرطی، مسیر بعدی بر اساس نتیجه یک مرحله تعیین می‌شود. این تصمیم می‌تواند مبتنی بر قواعد قطعی یا خروجی اعتبارسنجی‌شده یک Agent باشد.

۱۰. Reflection and Self-Correction

۱۰.۱ Reflection چیست؟

Reflection در Agentic AI به فرآیندی گفته می‌شود که Agent خروجی یا عملکرد قبلی خود را بررسی می‌کند، ضعف‌ها را شناسایی می‌کند و در صورت نیاز آن را اصلاح می‌کند.

به‌جای اینکه Agent پس از تولید اولین پاسخ متوقف شود، می‌تواند بررسی کند: آیا پاسخ با هدف مطابقت دارد؟ آیا شواهد کافی وجود دارد؟ آیا محدودیت‌ها رعایت شده‌اند؟ آیا خروجی از نظر ساختار معتبر است؟

۱۰.۳ روش‌های Self-Correction

الف) Self-Critique

Agent خروجی خود را بر اساس معیارهای مشخص بررسی می‌کند. برای مثال، یک Writer Agent می‌تواند متن تولیدشده را از نظر کامل بودن، انسجام و پوشش موضوع ارزیابی کند.

ب) External Validation

خروجی با یک ابزار یا منبع مستقل بررسی می‌شود. مثلاً کد تولیدشده اجرا می‌شود، JSON با Schema اعتبارسنجی می‌شود یا محاسبات با یک تابع قطعی دوباره انجام می‌شوند.

ج) Critic Agent

یک Agent جداگانه نقش منتقد را بر عهده دارد و خروجی Agent تولیدکننده را با معیارهای از پیش تعیین‌شده بررسی می‌کند.

۱۰.۴ نمونه Self-Correction

async def generate_with_review(task, max_revisions=2):
    draft = await writer_agent.generate(task)

    for attempt in range(max_revisions):
        review = await critic_agent.evaluate(
            task=task,
            output=draft
        )

        if review.passed:
            return draft

        draft = await writer_agent.revise(
            original=draft,
            feedback=review.feedback
        )

    return {
        "output": draft,
        "status": "needs_review"
    }

۱۰.۵ مشکل Self-Confirmation

اگر همان Agent هم پاسخ را تولید کند و هم آن را ارزیابی کند، ممکن است به‌جای کشف اشتباه، از تصمیم قبلی خود دفاع کند. همچنین مدل ممکن است برای یک خروجی نادرست توضیحی ظاهراً منطقی بسازد.

برای کاهش این مشکل:

  • از معیارهای ارزیابی روشن و قابل اندازه‌گیری استفاده کنید.
  • برای موارد مهم، اعتبارسنجی مستقل و مبتنی بر ابزار داشته باشید.
  • از شواهد و داده واقعی برای بررسی ادعاها استفاده کنید.
  • در صورت امکان، ارزیاب را از تولیدکننده جدا کنید.
  • تعداد دفعات اصلاح را محدود کنید.
Reflection تضمین‌کننده صحت نیست. یک Agent می‌تواند چند بار بازبینی کند و همچنان به نتیجه اشتباه برسد. برای مسائل حساس، Self-Correction باید با کنترل قطعی، تست، منبع معتبر یا تأیید انسان ترکیب شود.

۱۱. Planning and Replanning

۱۱.۱ Planning چیست؟

Planning فرآیند تبدیل یک هدف کلی به مجموعه‌ای از اقدامات مشخص است. Agent باید هدف را درک کند، منابع لازم را شناسایی کند، وابستگی‌ها را در نظر بگیرد و ترتیبی برای انجام کارها بسازد.

برای مثال، هدف «تهیه گزارش مالی سه‌ماهه» ممکن است به دریافت داده‌ها، پاک‌سازی، محاسبه شاخص‌ها، مقایسه با دوره قبل، بررسی ناهنجاری‌ها و تهیه گزارش نهایی تبدیل شود.

برنامه‌ریزی اولیه همیشه مطابق انتظار پیش نمی‌رود. ممکن است داده موردنیاز موجود نباشد، ابزار از دسترس خارج شود، نتیجه یک تحلیل فرضیه اولیه را رد کند یا کاربر هدف را تغییر دهد.

۱۴. Agent Security and Guardrails

۱۴.۱ چرا امنیت در سیستم Agentic متفاوت است؟

یک مدل زبانی معمولی ممکن است فقط متن تولید کند؛ اما Agent می‌تواند از ابزارها استفاده کند، اطلاعات بخواند، داده بنویسد، ایمیل ارسال کند، فایل تغییر دهد یا عملیات خارجی انجام دهد.

بنابراین، خطای Agent فقط یک پاسخ نادرست نیست. یک تصمیم اشتباه می‌تواند باعث تغییر داده، افشای اطلاعات، ارسال پیام ناخواسته یا اجرای عملیات غیرقابل بازگشت شود.

۱۴.۲ اصل Least Privilege

هر Agent باید فقط به ابزارها و داده‌هایی دسترسی داشته باشد که برای وظیفه‌اش ضروری است. برای مثال، Research Agent ممکن است مجاز به جست‌وجو و خواندن اسناد باشد، اما نیازی به حذف اطلاعات از پایگاه داده نداشته باشد.

۱۴.۳ مهم‌ترین تهدیدهای امنیتی

الف) Prompt Injection

ممکن است کاربر یا یک سند خارجی شامل دستوراتی باشد که تلاش می‌کنند Agent را از هدف اصلی منحرف کنند. برای مثال، یک صفحه وب ممکن است حاوی متنی باشد که از Agent بخواهد اطلاعات محرمانه را ارسال کند.

متن بازیابی‌شده از اسناد، صفحات وب، ایمیل‌ها و خروجی ابزارها نباید به‌عنوان دستور قابل اعتماد تلقی شود. این محتوا باید داده غیرقابل اعتماد محسوب شود و نباید سیاست‌های امنیتی سیستم را تغییر دهد.

ب) Excessive Agency

به Agent اختیاراتی داده می‌شود که برای وظیفه لازم نیست. برای نمونه، یک Agent پاسخ‌گوی مشتریان به مجوز بازپرداخت مالی بدون تأیید نیاز ندارد.

ج) Data Exfiltration

Agent ممکن است اطلاعات محرمانه را از یک منبع دریافت کند و به‌صورت ناخواسته در خروجی، ایمیل یا سرویس دیگری ارسال کند.

د) Tool Abuse

استفاده نادرست از ابزار، فراخوانی بیش از حد API، ارسال پارامترهای نامعتبر یا اجرای عملیات خارج از محدوده مجاز.

هـ) Cross-Agent Privilege Escalation

ممکن است یک Agent از طریق واگذاری وظیفه، پیام یا Shared State به اطلاعات و اختیاراتی دست پیدا کند که در حالت عادی مجاز به استفاده از آن‌ها نیست.

۱۴.۴ Guardrails چیست؟

Guardrails مجموعه‌ای از قواعد، اعتبارسنجی‌ها و کنترل‌ها هستند که رفتار Agent را در محدوده امن و قابل قبول نگه می‌دارند. Guardrail می‌تواند پیش از اجرای عملیات، هنگام اجرا یا پس از تولید خروجی اعمال شود.

۱۵.۳ Retry با Exponential Backoff

اگر یک سرویس موقتاً از دسترس خارج شود، تکرار فوری درخواست ممکن است فشار بیشتری ایجاد کند. Exponential Backoff فاصله میان تلاش‌های مجدد را افزایش می‌دهد. 

import asyncio
import random

async def retry_with_backoff(
    operation,
    max_attempts=4,
    base_delay=1.0
):
    for attempt in range(max_attempts):
        try:
            return await operation()

        except TemporaryServiceError:
            if attempt == max_attempts - 1:
                raise

            delay = base_delay * (2 ** attempt)
            jitter = random.uniform(0, 0.3)

            await asyncio.sleep(delay + jitter)

Retry باید برای خطاهای موقت استفاده شود. برای خطای مجوز، ورودی نامعتبر یا عملیات غیرمجاز، تکرار همان درخواست معمولاً مشکل را حل نمی‌کند.

۱۵.۴ مدیریت Loop

Agent ممکن است بارها یک ابزار را با ورودی مشابه فراخوانی کند، برنامه‌ای بسازد که به نقطه قبلی برگردد یا بدون تولید پیشرفت واقعی بین چند Agent جابه‌جا شود.

برای جلوگیری از حلقه بی‌پایان، محدودیت‌های زیر مفید هستند:

  • حداکثر تعداد گام‌ها.
  • حداکثر تعداد فراخوانی ابزار.
  • سقف Token یا بودجه مالی.
  • مهلت کلی اجرای درخواست.
  • تشخیص تکرار Tool Call با پارامترهای یکسان.
  • بررسی میزان پیشرفت پس از هر مرحله.
  • شرط توقف روشن و قابل ارزیابی.

۱۵.۵ تشخیص عدم پیشرفت

تنها شمردن تعداد گام‌ها کافی نیست. بهتر است سیستم بررسی کند آیا وضعیت مسئله نسبت به مرحله قبلی تغییر مفیدی داشته است یا خیر. 

async def run_agent(task, max_steps=12):
    state = initialize_state(task)
    seen_actions = set()

    for step in range(max_steps):
        if state.is_complete:
            return state.result

        action = await agent.choose_action(state)

        action_key = (
            action.tool_name,
            stable_hash(action.arguments)
        )

        if action_key in seen_actions:
            return {
                "status": "stopped",
                "reason": "Repeated action detected"
            }

        seen_actions.add(action_key)

        result = await execute_action(action)
        new_state = update_state(state, result)

        if not made_progress(state, new_state):
            new_state.no_progress_count += 1

        if new_state.no_progress_count >= 3:
            return await request_replanning(new_state)

        state = new_state

    return {
        "status": "stopped",
        "reason": "Maximum steps reached"
    }

۱۵.۶ Idempotency

در سیستم‌های Agentic ممکن است یک Tool Call به دلیل Timeout دوباره اجرا شود. اگر عملیات موردنظر مثلاً ثبت پرداخت یا ارسال ایمیل باشد، اجرای دوباره می‌تواند اثر نامطلوب داشته باشد.

Idempotency یعنی اجرای مجدد یک درخواست با شناسه یکسان، اثر تکراری ناخواسته ایجاد نکند. برای عملیات حساس، از شناسه یکتا و ثبت نتیجه عملیات استفاده کنید.

۱۵.۷ مدیریت وضعیت شکست

وضعیت معنا رفتار پیشنهادی
pending هنوز شروع نشده انتظار برای اجرا
running در حال اجرا مانیتور کردن
completed با موفقیت پایان یافته ثبت خروجی
failed با خطا مواجه شده تحلیل خطا
retrying در حال تلاش مجدد کنترل تعداد Retry
cancelled لغو شده توقف عملیات وابسته
needs_review نیازمند بررسی ارجاع به انسان
برای عملیات غیرقابل بازگشت، صرفاً به Retry تکیه نکنید. پیش از اجرای عملیات، مجوز، شناسه تکرارناپذیری، وضعیت قبلی و امکان جبران یا لغو را بررسی کنید.

import asyncio

async def run_research_system(user_goal):

    state = create_project_state(user_goal)

    # Step 1: Create plan
    plan = await supervisor.create_plan(
        user_goal
    )

    # Step 2: Run independent research tasks
    research_results = await asyncio.gather(
        research_agent.run(plan.research_task),
        competitor_agent.run(plan.competitor_task)
    )

    state["research_results"] = research_results

    # Step 3: Analyze collected data
    analysis = await analyst_agent.run(
        research_results
    )

    state["analysis"] = analysis

    # Step 4: Generate draft
    draft = await writer_agent.run(
        user_goal=user_goal,
        research=research_results,
        analysis=analysis
    )

    # Step 5: Review draft
    review = await reviewer_agent.run(
        report=draft,
        evidence=research_results
    )

    # Step 6: Revise if necessary
    if not review["passed"]:
        draft = await writer_agent.revise(
            draft=draft,
            feedback=review["feedback"]
        )

    # Step 7: Final validation
    final_result = validate_final_report(
        draft,
        research_results
    )

    if not final_result.valid:
        return {
            "status": "needs_review",
            "reason": final_result.errors
        }

    return {
        "status": "completed",
        "report": draft
    }
