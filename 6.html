۱. مبانی Agentic AI و مسئله‌ای که حل می‌کند

Agentic AI چیست؟

اصطلاح Agentic AI به رویکردی در طراحی سیستم‌های هوش مصنوعی اشاره دارد که در آن مدل یا مجموعه‌ای از مدل‌ها می‌توانند برای رسیدن به یک هدف، مراحل مختلفی از تصمیم‌گیری و اجرا را انجام دهند. این سیستم‌ها صرفاً به یک ورودی پاسخ نمی‌دهند؛ آن‌ها ممکن است هدف را تحلیل کنند، کار را به چند مرحله تقسیم کنند، ابزار مناسب را انتخاب کنند، نتیجه ابزار را بررسی کنند و در صورت نیاز برنامه خود را تغییر دهند.

برای درک بهتر، یک مدل زبانی معمولی را تصور کنید که از آن می‌پرسید: «برای سفر کاری من برنامه‌ریزی کن.» ممکن است مدل یک برنامه پیشنهادی بنویسد. اما یک سیستم Agentic می‌تواند در محدوده مجوزهای خود، اطلاعات پرواز را جست‌وجو کند، تقویم را بررسی کند، گزینه‌ها را مقایسه کند، پیش‌نویس برنامه سفر بسازد و برای تأیید نهایی به کاربر مراجعه کند.

تعریف کاربردی: یک AI Agent سیستمی است که با توجه به هدف و وضعیت فعلی، تصمیم می‌گیرد چه اقدامی انجام دهد، آن اقدام را اجرا می‌کند، نتیجه را مشاهده می‌کند و بر اساس نتیجه، مرحله بعدی را انتخاب می‌کند.

چرا Agentic AI اهمیت پیدا کرده است؟

بسیاری از کارهای واقعی با یک پاسخ متنی تمام نمی‌شوند. برای مثال، رسیدگی به یک درخواست پشتیبانی ممکن است به بررسی حساب مشتری، پیدا کردن سفارش، بررسی سیاست بازپرداخت، محاسبه مبلغ و ثبت درخواست نیاز داشته باشد. مدل زبانی می‌تواند درباره این مراحل توضیح دهد؛ اما سیستم عامل‌محور می‌تواند آن‌ها را به شکل کنترل‌شده اجرا کند.

آیا هر استفاده از LLM یک Agent است؟

خیر. اگر یک برنامه فقط یک prompt را به مدل ارسال کند و پاسخ آن را نمایش دهد، معمولاً با یک کاربرد ساده از LLM روبه‌رو هستیم. اگر مدل بتواند بر اساس هدف و وضعیت، میان چند اقدام انتخاب کند، ابزارها را به کار بگیرد و از نتایج برای تصمیم بعدی استفاده کند، به الگوی Agent نزدیک‌تر می‌شویم.

نکته مهم: «عامل‌محور بودن» به معنی هوشیاری، آگاهی یا استقلال نامحدود نیست. Agent همچنان نرم‌افزاری است که در چارچوب مدل، ابزارها، داده‌ها، مجوزها و محدودیت‌هایی که طراحان تعریف کرده‌اند عمل می‌کند.

۲. AI Assistant vs AI Agent vs Agentic System

سه اصطلاح Assistant، Agent و Agentic System گاهی به جای یکدیگر استفاده می‌شوند، اما از نظر طراحی سیستم بهتر است میان آن‌ها تمایز قائل شویم.

AI Assistant چیست؟

AI Assistant یک دستیار هوشمند است که معمولاً در تعامل مستقیم با کاربر قرار دارد. وظیفه آن فهم درخواست، ارائه اطلاعات، تولید محتوا و کمک به انجام کار است. یک Assistant ممکن است ابزار هم داشته باشد؛ بنابراین وجود Tool Calling به تنهایی برای تبدیل آن به یک Agent کافی نیست.

مثال: کاربر از دستیار می‌خواهد یک ایمیل رسمی بنویسد. دستیار متن ایمیل را تولید می‌کند و کاربر خودش آن را ارسال می‌کند.

AI Agent چیست؟

AI Agent یک واحد اجرایی و تصمیم‌گیر است که یک هدف یا وظیفه مشخص دارد و می‌تواند در یک چرخه تصمیم‌گیری و اقدام، از ابزارها استفاده کند. Agent معمولاً ورودی، هدف، وضعیت، مجموعه ابزارها و معیار پایان دارد.

مثال: عامل پشتیبانی ابتدا سفارش را پیدا می‌کند، سپس وضعیت ارسال را بررسی می‌کند، سیاست مربوط را می‌خواند و بعد تصمیم می‌گیرد چه پاسخی مناسب است.

Agentic System چیست؟

Agentic System یک سیستم کامل است که ممکن است یک یا چند Agent، ابزارها، حافظه، پایگاه داده، صف وظایف، کنترل دسترسی، مانیتورینگ و سازوکار تأیید انسانی را کنار هم قرار دهد. در این سطح، تمرکز فقط روی رفتار یک Agent نیست؛ بلکه روی همکاری اجزا و مدیریت کل فرایند است.

مثال مقایسه‌ای: درخواست بازپرداخت

یک درخواست، سه سطح از پیاده‌سازی
Assistant:

توضیح می‌دهد چگونه می‌توان درخواست بازپرداخت ثبت کرد.

Agent:

شماره سفارش را دریافت می‌کند، سفارش را بررسی می‌کند، شرایط را می‌سنجد و درخواست بازپرداخت را در صورت مجاز بودن ثبت می‌کند.

Agentic System:

چند Agent برای بررسی سفارش، سیاست‌ها، تقلب احتمالی، محاسبه مبلغ و ثبت درخواست با یکدیگر همکاری می‌کنند؛ سیستم نیز مجوزها، گزارش رخدادها و تأیید انسانی را مدیریت می‌کند.

قاعده طراحی: برای یک وظیفه ساده، ساخت یک Agent پیچیده یا معماری چندعاملی الزاماً بهتر نیست. ابتدا ساده‌ترین معماری‌ای را انتخاب کنید که نیازهای واقعی را برآورده می‌کند.

۳. معماری AI Agent

معماری Agent مشخص می‌کند سیستم چگونه ورودی را دریافت می‌کند، هدف را می‌فهمد، وضعیت را نگه می‌دارد، تصمیم می‌گیرد، ابزار را اجرا می‌کند و نتیجه را ارزیابی می‌کند. در یک طراحی معمول، چند جزء اصلی با یکدیگر همکاری می‌کنند.

اجزای اصلی معماری

۱. User Interface یا ورودی

نقطه تعامل با کاربر یا سیستم دیگر است. ورودی می‌تواند متن، فایل، رویداد، درخواست API یا پیام یک سیستم خارجی باشد. رابط ورودی باید اطلاعات لازم را اعتبارسنجی کند و درخواست را به ساختار قابل پردازش تبدیل کند.

۲. Agent Controller یا Runtime

کنترل‌کننده، چرخه اجرای Agent را مدیریت می‌کند. تعیین می‌کند چه زمانی مدل فراخوانی شود، چه زمانی ابزار اجرا شود، نتیجه چگونه ثبت شود و چه زمانی فرایند متوقف شود. در بسیاری از پیاده‌سازی‌ها، این بخش شامل کد معمولی و منطق کنترلی است، نه صرفاً یک prompt.

۳. LLM یا مدل تصمیم‌گیر

مدل زبانی می‌تواند درخواست را تفسیر کند، گزینه‌های اقدام را پیشنهاد دهد، پارامترهای ابزار را تولید کند، نتیجه مشاهده‌شده را تحلیل کند و پاسخ نهایی را بسازد. با این حال، مدل نباید تنها مرجع اجرای سیاست‌های امنیتی باشد.

۴. Tools یا ابزارها

ابزارها قابلیت انجام عملیات واقعی را فراهم می‌کنند: جست‌وجو، خواندن فایل، اجرای Query، ارسال پیام، ثبت سفارش، فراخوانی API یا تغییر وضعیت یک سامانه.

۵. Memory و State

حافظه می‌تواند اطلاعات مفید گذشته را نگه دارد؛ State نیز وضعیت جاری اجرای یک وظیفه را ثبت می‌کند. این دو مفهوم مرتبط‌اند، اما یکسان نیستند.

۶. Planner یا برنامه‌ریز

برنامه‌ریز هدف را به مراحل کوچک‌تر تبدیل می‌کند، وابستگی میان مراحل را مشخص می‌کند و ترتیب اجرای آن‌ها را پیشنهاد می‌دهد. برنامه‌ریزی ممکن است توسط خود LLM، یک الگوریتم مشخص یا ترکیبی از آن‌ها انجام شود.

۷. Guardrails و Policy Engine

۴. Agent Loop یا چرخه اجرای Agent

مهم‌ترین الگوی اجرایی در بسیاری از Agentها، یک چرخه تکرارشونده است. Agent وضعیت فعلی را بررسی می‌کند، تصمیم می‌گیرد چه کاری انجام دهد، آن کار را اجرا می‌کند، نتیجه را می‌بیند و سپس تصمیم بعدی را می‌گیرد.

مراحل چرخه

  1. Observe: دریافت ورودی، وضعیت، پیام‌ها و نتایج اقدامات قبلی.
  2. Interpret: درک شرایط و شناسایی مسئله فعلی.
  3. Decide: انتخاب اقدام بعدی یا تصمیم به پایان کار.
  4. Act: اجرای ابزار یا تولید خروجی مورد نیاز.
  5. Evaluate: بررسی نتیجه و مقایسه آن با هدف.
  6. Continue or Stop: ادامه چرخه، اصلاح برنامه یا پایان دادن به وظیفه.

یک مثال واقعی: پیدا کردن وضعیت سفارش

فرض کنید کاربر می‌گوید: «سفارشم هنوز نرسیده؛ لطفاً بررسی کن.»

مرحله رفتار Agent
Observe درخواست کاربر و شناسه سفارش را دریافت می‌کند.
Reason متوجه می‌شود برای پاسخ دقیق باید سفارش و وضعیت ارسال را بررسی کند.
Decide ابزار جست‌وجوی سفارش را انتخاب می‌کند.

Next action در صورت نیاز ابزار رهگیری مرسوله را فراخوانی می‌کند.
Finish وضعیت و اطلاعات قابل استناد را به کاربر اعلام می‌کند.

شرایط توقف چرخه

چرخه Agent نباید بدون محدودیت ادامه پیدا کند. باید شرایط پایان مشخص باشند؛ برای مثال:

  • هدف به شکل قابل قبول تکمیل شده باشد.
  • Agent به اطلاعاتی نیاز داشته باشد که کاربر باید فراهم کند.
  • اقدام بعدی به تأیید انسانی نیاز داشته باشد.
  • تعداد گام‌ها یا زمان مجاز تمام شده باشد.
  • ابزارها به شکل مکرر خطا بدهند.
  • Agent تشخیص دهد ادامه دادن امن یا مفید نیست.
خطر حلقه بی‌نهایت: اگر Agent نتواند تشخیص دهد که اقدام‌های قبلی شکست خورده‌اند، ممکن است بارها یک ابزار را با ورودی مشابه فراخوانی کند. محدودیت تعداد گام‌ها، timeout، تشخیص تکرار و سقف هزینه ضروری‌اند.

شبه‌کد Agent Loop

state = initialize_task(user_request)

for step in range(MAX_STEPS):

    observation = collect_observation(state)

    decision = model_decide(
        goal=state.goal,
        history=state.history,
        observation=observation,
        available_tools=tool_schemas
    )

    if decision.type == "final":
        return decision.answer

    if decision.type == "tool_call":
        validate_tool_call(decision)
        result = execute_tool(decision.tool, decision.arguments)
        state = update_state(state, result)

    if decision.type == "need_human":
        return request_human_approval(decision)

return stop_with_limit_message(state)

این شبه‌کد برای نمایش الگو است؛ در سامانه واقعی باید مدیریت خطا، احراز هویت، ثبت رخداد، کنترل مجوز و ذخیره پایدار وضعیت نیز اضافه شود.

۵. Reasoning and Planning — استدلال و برنامه‌ریزی

Reasoning چیست؟

Reasoning یا استدلال، فرایند تحلیل مسئله و انتخاب پاسخ یا اقدام مناسب است. در یک Agent، استدلال می‌تواند شامل فهم هدف، بررسی اطلاعات موجود، شناسایی اطلاعات ناقص، مقایسه گزینه‌ها و ارزیابی پیامدهای احتمالی باشد.

برای مثال، اگر هدف «آماده‌سازی گزارش فروش ماهانه» باشد، Agent باید تشخیص دهد که احتمالاً به داده‌های فروش، بازه زمانی، تعریف شاخص‌ها و قالب گزارش نیاز دارد. سپس باید مشخص کند کدام داده‌ها موجودند و چه اقداماتی لازم است.

Planning چیست؟

Planning یا برنامه‌ریزی، تبدیل هدف کلی به مجموعه‌ای از گام‌های مشخص است. برنامه باید ترتیب اجرا، وابستگی مراحل، ورودی‌های مورد نیاز و شرایط موفقیت را مشخص کند.

تفاوت اصلی: Reasoning کمک می‌کند بفهمیم چه چیزی مناسب است؛ Planning مشخص می‌کند برای رسیدن به هدف، چه مراحلی باید طی شوند. در عمل این دو به‌شدت به هم وابسته‌اند.

برنامه‌ریزی و عدم قطعیت

برنامه‌ریزی Agent باید انعطاف‌پذیر باشد. ممکن است یک API در دسترس نباشد، داده‌ای وجود نداشته باشد، کاربر اطلاعات ناقص داده باشد یا نتیجه یک مرحله با انتظار اولیه متفاوت باشد. بنابراین برنامه‌ریز باید بتواند:

  • مرحله شکست‌خورده را دوباره اجرا کند، اگر تکرار امن باشد.
  • از ابزار جایگزین استفاده کند.
  • برنامه را با توجه به اطلاعات جدید تغییر دهد.
  • در صورت نیاز از کاربر سؤال تکمیلی بپرسد.
  • وقتی هدف دیگر قابل دستیابی نیست، شفاف متوقف شود.
استدلال تولیدشده توسط مدل همیشه درست نیست. سیستم باید تصمیم‌های مهم را با داده واقعی، قوانین قطعی، خروجی ابزارها و اعتبارسنجی مستقل کنترل کند.

def get_order_status(order_id: str):
    if not isinstance(order_id, str) or not order_id.strip():

    # In a real application, call an authenticated backend API.
    return {
        "order_id": order_id,
        "status": "shipped",
        "tracking_available": True
    }


def execute_tool(name, arguments):

اصول طراحی Tool خوب

  • Single responsibility: هر ابزار یک وظیفه روشن داشته باشد.
  • Clear schema: ورودی و خروجی ساختاریافته و قابل اعتبارسنجی باشند.
  • Predictable errors: خطاها مشخص و قابل تفسیر باشند.
  • Authentication: ابزار از هویت و مجوز معتبر استفاده کند.
  • Idempotency: برای عملیات حساس، امکان جلوگیری از اجرای تکراری فراهم شود.
  • Observability: زمان، ورودی مجاز، نتیجه و خطا ثبت شوند.
  • Least privilege: ابزار فقط دسترسی لازم برای همان کار را داشته باشد.

۷. Agent Memory — حافظه عامل

چرا Agent به حافظه نیاز دارد؟

یک Agent ممکن است برای انجام یک وظیفه به چندین مرحله نیاز داشته باشد. اگر در هر مرحله فقط درخواست اولیه را ببیند و هیچ اطلاعاتی از مراحل قبلی نداشته باشد، نمی‌تواند به‌خوبی کار را ادامه دهد. حافظه کمک می‌کند اطلاعات مهم، ترجیحات، نتایج قبلی و زمینه لازم برای تصمیم‌های بعدی حفظ شوند.

برای مثال، در یک فرایند برنامه‌ریزی سفر، Agent باید بداند مقصد چیست، چه تاریخ‌هایی انتخاب شده‌اند، کدام گزینه‌ها بررسی شده‌اند، چه محدودیت‌هایی وجود دارد و کدام بخش هنوز تأیید نشده است.

حافظه چه چیزهایی را می‌تواند نگه دارد؟

  • اطلاعات مرتبط با مکالمه جاری
  • ترجیحات کاربر که مجاز به نگهداری آن‌ها هستیم
  • خلاصه وظایف و اقدامات قبلی
  • نتایج ابزارها و شناسه منابع
  • دانش بازیابی‌شده از پایگاه دانش
  • تجربه‌های عملیاتی یا الگوهای تکرارشونده، در صورت طراحی و کنترل مناسب

انواع حافظه در Agent

نوع توضیح مثال
Conversation Memory حفظ پیام‌های مکالمه جاری درخواست قبلی کاربر
Working Memory اطلاعات لازم برای کار در حال اجرا مرحله فعلی و نتایج میانی
Episodic Memory ثبت تجربه‌ها یا رخدادهای گذشته وظیفه‌ای که قبلاً انجام شده است
Semantic Memory دانش عمومی یا حقایق ذخیره‌شده قوانین یا اطلاعات دامنه
Procedural Memory روش‌ها و دستورالعمل‌های انجام کار مراحل رسیدگی به یک نوع درخواست

Conversation Memory

ساده‌ترین شکل حافظه، نگهداری پیام‌های قبلی مکالمه است. این روش برای مکالمات کوتاه مناسب است، اما با طولانی شدن تاریخچه، هزینه پردازش و حجم context افزایش می‌یابد. همچنین ممکن است اطلاعات غیرضروری زیادی وارد context شوند.

Working Memory

حافظه کاری شامل اطلاعاتی است که Agent برای تکمیل وظیفه جاری لازم دارد. این حافظه معمولاً از کل تاریخچه مکالمه کوچک‌تر و ساختاریافته‌تر است. برای مثال، می‌تواند شامل هدف، کارهای انجام‌شده، کارهای باقی‌مانده، نتیجه آخرین ابزار و محدودیت‌های فعال باشد.

Episodic Memory

حافظه اپیزودیک به رخدادها یا تجربه‌های قبلی اشاره دارد. یک سیستم ممکن است خلاصه کند که در اجرای قبلی چه اتفاقی افتاده، کدام روش موفق بوده و چه خطایی رخ داده است. ذخیره این اطلاعات باید با سیاست نگهداری داده و حریم خصوصی هماهنگ باشد.

Semantic Memory

حافظه معنایی شامل دانش نسبتاً پایدار است؛ مانند تعاریف، روابط مفهومی، اطلاعات دامنه یا حقایقی که برای چندین وظیفه کاربرد دارند. در برخی معماری‌ها، RAG نقش مهمی در دسترسی به چنین دانشی دارد.

Procedural Memory

حافظه رویه‌ای درباره چگونگی انجام کار است. برای مثال، یک Agent پشتیبانی می‌تواند دستورالعمل رسیدگی به شکایت را از طریق یک workflow تعریف‌شده یا مجموعه‌ای از رویه‌های مجاز دریافت کند. این حافظه نباید جایگزین کنترل‌های قطعی و قوانین امنیتی شود.

حافظه به تنهایی به معنی یادگیری مدل نیست. ذخیره اطلاعات در پایگاه داده یا بازیابی آن در prompt، لزوماً وزن‌های مدل را تغییر نمی‌دهد.

۸. Short-term and Long-term Memory

یکی از تقسیم‌بندی‌های رایج حافظه، تفاوت میان حافظه کوتاه‌مدت و بلندمدت است. این تقسیم‌بندی بیشتر درباره مدت و دامنه نگهداری اطلاعات صحبت می‌کند، نه اینکه الزاماً از دو فناوری کاملاً جدا استفاده شود.

Short-term Memory

حافظه کوتاه‌مدت اطلاعات مورد نیاز در مکالمه یا وظیفه جاری را نگه می‌دارد. این حافظه معمولاً شامل پیام‌های اخیر، نتایج ابزارها، تصمیم‌های موقت و وضعیت اجرای فعلی است.

نمونه: Agent در حال رزرو یک جلسه است. باید زمان انتخاب‌شده، شرکت‌کنندگان و اتاق‌های بررسی‌شده را در همان فرایند به خاطر بسپارد.

Long-term Memory

حافظه بلندمدت اطلاعاتی را نگه می‌دارد که ممکن است در وظایف آینده نیز مفید باشند. این اطلاعات می‌توانند ترجیحات مجاز، خلاصه تجربه‌های گذشته، دانش دامنه یا داده‌های ساختاریافته باشند.

نمونه: یک دستیار سازمانی ممکن است تنظیمات عمومی و مجاز مربوط به قالب گزارش‌های یک تیم را برای استفاده در دفعات بعد نگه دارد.

چالش اصلی مدیریت context و وضعیت جاری کیفیت، تازگی، حریم خصوصی و بازیابی

چه چیزی را باید به حافظه بلندمدت منتقل کرد؟

همه اطلاعات کوتاه‌مدت نباید به حافظه بلندمدت منتقل شوند. انتخاب باید بر اساس ارزش آینده، مجوز نگهداری، حساسیت اطلاعات، قابلیت اصلاح و زمان انقضا انجام شود.

یک الگوی مناسب: اطلاعات موقت را در State نگه دارید؛ اطلاعات پایدار و مجاز را با ساختار و سیاست نگهداری مشخص ذخیره کنید؛ و هنگام نیاز فقط بخش مرتبط را بازیابی کنید.

۹. State Management — مدیریت وضعیت

State چیست؟

State یا وضعیت، مجموعه اطلاعاتی است که نشان می‌دهد Agent یا وظیفه در حال حاضر در چه شرایطی قرار دارد. State می‌تواند هدف، مرحله فعلی، نتایج ابزارها، تصمیم‌های گرفته‌شده، کارهای باقی‌مانده، خطاها و وضعیت تأیید انسانی را در بر بگیرد.

حافظه معمولاً برای نگهداری اطلاعات مفید از گذشته به کار می‌رود؛ اما State وضعیت جاری فرایند را مشخص می‌کند. یک Agent ممکن است حافظه بلندمدت داشته باشد، اما بدون State دقیق نتواند اجرای نیمه‌تمام یک وظیفه را به درستی ادامه دهد.

در عمل، وضعیت‌های بیشتری نیز ممکن است لازم باشند: failed، cancelled، paused، needs_approval و retrying. وضعیت‌ها باید به شکل روشن تعریف شوند تا اجزای مختلف سیستم تفسیر یکسانی داشته باشند.

چرا State Management اهمیت دارد؟

  • ادامه اجرای وظایف بعد از قطع ارتباط یا restart.
  • جلوگیری از اجرای دوباره مراحل تکمیل‌شده.
  • تشخیص اینکه وظیفه منتظر کاربر یا تأیید انسانی است.
  • مدیریت retry و خطاهای موقت.
  • ثبت سابقه تصمیم‌ها و اقدامات برای audit.
  • هماهنگی میان چند Agent یا سرویس.

State و Idempotency

فرض کنید Agent یک درخواست پرداخت را ارسال می‌کند، اما قبل از دریافت پاسخ، ارتباط شبکه قطع می‌شود. Agent نمی‌داند پرداخت انجام شده است یا نه. اگر بدون بررسی دوباره همان عملیات را اجرا کند، ممکن است پرداخت تکراری رخ دهد.

برای چنین مواردی، استفاده از شناسه یکتای عملیات یا Idempotency Key کمک می‌کند درخواست تکراری به اجرای تکراری اثر مالی منجر نشود. همچنین باید وضعیت عملیات از سرویس مرجع استعلام شود.

الگوی ذخیره‌سازی امن State

  • برای هر وظیفه شناسه یکتا در نظر بگیرید.
  • تغییرات مهم State را به شکل اتمیک ذخیره کنید.
  • وضعیت و تاریخچه رویدادها را از هم تفکیک کنید.
  • اطلاعات حساس را بدون ضرورت در State ذخیره نکنید.
  • برای وظایف طولانی checkpoint ایجاد کنید.
  • برای Stateهای قدیمی سیاست انقضا و پاک‌سازی داشته باشید.

۱۰. Goal-oriented Agents — عامل‌های هدف‌محور

هدف‌محوری به چه معناست؟

یک Agent هدف‌محور، اقدامات خود را با توجه به یک وضعیت مطلوب انتخاب می‌کند. به جای اینکه فقط به پیام بعدی واکنش نشان دهد، تلاش می‌کند فاصله میان وضعیت فعلی و وضعیت مورد نظر را کاهش دهد.

برای مثال، هدف «تهیه گزارش نهایی» است. وضعیت فعلی ممکن است شامل داده خام و چند منبع ناقص باشد. Agent باید تشخیص دهد برای رسیدن به وضعیت نهایی چه مراحلی باقی مانده‌اند.

هدف خوب چه ویژگی‌هایی دارد؟

  • Clarity: هدف باید روشن و قابل تفسیر باشد.
  • Measurability: تا حد امکان معیار موفقیت داشته باشد.
  • Feasibility: با ابزارها و مجوزهای موجود قابل انجام باشد.
  • Constraints: محدودیت‌ها و مرزهای اجرا مشخص باشند.
  • Completion criteria: معلوم باشد چه زمانی کار تمام شده است.

Goal، Task و Action چه تفاوتی دارند؟

مفهوم معنا مثال
Goal نتیجه نهایی مورد نظر تهیه گزارش فروش
Task یک بخش قابل مدیریت از هدف جمع‌آوری داده فروش
Action یک اقدام اجرایی مشخص اجرای Query روی دیتابیس

Goal Decomposition

در Goal Decomposition، هدف اصلی به چند هدف فرعی تقسیم می‌شود. این کار برای جلوگیری از مبهم ماندن وظیفه و کنترل پیشرفت ضروری است. 

Goal:
  Resolve customer complaint

Subgoals:
  1. Identify customer
  2. Retrieve relevant order
  3. Understand complaint category
  4. Retrieve applicable policy
  5. Determine eligible resolution
  6. Obtain approval if required
  7. Execute approved action
  8. Confirm result to customer

Goal Conflict

ممکن است چند هدف با یکدیگر تعارض داشته باشند. برای مثال، هدف کاهش هزینه با هدف افزایش کیفیت خدمات، یا هدف سرعت با هدف بررسی دقیق امنیتی در تعارض قرار گیرد. سیستم باید اولویت‌ها و محدودیت‌ها را از قبل مشخص کند.

یک Agent خوب صرفاً برای رسیدن به هدف تلاش نمی‌کند؛ بلکه باید بداند کدام راه‌ها برای رسیدن به هدف مجاز نیستند.

۱۱. Autonomous Agents — عامل‌های خودمختار

Autonomy چیست؟

خودمختاری یا Autonomy به میزان توانایی Agent در انتخاب و اجرای اقدامات بدون نیاز به دستور جداگانه برای هر مرحله اشاره دارد. یک Agent با خودمختاری بیشتر می‌تواند پس از دریافت هدف، چند مرحله را خودش برنامه‌ریزی و اجرا کند.

خودمختاری یک ویژگی صفر و یک نیست. سیستم می‌تواند برای اقدامات کم‌خطر مستقل باشد، اما برای اقدامات حساس به تأیید انسان نیاز داشته باشد.

طیف خودمختاری

سطح شرح نمونه
سطح ۱: پیشنهاددهنده فقط پیشنهاد اقدام می‌دهد. پیشنهاد پاسخ به ایمیل
سطح ۲: اجرای تأییدشده اقدام را آماده می‌کند و پیش از اجرا تأیید می‌گیرد. پیش‌نویس ایمیل و درخواست تأیید ارسال
سطح ۳: خودمختاری محدود اقدامات کم‌خطر را در محدوده مجاز اجرا می‌کند. دسته‌بندی و برچسب‌گذاری تیکت
سطح ۴: خودمختاری مشروط چند مرحله را مستقل اجرا می‌کند، اما برای نقاط حساس متوقف می‌شود. رسیدگی به درخواست با تأیید بازپرداخت
سطح ۵: خودمختاری گسترده در محدوده سیاست‌های سخت‌گیرانه، وظایف طولانی را مدیریت می‌کند. پایش و مدیریت یک workflow عملیاتی

این سطوح یک مدل آموزشی برای مقایسه‌اند، نه یک استاندارد رسمی یا طبقه‌بندی جهان‌شمول.

چه عواملی خودمختاری را محدود می‌کنند؟

  • مجوزهای دسترسی به ابزارها
  • سطح ریسک عملیات
  • میزان اطمینان به اطلاعات
  • هزینه اجرای مراحل
  • قوانین سازمان و الزامات قانونی
  • امکان بازگشت از اقدام یا اصلاح آن
  • محدودیت زمان و تعداد گام‌ها

خطر خودمختاری بیش از حد

اگر Agent به ابزارهای قدرتمند دسترسی داشته باشد، اما محدودیت کافی نداشته باشد، ممکن است اقدام اشتباه را در مقیاس بزرگ اجرا کند. برای مثال، یک عامل مدیریت ایمیل ممکن است پیام نادرستی ارسال کند، یا عامل مالی ممکن است تراکنش نامناسبی ثبت کند.

خودمختاری بیشتر الزاماً به معنی کیفیت بیشتر نیست. میزان استقلال باید با سطح ریسک، قابلیت نظارت و امکان جبران خطا متناسب باشد.

الگوی Autonomy با محدوده امن

Allowed without approval:
  - Search internal documentation
  - Read order status
  - Classify support tickets
  - Draft customer responses

Requires approval:
  - Send external messages
  - Issue refunds
  - Modify customer account data
  - Delete business records

Always blocked:
  - Access data outside the user's permissions
  - Bypass security controls
  - Execute prohibited operations

۱۲. Human-in-the-loop — انسان در حلقه تصمیم‌گیری

Human-in-the-loop چیست؟

Human-in-the-loop یا HITL به رویکردی گفته می‌شود که در آن انسان در بخشی از فرایند تصمیم‌گیری یا اجرا نقش دارد. این نقش می‌تواند تأیید یک اقدام، اصلاح نتیجه، ارائه اطلاعات تکمیلی یا داوری درباره خروجی باشد.

هدف HITL حذف کامل خودکارسازی نیست؛ بلکه ایجاد تعادل میان سرعت سیستم و کنترل انسانی است.

۱۳. Agent Orchestration — هماهنگی و ارکستریشن عامل‌ها

Orchestration چیست؟

Orchestration به مدیریت جریان کار میان Agentها، ابزارها و سرویس‌های مختلف گفته می‌شود. در یک سیستم ساده، یک Agent ممکن است تمام کار را انجام دهد. اما در سیستم‌های بزرگ‌تر، وظیفه می‌تواند میان چند Agent یا چند جزء تخصصی تقسیم شود.

برای مثال، یک سیستم تحلیل بازار ممکن است شامل عامل جست‌وجوی اطلاعات، عامل تحلیل رقبا، عامل بررسی داده‌ها و عامل تهیه گزارش باشد. Orchestrator مشخص می‌کند هر عامل چه کاری انجام دهد، چه زمانی اجرا شود و خروجی آن به کدام بخش منتقل شود.

چه زمانی به Multi-Agent نیاز داریم؟

  • وقتی وظیفه به حوزه‌های تخصصی مستقل تقسیم می‌شود.
  • وقتی چند فعالیت می‌توانند هم‌زمان اجرا شوند.
  • وقتی جداسازی دسترسی‌ها و مسئولیت‌ها مهم است.
  • وقتی یک Agent واحد بیش از حد پیچیده شده است.
  • وقتی لازم است نتایج چند تحلیل مستقل با هم ترکیب شوند.
Multi-Agent همیشه بهتر از Single-Agent نیست. ارتباط میان Agentها، هزینه فراخوانی مدل، هماهنگی State، مدیریت خطا و احتمال ناسازگاری خروجی‌ها می‌تواند پیچیدگی را افزایش دهد.

سناریو: دستیار هوشمند پشتیبانی مشتری

فرض کنید می‌خواهیم یک Agent بسازیم که درخواست‌های پشتیبانی را بررسی کند. این Agent باید بتواند سفارش را پیدا کند، وضعیت آن را بخواند، سیاست مرتبط را بازیابی کند و پاسخ مناسب تهیه کند. اگر نیاز به بازپرداخت باشد، باید پیش از اجرای آن تأیید انسانی بگیرد.

جریان اجرای سناریو

  1. کاربر درخواست خود را ارسال می‌کند.
  2. Agent موضوع درخواست را تشخیص می‌دهد.
  3. شناسه سفارش را دریافت یا در صورت لزوم درخواست می‌کند.
  4. Order Tool وضعیت سفارش را بازیابی می‌کند.
  5. Agent سیاست مربوط به مسئله را از دانش سازمانی می‌خواند.
  6. Agent بررسی می‌کند چه گزینه‌هایی مجاز هستند.
  7. اگر اقدام فقط خواندنی باشد، نتیجه را به کاربر اعلام می‌کند.
  8. اگر اقدام حساسی مانند بازپرداخت لازم باشد، درخواست تأیید می‌سازد.
  9. پس از تأیید معتبر، سرویس مجاز عملیات را اجرا می‌کند.
  10. Agent نتیجه واقعی را بررسی و به کاربر گزارش می‌کند.

نمونه کد آموزشی: ساختار ساده Agent

class SupportAgent:

    def __init__(self, llm, tools, state_store):
        self.llm = llm
        self.tools = tools
        self.state_store = state_store

    def run(self, user_request, task_id):

        state = self.state_store.load(task_id)

        if state is None:
            state = {
                "task_id": task_id,
                "goal": user_request,
                "history": [],
                "status": "running"
            }

        for step in range(8):

            decision = self.llm.decide(
                goal=state["goal"],
                history=state["history"],
                tools=self.tools.schemas()
            )

            if decision["type"] == "final":
                state["status"] = "completed"
                self.state_store.save(task_id, state)
                return decision["answer"]

            if decision["type"] == "tool_call":

                tool_name = decision["tool_name"]
                arguments = decision["arguments"]

                self.tools.validate(
                    tool_name,
                    arguments
                )

                result = self.tools.execute(
                    tool_name,
                    arguments
                )

                state["history"].append({
                    "tool": tool_name,
                    "result": result
                })

                self.state_store.save(task_id, state)

            elif decision["type"] == "needs_approval":

                state["status"] = "needs_approval"
                self.state_store.save(task_id, state)

                return {
                    "status": "needs_approval",
                    "proposal": decision["proposal"]
                }

        state["status"] = "max_steps_reached"
        self.state_store.save(task_id, state)

        return {
            "status": "incomplete",
            "message": "Execution limit reached"
        }
این کد یک اسکلت آموزشی است و مستقیماً برای محیط Production آماده نیست. در نسخه واقعی باید احراز هویت، کنترل دسترسی، مدیریت خطا، اعتبارسنجی دقیق schema، اجرای امن ابزارها، ذخیره پایدار، جلوگیری از عملیات تکراری و کنترل انسانی اضافه شوند. متد llm.decide نیز نمایشی است و به پیاده‌سازی واقعی مدل وابسته است.

چرا ارزیابی Agent دشوارتر از ارزیابی یک پاسخ متنی است؟

در یک سیستم ساده، ممکن است کیفیت پاسخ را بررسی کنیم. اما در Agent، باید علاوه بر پاسخ نهایی، مسیر رسیدن به پاسخ را نیز ارزیابی کنیم: آیا ابزار مناسب انتخاب شده؟ آیا ورودی ابزار صحیح بوده؟ آیا سیستم مجوز داشته؟ آیا هدف تکمیل شده؟ آیا عملیات ناخواسته‌ای رخ داده است؟

امنیت Agentic System

Agentها می‌توانند به داده‌ها و ابزارهای واقعی دسترسی داشته باشند. به همین دلیل، یک اشتباه در طراحی آن‌ها ممکن است فراتر از تولید پاسخ اشتباه باشد و به تغییر داده، افشای اطلاعات یا اجرای عملیات ناخواسته منجر شود.

۱. Least Privilege

هر Agent باید فقط به ابزارها و داده‌هایی دسترسی داشته باشد که برای وظیفه‌اش لازم‌اند. عامل تحلیل گزارش نباید به ابزار حذف حساب مشتری دسترسی داشته باشد.

۲. Prompt Injection

ممکن است محتوای بازیابی‌شده از یک سند، صفحه وب یا ایمیل شامل دستورهای مخرب باشد؛ برای مثال، به Agent بگوید دستورهای قبلی را نادیده بگیرد یا اطلاعات محرمانه را ارسال کند. سیستم باید محتوای خارجی را داده غیرقابل اعتماد تلقی کند، نه دستور معتبر برای تغییر سیاست‌ها.

۳. Tool Permission

کنترل دسترسی باید در لایه اجرای ابزار اعمال شود. نباید فرض کنیم که چون Agent در prompt گفته شده «فقط داده مجاز را بخوان»، دیگر نیازی به کنترل دسترسی واقعی وجود ندارد.

۴. Data Isolation

در سیستم‌های چندمستاجری، داده‌های هر سازمان یا کاربر باید جدا بمانند. Agent نباید بتواند از طریق جست‌وجو یا حافظه مشترک به اطلاعات دیگران دسترسی پیدا کند.

۵. Auditability

اقدامات مهم باید با شناسه وظیفه، هویت اجراکننده، ابزار، زمان، وضعیت تأیید و نتیجه ثبت شوند. اطلاعات حساس نباید بی‌دلیل در logها ذخیره شوند.

Observability یا مشاهده‌پذیری

برای فهم رفتار Agent باید بتوانیم مسیر اجرای آن را مشاهده کنیم. ثبت صرف پاسخ نهایی کافی نیست. بهتر است trace هر وظیفه نشان دهد چه تصمیمی گرفته شده، کدام ابزار فراخوانی شده، چقدر طول کشیده و چه نتیجه‌ای برگشته است.

۱۶. الگوهای پیشرفته در Agentic AI

۱. ReAct

ReAct نام الگویی است که Reasoning و Action را در یک چرخه به هم پیوند می‌دهد. سیستم با توجه به وضعیت، اقدام بعدی را انتخاب می‌کند، نتیجه اقدام را دریافت می‌کند و بر اساس مشاهده جدید ادامه می‌دهد. این الگو برای وظایفی مفید است که نیاز به تعامل مرحله‌ای با ابزارها دارند. 

Question
  ↓
Reason about next step
  ↓
Choose an action
  ↓
Execute tool
  ↓
Observe result
  ↓
Reason again
  ↓
Final response

۲. Reflection

در الگوی Reflection، سیستم خروجی یا اقدام قبلی خود را دوباره بررسی می‌کند. برای مثال، Agent پس از تهیه گزارش، آن را از نظر کامل بودن، سازگاری اعداد و رعایت قالب ارزیابی می‌کند. اگر ایرادی پیدا شود، خروجی را اصلاح می‌کند.

۳. Planning-based Agents

در این رویکرد، Agent پیش از اجرا برنامه‌ای از مراحل مورد نیاز می‌سازد. سپس هر مرحله را اجرا و نتیجه را با برنامه مقایسه می‌کند. برنامه ممکن است ثابت باشد یا با مشاهده اطلاعات جدید اصلاح شود.

۴. RAG-based Agents

این عامل‌ها هنگام تصمیم‌گیری یا پاسخ‌گویی از یک سامانه بازیابی دانش استفاده می‌کنند. برای مثال، Agent پشتیبانی ابتدا سیاست بازپرداخت را بازیابی می‌کند و سپس بر اساس آن تصمیم می‌گیرد. در این معماری، RAG منبع اطلاعات است و Agent چرخه تصمیم و اقدام را مدیریت می‌کند.

۵. Multi-Agent Debate یا Review

چند Agent ممکن است یک مسئله را از زاویه‌های مختلف بررسی کنند. سپس یک Agent دیگر یا یک مرحله ارزیابی، اختلاف‌ها و شواهد را مقایسه می‌کند. این روش می‌تواند برای بازبینی مفید باشد، اما توافق چند Agent به معنی درست بودن نتیجه نیست؛ همه آن‌ها ممکن است از یک داده ناقص یا فرض اشتباه استفاده کنند.

۶. Event-driven Agents

در سیستم‌های رویدادمحور، Agent با وقوع یک رویداد فعال می‌شود؛ مثلاً ثبت سفارش جدید، دریافت پیام، تغییر وضعیت یک پرونده یا عبور یک شاخص از حد مشخص. این معماری برای پایش و عملیات تکرارشونده کاربرد دارد.

۷. Multimodal Agents

عامل چندوجهی می‌تواند با انواع مختلف داده مانند متن، تصویر، صوت یا ویدئو کار کند؛ البته قابلیت‌های دقیق به مدل‌ها و ابزارهای در دسترس وابسته است. برای مثال، Agent تعمیر و نگهداری ممکن است تصویر یک قطعه را تحلیل کند، سوابق تعمیر را بخواند و یک دستورالعمل مرتبط را بازیابی کند.

۸. Agentic Workflow در برابر Agent کاملاً پویا

همه فرایندهای عامل‌محور نیازمند تصمیم‌گیری کاملاً آزاد نیستند. گاهی یک Workflow مشخص با چند نقطه تصمیم‌گیری، امن‌تر و قابل پیش‌بینی‌تر است. برای کارهای حساس، می‌توان مسیر کلی را از پیش تعیین کرد و فقط انتخاب‌های محدود را به مدل سپرد.

۱۷. چگونه یک Agent Production-ready طراحی کنیم؟

ساخت یک نمونه آزمایشی Agent نسبتاً ساده است؛ اما تبدیل آن به یک سرویس قابل اعتماد نیازمند طراحی دقیق است. باید از ابتدا به رفتارهای شکست، امنیت، کنترل هزینه و نگهداری فکر کرد.

۱۸. تمرین‌های عملی برای تسلط بر Agentic AI

تمرین ۱: طراحی Agent ساده

هدف: یک Agent طراحی کنید که بتواند اطلاعات آب‌وهوا را برای یک شهر دریافت کند و خلاصه‌ای از وضعیت ارائه دهد.

کارهایی که باید مشخص کنید:

  • هدف Agent چیست؟
  • چه ابزاری لازم دارد؟
  • ورودی ابزار چیست؟
  • خروجی ابزار چه ساختاری دارد؟
  • اگر شهر مشخص نشده باشد، چه می‌کند؟
  • شرط پایان چرخه چیست؟

تمرین ۲: طراحی حافظه

یک Agent برنامه‌ریز پروژه طراحی کنید. مشخص کنید کدام اطلاعات باید در حافظه کوتاه‌مدت، کدام اطلاعات در حافظه بلندمدت و کدام اطلاعات در State ذخیره شوند.

تمرین ۳: طراحی Human-in-the-loop

Agentی بسازید که بتواند پیش‌نویس ایمیل را تهیه کند، اما برای ارسال آن تأیید انسانی بگیرد. طراحی کنید که چه اطلاعاتی باید در صفحه تأیید نمایش داده شود.

تمرین ۴: Multi-Agent Orchestration

یک سیستم تولید گزارش بازار طراحی کنید که شامل Research Agent، Analysis Agent و Writing Agent باشد. مشخص کنید داده‌ها چگونه میان عامل‌ها منتقل می‌شوند، چه کسی مسئول کنترل کیفیت است و در صورت شکست یک عامل چه اتفاقی می‌افتد.

تمرین ۵: تحلیل خطا

فرض کنید Agent سه بار پشت سر هم یک ابزار را با پارامتر اشتباه فراخوانی می‌کند. علت‌های احتمالی را بررسی کنید و راهکارهایی برای جلوگیری از تکرار این خطا پیشنهاد دهید.

جمع‌بندی نهایی

Agentic AI را می‌توان مرحله‌ای فراتر از تولید پاسخ متنی دانست: سیستمی که هدف را دریافت می‌کند، وضعیت را می‌فهمد، برای رسیدن به هدف برنامه می‌ریزد، ابزار مناسب را فراخوانی می‌کند، نتیجه را مشاهده می‌کند و در صورت نیاز مسیر خود را تغییر می‌دهد.

برای ساخت یک Agent قابل اعتماد، صرفاً انتخاب یک مدل قدرتمند کافی نیست. باید معماری مناسب، ابزارهای خوش‌تعریف، حافظه و State قابل کنترل، شرایط توقف، محدودیت دسترسی، تأیید انسانی و روش ارزیابی دقیق طراحی شوند.

نکته کلیدی این دوره: یک Agent خوب فقط نمی‌داند چه کاری می‌تواند انجام دهد؛ باید بداند چه کاری را مجاز است انجام دهد، چگونه نتیجه آن را بررسی کند و چه زمانی باید متوقف شود یا از انسان کمک بگیرد.
