مقدمه: از AI Prototype تا Production AI

ساخت یک برنامه ساده با استفاده از یک مدل زبانی بزرگ، معمولاً کار دشواری نیست. می‌توان با چند خط کد به یک API متصل شد، یک Prompt فرستاد و پاسخ دریافت کرد. اما این موضوع به‌معنای ساخت یک محصول هوش مصنوعی آماده استفاده در محیط واقعی نیست.

در دنیای واقعی، سیستم باید در برابر خطاهای شبکه، افزایش تعداد کاربران، تغییر رفتار مدل، داده‌های ناقص، حملات امنیتی، درخواست‌های غیرمنتظره، محدودیت بودجه و نیازهای جدید کسب‌وکار مقاوم باشد. همچنین باید بتوانیم کیفیت آن را اندازه‌گیری کنیم، هزینه آن را کنترل کنیم، نسخه‌های مختلفش را مدیریت کنیم و در صورت بروز مشکل، علت را پیدا کنیم.

اینجاست که مفهوم Advanced AI Engineering مطرح می‌شود. مهندسی پیشرفته هوش مصنوعی فقط به انتخاب یک مدل قوی‌تر یا نوشتن Prompt بهتر محدود نیست؛ بلکه مجموعه‌ای از اصول معماری نرم‌افزار، مهندسی داده، مهندسی مدل، امنیت، زیرساخت، ارزیابی، عملیات و مدیریت چرخه عمر سیستم است.

هدف نهایی: تبدیل قابلیت‌های هوش مصنوعی به یک سرویس قابل اتکا که بتواند در مقیاس واقعی، با کیفیت قابل اندازه‌گیری و هزینه کنترل‌شده، ارزش تجاری ایجاد کند.

1. Fine-tuning and Model Adaptation

۱.۱. مفهوم Model Adaptation چیست؟

مدل‌های پایه یا Foundation Models روی حجم بزرگی از داده‌ها آموزش دیده‌اند و توانایی‌های عمومی زیادی دارند. این مدل‌ها می‌توانند متن تولید کنند، کد بنویسند، سؤال پاسخ دهند، اطلاعات را خلاصه کنند و در بسیاری از مسائل استدلال کنند.

بااین‌حال، یک مدل عمومی لزوماً برای نیازهای خاص یک سازمان مناسب نیست. ممکن است سازمان به مدل نیاز داشته باشد که اصطلاحات تخصصی صنعت را بشناسد، خروجی را دقیقاً در قالب مشخصی تولید کند، سبک ارتباطی خاصی داشته باشد یا در یک وظیفه محدود عملکرد پایدارتری ارائه دهد.

Model Adaptation به مجموعه روش‌هایی گفته می‌شود که رفتار یا عملکرد مدل را برای یک مسئله مشخص تنظیم می‌کنند. Fine-tuning یکی از این روش‌هاست، اما تنها روش نیست.

۱.۲. تفاوت Prompt Engineering، RAG و Fine-tuning

روش چه چیزی را تغییر می‌دهد؟ کاربرد اصلی محدودیت
Prompt Engineering دستور و زمینه‌ای که به مدل داده می‌شود تغییر شیوه پاسخ‌گویی و هدایت رفتار وابسته به محدودیت Context Window و پایبندی مدل
RAG اطلاعاتی که هنگام پاسخ در اختیار مدل قرار می‌گیرد استفاده از دانش سازمانی و اطلاعات به‌روز کیفیت بازیابی و کیفیت اسناد اهمیت زیادی دارد
Fine-tuning پارامترهای مدل یا بخشی از آن‌ها یادگیری الگوهای رفتاری و وظایف تخصصی نیازمند داده مناسب، آموزش و ارزیابی دقیق

برای مثال، فرض کنیم یک شرکت حقوقی می‌خواهد دستیار هوشمندی بسازد. اگر هدف دستیار پاسخ‌گویی با استفاده از آخرین نسخه قراردادها و قوانین باشد، RAG احتمالاً انتخاب مناسبی است. اگر هدف تولید متن با ساختار و سبک ثابت حقوقی باشد، Fine-tuning می‌تواند مفید باشد. اگر فقط لازم باشد مدل در پاسخ‌ها از قالب خاصی استفاده کند، شاید Prompt Engineering کافی باشد.

Fine-tuning را نباید به‌عنوان راه‌حل پیش‌فرض برای هر مشکل مدل در نظر گرفت. بسیاری از مشکلاتی که ظاهراً به کمبود دانش مدل مربوط هستند، در واقع از بازیابی نامناسب، Prompt ضعیف، داده بی‌کیفیت یا طراحی نادرست سیستم ناشی می‌شوند.

۱.۳. انواع Fine-tuning

Supervised Fine-tuning (SFT)

در این روش، مدل با نمونه‌هایی از ورودی و خروجی مطلوب آموزش داده می‌شود. هر نمونه نشان می‌دهد که برای یک ورودی مشخص، پاسخ مناسب چه شکلی دارد.

برای نمونه، مجموعه داده ممکن است چنین ساختاری داشته باشد:

{
  "instruction": "این پیام مشتری را دسته‌بندی کن.",
  "input": "سفارش من هنوز به دستم نرسیده است.",
  "output": {
    "category": "delivery_issue",
    "priority": "medium"
  }
}

مدل با دیدن نمونه‌های متعدد، یاد می‌گیرد که برای ورودی‌های مشابه چه نوع خروجی‌ای تولید کند. کیفیت داده‌های آموزشی، تنوع مثال‌ها، سازگاری برچسب‌ها و نمایندگی سناریوهای واقعی در نتیجه نهایی تأثیر مستقیم دارند.

Parameter-Efficient Fine-tuning (PEFT)

آموزش همه پارامترهای یک مدل بزرگ ممکن است به منابع محاسباتی قابل‌توجهی نیاز داشته باشد. روش‌های PEFT تلاش می‌کنند با تغییر تعداد محدودتری از پارامترها یا اضافه کردن پارامترهای کوچک قابل‌آموزش، مدل را برای وظیفه موردنظر سازگار کنند.

  • LoRA: به‌جای تغییر مستقیم تمام وزن‌های مدل، به‌روزرسانی‌های کم‌رتبه‌ای را یاد می‌گیرد.
  • QLoRA: از کوانتیزه‌سازی برای کاهش مصرف حافظه در کنار روش LoRA استفاده می‌کند.
  • Adapters: لایه‌ها یا ماژول‌های کوچکی به مدل اضافه می‌شوند و همان بخش‌ها آموزش می‌بینند.

Instruction Tuning

هدف Instruction Tuning بهبود توانایی مدل در دنبال‌کردن دستورهاست. داده‌ها معمولاً شامل دستورهای متنوع، ورودی‌های اختیاری و پاسخ‌های مورد انتظار هستند. این روش می‌تواند مدل را برای انجام وظایف تعریف‌شده و پیروی از فرمت خروجی آماده‌تر کند.

Preference Optimization و روش‌های مبتنی بر بازخورد

در برخی روش‌ها، به‌جای ارائه تنها یک پاسخ صحیح، ترجیحات میان چند پاسخ به مدل آموزش داده می‌شود. برای مثال مشخص می‌شود پاسخ A از پاسخ B بهتر است، چون دقیق‌تر، مفیدتر یا ایمن‌تر است.

روش‌هایی مانند RLHF و DPO در این حوزه شناخته‌شده‌اند. انتخاب روش به نوع هدف، داده در دسترس، زیرساخت و هزینه آموزش بستگی دارد.

۱.۴. آماده‌سازی Dataset برای Fine-tuning

یکی از مهم‌ترین مراحل، آماده‌سازی داده است. مدل به‌طور خودکار نمی‌تواند کیفیت پایین داده آموزشی را جبران کند. داده‌های متناقض، پاسخ‌های اشتباه، اطلاعات حساس و مثال‌های تکراری می‌توانند مدل را به رفتار نامطلوب سوق دهند.

  • حذف نمونه‌های تکراری و خراب
  • بررسی صحت پاسخ‌های مرجع
  • حذف یا ناشناس‌سازی اطلاعات محرمانه و شخصی
  • توازن میان انواع سناریوها
  • ثبت منشأ و مجوز استفاده از داده‌ها
  • تفکیک داده‌های Train، Validation و Test
  • جلوگیری از نشت اطلاعات میان مجموعه‌های آموزشی و آزمون

۱.۵. ارزیابی مدل Fine-tuned

پس از آموزش، نباید صرفاً با مشاهده چند پاسخ خوب نتیجه بگیریم که مدل موفق بوده است. باید آن را با مدل پایه و نسخه‌های دیگر مقایسه کنیم.

شاخص‌های ارزیابی می‌توانند شامل این موارد باشند:

  • Accuracy و F1 برای وظایف طبقه‌بندی
  • Exact Match برای خروجی‌هایی که تطابق دقیق مهم است
  • اعتبار JSON یا ساختار خروجی
  • کیفیت پاسخ در ارزیابی انسانی
  • نرخ پاسخ‌های نادرست یا ساختگی
  • Latency، هزینه و مصرف حافظه
  • عملکرد روی داده‌های خارج از مجموعه آموزش

۱.۶. چه زمانی Fine-tuning انتخاب مناسبی است؟

موارد مناسب

  • طبقه‌بندی تخصصی و پرتکرار
  • تولید خروجی با قالب رفتاری ثابت
  • تطبیق لحن و سبک پاسخ‌گویی
  • یادگیری الگوهای تخصصی از مثال‌های معتبر
  • کاهش وابستگی به Promptهای طولانی

مواردی که باید با احتیاط بررسی شوند

  • نیاز به اطلاعاتی که مرتب تغییر می‌کنند
  • نبود داده آموزشی باکیفیت
  • مشکل اصلی در بازیابی اطلاعات
  • تعداد کم درخواست‌ها و نبود توجیه اقتصادی
  • نیاز به تضمین صحت بدون سیستم ارزیابی

۱.۷. چرخه عملی Model Adaptation

Define the task ↓ Build a baseline with an existing model ↓ Collect representative examples ↓ Clean and validate the dataset ↓ Choose adaptation method ↓ Train / tune the model ↓ Evaluate against baseline ↓ Security and regression testing ↓ Controlled deployment ↓ Monitor real-world performance ↓ Collect feedback and improve

نکته کلیدی این است که Fine-tuning یک فعالیت یک‌باره نیست. مدل پس از استقرار نیز باید از نظر کیفیت، تغییر توزیع داده‌ها، هزینه و رفتارهای ناخواسته بررسی شود.

2. Model Selection and Model Routing

۲.۱. چرا انتخاب مدل اهمیت دارد؟

در معماری یک سیستم AI، انتخاب مدل یکی از تصمیم‌های بنیادی است. مدل‌های مختلف از نظر توانایی استدلال، سرعت پاسخ‌گویی، هزینه، ظرفیت Context، پشتیبانی از تصویر و صوت، قابلیت فراخوانی ابزارها، محدودیت نرخ و سیاست‌های داده با یکدیگر تفاوت دارند.

انتخاب مدلی که برای همه درخواست‌ها استفاده شود، همیشه تصمیم بهینه‌ای نیست. ممکن است یک مدل قدرتمند برای درخواست‌های پیچیده ضروری باشد، اما استفاده از همان مدل برای دسته‌بندی ساده یا استخراج چند فیلد، هزینه غیرضروری ایجاد کند.

۲.۳. Model Routing چیست؟

Model Routing به معنای انتخاب مدل مناسب برای هر درخواست بر اساس ویژگی‌های درخواست، سیاست‌های سیستم و محدودیت‌های عملیاتی است.

در یک سیستم ساده، همه درخواست‌ها به یک مدل ارسال می‌شوند. در یک سیستم دارای Router، ابتدا درخواست تحلیل می‌شود و سپس به مدل یا مسیر پردازشی مناسب هدایت می‌شود.

۲.۴. انواع Model Router

Rule-based Routing

تصمیم‌گیری با قواعد مشخص انجام می‌شود. مثلاً اگر درخواست فقط شامل استخراج فیلدهای ساده باشد، از مدل کم‌هزینه استفاده می‌کنیم؛ اگر درخواست نیازمند تحلیل چندمرحله‌ای باشد، آن را به مدل قوی‌تر می‌فرستیم. 

if request.task_type == "classification":
    model = "small-model"

elif request.requires_complex_reasoning:
    model = "reasoning-model"

elif request.contains_images:
    model = "vision-model"

else:
    model = "general-purpose-model"

Classifier-based Routing

یک طبقه‌بند، نوع درخواست را تشخیص می‌دهد. این طبقه‌بند می‌تواند یک مدل کوچک، یک مدل زبانی یا ترکیبی از قواعد و مدل‌ها باشد.

Quality-aware Routing

Router علاوه بر نوع وظیفه، سطح کیفیت موردنیاز را نیز در نظر می‌گیرد. مثلاً برای یک پاسخ ساده، مدل ارزان کافی است؛ اما برای تصمیمی که خطای آن هزینه بالایی دارد، مسیر دقیق‌تر با اعتبارسنجی بیشتر انتخاب می‌شود.

Latency-aware Routing

در این روش، سرعت پاسخ‌گویی اهمیت زیادی دارد. اگر یک مدل کند باشد یا ظرفیت آن پر شده باشد، درخواست می‌تواند به مدل جایگزین هدایت شود.

Fallback Routing

اگر مدل اصلی خطا دهد، از دسترس خارج شود یا در زمان تعیین‌شده پاسخ ندهد، سیستم می‌تواند به مدل جایگزین منتقل شود. البته Fallback نباید به‌صورت کورکورانه انجام شود؛ مدل جایگزین باید برای همان نوع وظیفه قابل قبول باشد.

۲.۵. نمونه معماری Router

async def route_request(request):
    task = classify_task(request)

    if task == "simple":
        selected_model = "fast-model"

    elif task == "reasoning":
        selected_model = "reasoning-model"

    elif task == "vision":
        selected_model = "vision-model"

    else:
        selected_model = "general-model"

    try:
        response = await call_model(
            selected_model,
            request
        )

        return validate_response(response)

    except TemporaryModelError:
        fallback = choose_compatible_fallback(
            task,
            selected_model
        )

        return await call_model(fallback, request)

۲.۶. خطرهای Model Routing

  • Misclassification: درخواست به مدل نامناسب فرستاده می‌شود.
  • Quality inconsistency: کاربران برای درخواست‌های مشابه پاسخ‌های متفاوت می‌گیرند.
  • Routing overhead: تحلیل درخواست ممکن است زمان و هزینه اضافه کند.
  • Provider dependency: وابستگی بیش‌ازحد به یک ارائه‌دهنده می‌تواند ریسک عملیاتی ایجاد کند.
  • Silent degradation: سیستم در زمان اختلال به مدل ضعیف‌تر منتقل می‌شود، اما این تغییر ثبت نمی‌شود.
یک Router حرفه‌ای باید علاوه بر انتخاب مدل، دلیل انتخاب، نسخه سیاست Routing، زمان پاسخ، هزینه، نتیجه اعتبارسنجی و استفاده از مسیر جایگزین را ثبت کند.

3. AI Gateway Architecture

۳.۱. AI Gateway چیست؟

وقتی یک سازمان چند مدل، چند ارائه‌دهنده و چند برنامه هوش مصنوعی دارد، اتصال مستقیم هر برنامه به API هر مدل می‌تواند به معماری پیچیده و غیرقابل‌کنترلی منجر شود.

AI Gateway یک لایه واسط مرکزی میان برنامه‌ها و سرویس‌های مدل است. این لایه درخواست‌ها را دریافت می‌کند، سیاست‌های امنیتی را اعمال می‌کند، مدل مناسب را انتخاب می‌کند، محدودیت‌ها را کنترل می‌کند و نتیجه را به برنامه بازمی‌گرداند.

۳.۲. وظایف اصلی Gateway

Authentication و Authorization

Gateway باید تشخیص دهد درخواست از کدام کاربر، سرویس یا Agent آمده است و آیا اجازه استفاده از مدل یا قابلیت مشخص را دارد یا خیر.

Centralized Model Access

به‌جای آنکه هر سرویس کلید API جداگانه و تنظیمات مستقل داشته باشد، برنامه‌ها از یک نقطه کنترل‌شده به مدل‌ها دسترسی پیدا می‌کنند.

Rate Limiting و Quota

Gateway می‌تواند تعداد درخواست‌ها، تعداد توکن‌ها یا هزینه مصرف‌شده را برای هر کاربر، تیم یا سرویس محدود کند.

Model Routing

Gateway می‌تواند بر اساس سیاست سازمان، درخواست را به مدل مناسب هدایت کند. این تصمیم ممکن است با توجه به هزینه، تأخیر، نوع وظیفه یا دسترس‌پذیری مدل انجام شود.

Retries و Timeout

Gateway باید برای درخواست‌های ناموفق سیاست مشخصی داشته باشد. Timeout، Retry، Backoff و Circuit Breaker از جمله سازوکارهای مهم هستند.

Observability

Gateway محل مناسبی برای ثبت اطلاعات عملیاتی درخواست‌هاست: مدل استفاده‌شده، زمان پاسخ، تعداد توکن‌ها، هزینه تخمینی، خطا و وضعیت درخواست.

۳.۴. چرا Abstraction مهم است؟

هر Provider ممکن است ساختار API، نام پارامترها، روش Streaming، قالب خطا و قابلیت‌های متفاوتی داشته باشد. Gateway می‌تواند یک قرارداد داخلی مشترک ایجاد کند تا برنامه‌ها به جزئیات هر Provider وابسته نباشند.

بااین‌حال، Abstraction نباید تفاوت‌های واقعی مدل‌ها را پنهان کند. برای مثال، همه مدل‌ها قابلیت Tool Calling، خروجی JSON، تصویر یا Context یکسان ندارند. Gateway باید قابلیت‌های هر مدل را به‌شکل صریح نگهداری کند.

۳.۵. ملاحظات طراحی Gateway

  • Gateway نباید به نقطه شکست واحد بدون افزونگی تبدیل شود.
  • مسیرهای Streaming باید بدون Buffering غیرضروری طراحی شوند.
  • کلیدهای API نباید به کلاینت‌های نهایی ارسال شوند.
  • لاگ‌ها نباید به‌طور پیش‌فرض شامل متن محرمانه Prompt و پاسخ باشند.
  • سیاست‌های محدودیت مصرف باید قابل تنظیم و قابل ممیزی باشند.
  • تغییر مدل نباید باعث شکستن قرارداد API برنامه‌های وابسته شود.

4. AI Design Patterns

۴.۱. Design Pattern در سیستم‌های AI

Design Pattern یک الگوی تکرارشونده برای حل یک مسئله معماری یا طراحی است. در سیستم‌های AI، برخی مسائل مانند کنترل خروجی مدل، مدیریت خطا، بازیابی اطلاعات، اجرای ابزارها و کنترل گردش کار بارها تکرار می‌شوند.

استفاده از الگوهای طراحی باعث می‌شود سیستم‌ها ساختار قابل فهم‌تری داشته باشند، رفتار آن‌ها قابل آزمایش باشد و توسعه‌دهندگان بتوانند از راه‌حل‌های اثبات‌شده استفاده کنند.

۴.۲. الگوی Retrieval-Augmented Generation

در RAG، به‌جای تکیه کامل بر دانش پارامتری مدل، ابتدا اطلاعات مرتبط از یک منبع خارجی بازیابی می‌شود و سپس به مدل داده می‌شود تا پاسخ را با اتکا به آن اطلاعات تولید کند.

User Question ↓ Query Processing ↓ Retriever ↓ Relevant Documents ↓ Context Construction ↓ LLM ↓ Answer + Sources

RAG برای پاسخ‌گویی بر اساس اسناد داخلی، دانش سازمانی، راهنماها، مستندات فنی و اطلاعاتی که مرتب به‌روزرسانی می‌شوند مناسب است.

کیفیت RAG تنها به مدل زبانی وابسته نیست. Chunking، Embedding، Metadata Filtering، Retrieval، Reranking و Context Construction نیز اهمیت دارند.

۴.۳. الگوی Tool Calling

مدل به‌جای آنکه صرفاً پاسخ متنی تولید کند، یک ابزار را انتخاب و ورودی موردنیاز آن را پیشنهاد می‌کند. برنامه میزبان ابزار را اجرا می‌کند و نتیجه را دوباره در اختیار مدل می‌گذارد.

User Request ↓ LLM decides a tool is needed ↓ Tool call with structured arguments ↓ Application validates the call ↓ Tool execution ↓ Tool result ↓ LLM produces final answer

نکته مهم این است که مدل معمولاً خود ابزار را اجرا نمی‌کند؛ برنامه میزبان مسئول کنترل دسترسی، اعتبارسنجی ورودی و اجرای واقعی است.

۴.۴. الگوی Planner-Executor

در این الگو، یک بخش برنامه‌ریزی، مسئله را به مراحل کوچک‌تر تقسیم می‌کند و بخش اجرا آن مراحل را انجام می‌دهد.

  • Planner هدف را تحلیل می‌کند.
  • برنامه یا فهرست وظایف را تولید می‌کند.
  • Executor وظایف را اجرا می‌کند.
  • نتیجه هر مرحله بررسی می‌شود.
  • در صورت نیاز، برنامه اصلاح می‌شود.

این الگو برای کارهایی که چند مرحله وابسته دارند مناسب است؛ اما اگر مسئله ساده باشد، استفاده از Planner ممکن است پیچیدگی و هزینه غیرضروری ایجاد کند.

۴.۵. الگوی Guardrails

Guardrails مجموعه کنترل‌هایی هستند که ورودی، فرایند و خروجی سیستم را بررسی می‌کنند. این کنترل‌ها می‌توانند شامل اعتبارسنجی ساختار، بررسی سیاست‌های محتوا، محدودیت ابزار، تشخیص داده حساس و کنترل خروجی باشند.

Input ↓ Input Validation ↓ Safety / Policy Checks ↓ Model or Agent ↓ Output Validation ↓ Sensitive Data Checks ↓ Final Response

۴.۶. الگوی Human-in-the-Loop

در این الگو، بعضی تصمیم‌ها یا اقدامات مهم پیش از اجرا به تأیید انسان نیاز دارند. برای مثال، Agent می‌تواند یک ایمیل را آماده کند، اما ارسال آن نیازمند تأیید کاربر باشد.

این الگو در عملیات مالی، حذف داده، تغییر تنظیمات حساس، انتشار محتوا و عملیات غیرقابل بازگشت اهمیت زیادی دارد.

۴.۷. الگوی Structured Output

در این الگو، سیستم به‌جای پذیرش متن آزاد، از مدل می‌خواهد خروجی را در قالب ساختاریافته تولید کند. JSON یکی از قالب‌های متداول است. 

{
  "sentiment": "negative",
  "category": "billing",
  "priority": "high",
  "requires_human_review": true
}

خروجی ساختاریافته برای اتصال مدل به APIها، پایگاه داده‌ها و گردش کارهای نرم‌افزاری مفید است. بااین‌حال، معتبر بودن JSON به‌معنای درست بودن معنایی آن نیست؛ باید قواعد دامنه نیز بررسی شوند.

۴.۸. الگوی Retry و Fallback

سیستم‌های AI ممکن است با خطای موقت Provider، Timeout، پاسخ ناقص یا خروجی نامعتبر مواجه شوند. Retry برای تلاش مجدد و Fallback برای انتقال کنترل به مسیر جایگزین استفاده می‌شود.

Retry باید محدود، زمان‌بندی‌شده و متناسب با نوع خطا باشد. تکرار یک درخواست ناموفق بدون محدودیت می‌تواند هزینه را افزایش دهد یا عملیات جانبی را چند بار اجرا کند.

۴.۹. الگوی Cache

Cache می‌تواند پاسخ یا بخشی از محاسبات تکراری را ذخیره کند. در سیستم‌های LLM، Semantic Cache تلاش می‌کند درخواست‌هایی با معنای مشابه را شناسایی کند، حتی اگر متن آن‌ها دقیقاً یکسان نباشد.

استفاده از Cache باید با توجه به تازگی داده، مجوز کاربر، نسخه Prompt و نسخه مدل انجام شود. پاسخ یک کاربر نباید به کاربر دیگری که مجوز متفاوتی دارد نشت کند.

۴.۱۰. الگوی Circuit Breaker

اگر یک Provider یا سرویس وابسته مرتب خطا دهد، Circuit Breaker موقتاً ارسال درخواست‌های جدید به آن را متوقف می‌کند تا از فشار بیشتر و زنجیره‌ای شدن خطاها جلوگیری شود.

  • Closed: درخواست‌ها عبور می‌کنند.
  • Open: درخواست‌ها به سرویس معیوب ارسال نمی‌شوند.
  • Half-open: چند درخواست آزمایشی برای بررسی بازیابی سرویس ارسال می‌شود.

۴.۱۱. انتخاب Pattern مناسب

الگوها نباید صرفاً به‌دلیل محبوب بودن وارد معماری شوند. برای هر الگو باید مسئله‌ای مشخص وجود داشته باشد که استفاده از آن را توجیه کند. پیچیدگی معماری، هزینه اجرا، قابلیت تست و ریسک عملیاتی باید در تصمیم لحاظ شوند.

5. LLM Evaluation

۵.۱. چرا ارزیابی LLM دشوار است؟

در نرم‌افزارهای سنتی، برای ورودی مشخص اغلب می‌توان خروجی دقیق و قطعی تعریف کرد. اما مدل‌های زبانی ممکن است برای یک سؤال چند پاسخ متفاوت و درعین‌حال قابل قبول تولید کنند. همچنین پاسخ ممکن است از نظر نگارشی خوب باشد، اما از نظر factual accuracy اشتباه باشد.

بنابراین ارزیابی LLM باید چندبعدی باشد و فقط به یک معیار مانند شباهت متنی یا رضایت کاربر محدود نشود.

۵.۳. Golden Dataset

Golden Dataset مجموعه‌ای از نمونه‌های آزمون با پاسخ مرجع یا معیارهای ارزیابی تعریف‌شده است. این مجموعه باید نماینده کاربرد واقعی سیستم باشد.

برای یک دستیار پشتیبانی مشتری، نمونه‌ها باید شامل درخواست‌های ساده، شکایت‌ها، پرسش‌های چندمرحله‌ای، ورودی‌های ناقص، درخواست‌های خارج از حوزه و تلاش برای سوءاستفاده باشند.

بهتر است Golden Dataset نسخه‌بندی شود و نمونه‌های جدید از خطاهای مشاهده‌شده در Production به آن اضافه شوند.

۵.۴. روش‌های ارزیابی

Human Evaluation

ارزیاب انسانی پاسخ‌ها را با توجه به معیارهای مشخص بررسی می‌کند. این روش برای ارزیابی کیفیت معنایی، کاربردپذیری، صحت تخصصی و ایمنی بسیار مهم است.

Automated Metrics

معیارهای خودکار می‌توانند ساختار، شباهت، طبقه‌بندی، صحت محاسباتی یا وجود عبارت‌های مشخص را بررسی کنند. این معیارها سریع و قابل تکرار هستند، اما همیشه کیفیت واقعی پاسخ را نشان نمی‌دهند.

LLM-as-a-Judge

در این روش، یک مدل دیگر پاسخ تولیدشده را بر اساس Rubric ارزیابی می‌کند. این روش برای ارزیابی در مقیاس بزرگ مفید است، اما خود داور نیز ممکن است اشتباه کند، به پاسخ‌های طولانی‌تر امتیاز بیشتری بدهد یا نسبت به سبک خاصی سوگیری داشته باشد.

LLM-as-a-Judge نباید تنها معیار پذیرش محصول باشد. در کاربردهای حساس، نمونه‌ای از نتایج باید به‌صورت مستقل توسط انسان بررسی شود.

۵.۵. ارزیابی RAG

در سیستم RAG باید بخش بازیابی و بخش تولید پاسخ جداگانه ارزیابی شوند. ممکن است مدل پاسخ ضعیفی تولید کند، چون سند مناسب بازیابی نشده است؛ یا سند مناسب بازیابی شده باشد، اما مدل آن را اشتباه تفسیر کند.

  • Retrieval Recall: آیا اسناد مرتبط در نتایج بازیابی حضور دارند؟
  • Precision: چه نسبتی از اسناد بازیابی‌شده واقعاً مرتبط هستند؟
  • Ranking Quality: آیا اسناد مهم‌تر در رتبه‌های بالاتر قرار گرفته‌اند؟
  • Faithfulness: آیا پاسخ با محتوای منابع سازگار است؟
  • Answer Relevance: آیا پاسخ واقعاً سؤال کاربر را جواب می‌دهد؟
  • Citation Quality: آیا ارجاع‌ها از ادعاهای پاسخ پشتیبانی می‌کنند؟

۵.۶. ارزیابی Agentها

ارزیابی Agent پیچیده‌تر از ارزیابی یک پاسخ متنی است؛ زیرا Agent ممکن است چندین ابزار فراخوانی کند، برنامه‌ریزی انجام دهد، وضعیت نگهداری کند و در چند مرحله به هدف برسد.

معیارهای مهم عبارت‌اند از:

  • Task Success Rate: درصد وظایفی که به نتیجه مطلوب می‌رسند.
  • Tool Selection Accuracy: انتخاب ابزار درست.
  • Tool Argument Accuracy: درستی پارامترهای ابزار.
  • Step Efficiency: تعداد مراحل و فراخوانی‌های غیرضروری.
  • Recovery Rate: توانایی بازیابی پس از خطا.
  • Policy Compliance: رعایت مجوزها و سیاست‌ها.
  • Human Escalation Quality: تشخیص زمان مناسب برای ارجاع به انسان.

۵.۷. Regression Evaluation

هر تغییر در Prompt، مدل، ابزار، Retriever یا معماری ممکن است رفتار سیستم را تغییر دهد. Regression Evaluation بررسی می‌کند که آیا نسخه جدید باعث افت عملکرد در سناریوهای قبلی شده است یا خیر.

قبل از انتشار نسخه جدید باید مجموعه آزمون ثابت اجرا شود و نتایج آن با نسخه قبلی مقایسه شود.

۵.۸. Evaluation Pipeline

Dataset Version ↓ Run Model / Agent ↓ Collect Outputs and Traces ↓ Automated Evaluation ↓ Human Review (sampled / critical cases) ↓ Compare with Baseline ↓ Pass / Fail Gates ↓ Release Decision

6. AI Testing Strategies

۶.۱. تفاوت AI Testing با تست نرم‌افزار سنتی

در نرم‌افزار سنتی، رفتار تابع‌ها و سرویس‌ها معمولاً با ورودی و خروجی‌های نسبتاً مشخص قابل آزمایش است. در سیستم‌های AI، خروجی مدل ممکن است غیرقطعی باشد و کیفیت آن به Prompt، Context، مدل، تنظیمات Sampling و داده وابسته باشد.

به همین دلیل، تست AI باید علاوه بر تست کد، رفتار مدل و کل زنجیره تصمیم‌گیری را نیز بررسی کند.

۶.۲. Unit Testing

Unit Test اجزای کوچک و مستقل سیستم را آزمایش می‌کند. برای نمونه، تابع ساخت Prompt، اعتبارسنجی JSON، محاسبه هزینه، انتخاب مدل و تبدیل داده باید بدون نیاز به فراخوانی واقعی مدل تست شوند. 

def test_validate_priority():
    result = validate_ticket({
        "priority": "high",
        "category": "billing"
    })

    assert result.is_valid is True

۶.۳. Integration Testing

Integration Test تعامل اجزای مختلف را بررسی می‌کند. برای مثال، ارتباط میان برنامه، AI Gateway، Provider، پایگاه داده، Retriever و سرویس ابزارها.

در این سطح باید خطاهای شبکه، Timeout، پاسخ ناقص، محدودیت نرخ و ناسازگاری قراردادها نیز آزمایش شوند.

۶.۴. End-to-End Testing

تست End-to-End یک سناریوی کامل را از ورودی کاربر تا نتیجه نهایی بررسی می‌کند. در یک Agent پشتیبانی مشتری، می‌توان بررسی کرد که آیا سیستم درخواست را تشخیص می‌دهد، اطلاعات سفارش را بازیابی می‌کند، سیاست را رعایت می‌کند و پاسخ مناسب ارائه می‌دهد.

۶.۵. Prompt Testing

Prompt بخشی از منطق سیستم است و باید مانند کد، نسخه‌بندی و آزمایش شود. تغییر کوچک در Prompt ممکن است رفتار مدل را در مجموعه بزرگی از سناریوها تغییر دهد.

  • آزمون دستورهای عادی
  • آزمون ورودی مبهم
  • آزمون ورودی متناقض
  • آزمون تلاش برای نادیده گرفتن دستورهای سیستم
  • آزمون رعایت قالب خروجی
  • آزمون درخواست‌های خارج از حوزه

۶.۶. Adversarial Testing و Red Teaming

در Adversarial Testing، سیستم عمداً با ورودی‌های دشوار، خصمانه یا فریبنده آزمایش می‌شود. هدف شناسایی ضعف‌هایی است که در استفاده عادی آشکار نمی‌شوند.

نمونه سناریوها:

  • تلاش برای افشای System Prompt
  • درخواست دسترسی به داده کاربر دیگر
  • تزریق دستور مخرب داخل یک سند بازیابی‌شده
  • درخواست اجرای ابزار با پارامتر نامعتبر
  • تلاش برای دور زدن محدودیت‌های مالی یا عملیاتی
  • ارائه متن طولانی برای ایجاد اختلال در پردازش

۶.۷. Load Testing و Stress Testing

Load Testing بررسی می‌کند سیستم در حجم کاری مورد انتظار چه رفتاری دارد. Stress Testing سیستم را به فراتر از ظرفیت عادی می‌رساند تا نقطه شکست و رفتار آن هنگام فشار زیاد مشخص شود.

در سیستم‌های AI باید علاوه بر تعداد درخواست‌ها، تعداد توکن‌ها، طول Context، Streaming، تعداد فراخوانی ابزارها و مدت اجرای Agent نیز در نظر گرفته شوند.

۶.۸. Chaos Testing

Chaos Testing خرابی‌های کنترل‌شده ایجاد می‌کند تا مشخص شود سیستم چگونه به اختلال واکنش نشان می‌دهد. برای مثال می‌توان دسترسی به یک Provider را موقتاً قطع کرد، تأخیر شبکه را افزایش داد یا یک سرویس وابسته را از دسترس خارج کرد.

7. LLMOps and MLOps

۷.۱. MLOps چیست؟

MLOps مجموعه‌ای از اصول و فرایندها برای مدیریت چرخه عمر سیستم‌های یادگیری ماشین است. این چرخه از آماده‌سازی داده و آموزش مدل آغاز می‌شود و تا ارزیابی، انتشار، مانیتورینگ و به‌روزرسانی ادامه پیدا می‌کند.

هدف MLOps این است که توسعه و عملیات مدل‌های یادگیری ماشین قابل تکرار، قابل ردیابی، قابل اتوماسیون و قابل اعتماد باشد.

۷.۲. LLMOps چیست؟

LLMOps بر مدیریت عملیاتی برنامه‌هایی تمرکز دارد که از مدل‌های زبانی بزرگ استفاده می‌کنند. این حوزه بخشی از مفاهیم MLOps را به ارزیابی Prompt، مدیریت نسخه مدل، مدیریت Context، RAG، Tool Calling، Agentها، مصرف توکن و کنترل رفتار مدل گسترش می‌دهد.

۷.۵. Versioning

در یک سیستم LLM، نسخه مدل تنها چیزی نیست که باید ثبت شود. نسخه Prompt، داده‌های ارزیابی، ابزارها، تنظیمات Sampling، Retriever، Embedding Model و سیاست‌های امنیتی نیز باید مشخص باشند.

اگر یک پاسخ اشتباه در Production تولید شود، باید بتوانیم بفهمیم دقیقاً کدام نسخه مدل و Prompt، با چه Context و چه ابزارهایی در تولید آن نقش داشته‌اند.

۷.۶. CI/CD برای سیستم‌های AI

Continuous Integration و Continuous Delivery در سیستم‌های AI باید علاوه بر تست نرم‌افزار، ارزیابی رفتار مدل و کنترل‌های ایمنی را نیز شامل شوند.

Developer Change ↓ Code and Prompt Validation ↓ Unit / Integration Tests ↓ LLM Evaluation Suite ↓ Security Checks ↓ Build and Package ↓ Staging Deployment ↓ Smoke Tests ↓ Canary / Gradual Release ↓ Production

۷.۷. Model Registry و Artifact Management

Model Registry برای ثبت و مدیریت نسخه‌های مدل و اطلاعات مرتبط با آن‌ها استفاده می‌شود. در پروژه‌های AI، مدیریت Artifact می‌تواند شامل وزن مدل، فایل Tokenizer، تنظیمات آموزش، متادیتای Dataset، نتایج ارزیابی و گزارش‌های انتشار باشد.

۷.۸. Data و Model Drift

Data Drift زمانی رخ می‌دهد که توزیع داده‌های ورودی در Production با داده‌های قبلی تفاوت کند. Concept Drift زمانی رخ می‌دهد که رابطه میان ورودی و خروجی مطلوب تغییر کند.

در سیستم‌های LLM، تغییر در زبان کاربران، نوع سؤال‌ها، اسناد سازمانی، ابزارهای متصل یا سیاست‌های کسب‌وکار می‌تواند کیفیت پاسخ را تحت تأثیر قرار دهد.

8. AI Deployment

۸.۱. Deployment در سیستم‌های AI

Deployment به معنای قرار دادن مدل یا برنامه هوش مصنوعی در محیطی است که کاربران یا سرویس‌های دیگر بتوانند از آن استفاده کنند. استقرار می‌تواند به شکل API، سرویس داخلی، برنامه وب، سرویس پردازش دسته‌ای یا اجرای مدل روی دستگاه کاربر انجام شود.

۸.۲. انواع روش‌های استقرار

Cloud-based Deployment

مدل یا برنامه در زیرساخت ابری اجرا می‌شود. این روش می‌تواند مدیریت ظرفیت، شبکه و زیرساخت را ساده‌تر کند، اما باید هزینه، محل پردازش داده و وابستگی به Provider بررسی شود.

Self-hosted Deployment

سازمان مدل را در زیرساخت تحت کنترل خود اجرا می‌کند. این روش برای کنترل بیشتر بر داده، محیط اجرا و تنظیمات مفید است؛ اما مسئولیت مدیریت GPU، به‌روزرسانی، امنیت، ظرفیت و نگهداری بر عهده سازمان خواهد بود.

Hybrid Deployment

در معماری Hybrid، بخشی از درخواست‌ها به مدل‌های ابری و بخشی به مدل‌های داخلی هدایت می‌شوند. برای مثال، داده‌های حساس ممکن است در مدل داخلی پردازش شوند و درخواست‌های عمومی به سرویس ابری فرستاده شوند.

Edge Deployment

در Edge Deployment، مدل روی دستگاه یا نزدیک به محل تولید داده اجرا می‌شود. مزایای آن می‌تواند کاهش تأخیر، کاهش انتقال داده و امکان کار در شرایط اتصال محدود باشد.

۸.۳. Containerization

Containerization برنامه و وابستگی‌های آن را در یک بسته قابل اجرا قرار می‌دهد. Docker یکی از فناوری‌های متداول این حوزه است.

کانتینرها به تیم‌ها کمک می‌کنند محیط توسعه، تست و Production را به هم نزدیک‌تر کنند. در سرویس‌های مدل، باید منابع CPU، GPU، حافظه، فایل‌های مدل و تنظیمات شبکه نیز در نظر گرفته شوند.

۸.۴. Orchestration

وقتی تعداد سرویس‌ها زیاد می‌شود، مدیریت دستی کانتینرها دشوار خواهد شد. ابزارهای Orchestration برای مدیریت استقرار، مقیاس‌پذیری، بازیابی سرویس و توزیع بار استفاده می‌شوند.

Kubernetes نمونه شناخته‌شده‌ای از این دسته است. بااین‌حال، استفاده از آن برای هر پروژه‌ای ضروری نیست و باید با پیچیدگی واقعی زیرساخت تناسب داشته باشد.

۸.۵. استراتژی‌های Release

  • Rolling Deployment: جایگزینی تدریجی نسخه‌های قبلی با نسخه جدید.
  • Blue-Green: نگهداری دو محیط و انتقال کنترل‌شده ترافیک به محیط جدید.
  • Canary: ارسال درصد کمی از ترافیک به نسخه جدید و ارزیابی رفتار آن.
  • Shadow Deployment: ارسال نسخه‌ای از درخواست‌ها به سیستم جدید بدون استفاده از پاسخ آن برای کاربر.

۸.۶. Canary Release برای مدل‌ها

فرض کنیم نسخه جدید یک مدل یا Prompt آماده شده است. به‌جای جایگزینی فوری همه ترافیک، ابتدا بخش کوچکی از درخواست‌ها به نسخه جدید ارسال می‌شوند.

سپس کیفیت پاسخ، تأخیر، هزینه، خطا و شاخص‌های ایمنی با نسخه قبلی مقایسه می‌شوند. اگر شاخص‌ها در محدوده قابل قبول باشند، سهم ترافیک افزایش پیدا می‌کند.

۸.۷. Rollback

Rollback یعنی بازگشت به نسخه قبلی در صورت بروز مشکل. این قابلیت باید برای کد، Prompt، مدل، تنظیمات Gateway و در صورت امکان اجزای بازیابی اطلاعات طراحی شود.

صرفاً نگهداری نسخه قبلی کافی نیست؛ باید مسیر بازگشت، سازگاری داده‌ها و زمان بازیابی نیز آزمایش شوند.

۸.۸. Deployment Checklist

  • مدل و نسخه آن مشخص و ثبت شده است.
  • ارزیابی کیفیت و Regression Test موفق بوده است.
  • سیاست‌های دسترسی و امنیت بررسی شده‌اند.
  • Timeout، Retry و Rate Limit تنظیم شده‌اند.
  • مدیریت Secretها و کلیدهای API امن است.
  • Logging و Monitoring فعال است.
  • بودجه و محدودیت مصرف تعریف شده است.
  • Rollback و Runbook آماده است.
  • تست‌های Staging و Smoke Test انجام شده‌اند.

9. Scaling AI Applications

۹.۱. Scaling چیست؟

Scaling به توانایی سیستم برای پاسخ‌گویی به افزایش بار کاری گفته می‌شود. افزایش تعداد کاربران، درخواست‌ها، حجم داده‌ها یا پیچیدگی وظایف می‌تواند نیاز به مقیاس‌پذیری را ایجاد کند.

مقیاس‌پذیری در سیستم‌های AI فقط به افزایش تعداد سرورها محدود نیست. تعداد توکن‌ها، اندازه Context، تعداد فراخوانی ابزارها، زمان پردازش مدل و ظرفیت Provider نیز در آن نقش دارند.

۹.۲. Vertical Scaling

در Vertical Scaling منابع یک ماشین افزایش پیدا می‌کند؛ برای مثال CPU، RAM یا GPU قوی‌تری در اختیار سرویس قرار می‌گیرد.

این روش در بعضی سرویس‌ها ساده است، اما محدودیت سخت‌افزاری و هزینه دارد و ممکن است به‌تنهایی پاسخ‌گوی رشد بلندمدت نباشد.

۹.۳. Horizontal Scaling

در Horizontal Scaling تعداد نمونه‌های سرویس افزایش پیدا می‌کند. یک Load Balancer درخواست‌ها را بین نمونه‌ها توزیع می‌کند.

Incoming Requests | v Load Balancer / | \ v v v Instance Instance Instance \ | / \ | / v Shared / Managed Services

۹.۴. Stateless Architecture

یک سرویس Stateless برای پاسخ‌گویی به هر درخواست به وضعیت محلی دائمی وابسته نیست. وضعیت مکالمه، فایل‌ها و اطلاعات موردنیاز در سیستم‌های مناسب مانند پایگاه داده، Cache یا سرویس مدیریت Session نگهداری می‌شوند.

Stateless بودن سرویس API می‌تواند توزیع درخواست‌ها میان چند نمونه را ساده‌تر کند. البته خود Agent ممکن است به وضعیت مکالمه یا وظیفه نیاز داشته باشد؛ این وضعیت باید به‌صورت کنترل‌شده و قابل بازیابی ذخیره شود.

۹.۵. Asynchronous Processing

همه درخواست‌ها نباید تا پایان پردازش مدل، اتصال کاربر را باز نگه دارند. در کارهای طولانی می‌توان از صف پیام و Worker استفاده کرد.

Client | v API Service | v Message Queue | +------ Worker 1 +------ Worker 2 +------ Worker 3 | v Result Storage | v Notification / Polling

این معماری برای پردازش اسناد حجیم، تولید گزارش، تحلیل چندمرحله‌ای و وظایف طولانی Agent مناسب است.

۹.۶. Batching

Batching چند درخواست را در یک عملیات پردازش ترکیب می‌کند. این روش در پردازش Embedding، طبقه‌بندی انبوه و برخی زیرساخت‌های Model Serving می‌تواند بهره‌وری را افزایش دهد.

بااین‌حال، Batch بزرگ‌تر ممکن است زمان انتظار را افزایش دهد. بنابراین باید میان Throughput و Latency تعادل ایجاد شود.

۹.۷. GPU و Model Serving

در اجرای مدل‌های بزرگ، GPU و حافظه آن از منابع حیاتی هستند. ظرفیت مدل تنها به تعداد پارامترها وابسته نیست؛ طول Context، تعداد درخواست‌های هم‌زمان، روش Quantization و نحوه مدیریت KV Cache نیز اهمیت دارند.

در زیرساخت‌های خودمیزبان، باید مصرف حافظه GPU، زمان بارگذاری مدل، Throughput، زمان تولید هر توکن و رفتار سیستم در فشار زیاد اندازه‌گیری شود.

۹.۸. Streaming

Streaming اجازه می‌دهد بخش‌های پاسخ به‌تدریج به کاربر ارسال شوند. این روش می‌تواند زمان ادراک‌شده تا دریافت پاسخ را کاهش دهد.

باید تفاوت میان Time to First Token و زمان کامل‌شدن پاسخ اندازه‌گیری شود. همچنین قطع اتصال کاربر، لغو درخواست و خطای میانی باید مدیریت شوند.

۹.۹. Backpressure

Backpressure زمانی مطرح می‌شود که سرعت ورود درخواست‌ها از ظرفیت پردازش بیشتر باشد. سیستم باید بتواند صف را کنترل کند، درخواست‌های اضافی را محدود کند یا به کاربر پاسخ مناسب درباره ظرفیت بدهد.

۹.۱۰. شاخص‌های مقیاس‌پذیری

  • Requests per Second
  • Concurrent Requests
  • Tokens per Second
  • Time to First Token
  • End-to-End Latency
  • Queue Length و Queue Wait Time
  • GPU Utilization و GPU Memory
  • Error Rate و Timeout Rate

10. Monitoring and Observability

۱۰.۱. Monitoring و Observability چه تفاوتی دارند؟

Monitoring به اندازه‌گیری وضعیت سیستم با شاخص‌ها و هشدارهای تعریف‌شده می‌پردازد. برای مثال، اگر نرخ خطا از حد مشخصی بیشتر شود، یک Alert ایجاد می‌شود.

Observability به توانایی فهمیدن وضعیت داخلی سیستم از طریق داده‌های خروجی آن اشاره دارد. این مفهوم کمک می‌کند حتی برای مشکلاتی که از قبل دقیقاً پیش‌بینی نشده‌اند، علت احتمالی را پیدا کنیم.

۱۰.۲. سه ستون اصلی Observability

Logs

Logها رویدادهای ثبت‌شده در سیستم هستند. برای مثال، درخواست دریافت شد، مدل انتخاب شد، ابزار فراخوانی شد یا درخواست با خطا مواجه شد.

Metrics

Metricها مقادیر عددی و قابل اندازه‌گیری در طول زمان هستند؛ مانند نرخ درخواست، درصد خطا، زمان پاسخ و مصرف توکن.

Traces

Trace مسیر یک درخواست را در چند سرویس دنبال می‌کند. در یک سیستم Agentic، Trace می‌تواند نشان دهد درخواست از API وارد شده، به Planner رسیده، چند ابزار را فراخوانی کرده و در نهایت پاسخ تولید کرده است.

۱۰.۴. Latency را چگونه تحلیل کنیم؟

میانگین زمان پاسخ به‌تنهایی کافی نیست؛ زیرا ممکن است بیشتر درخواست‌ها سریع باشند اما تعداد کمی از درخواست‌ها بسیار کند شوند.

  • p50: نیمی از درخواست‌ها سریع‌تر از این مقدار تمام می‌شوند.
  • p95: ۹۵ درصد درخواست‌ها در این زمان یا کمتر تمام می‌شوند.
  • p99: ۹۹ درصد درخواست‌ها در این زمان یا کمتر تمام می‌شوند.

در سیستم‌های LLM بهتر است تأخیر به بخش‌های جداگانه تقسیم شود: زمان صف، زمان آماده‌سازی Prompt، زمان اولین توکن، زمان Tool Call و زمان کامل‌شدن پاسخ.

۱۰.۵. Distributed Tracing برای Agentها

Agent ممکن است در یک وظیفه چندین مدل و ابزار را فراخوانی کند. اگر فقط زمان کل درخواست را ثبت کنیم، مشخص نمی‌شود کدام مرحله باعث تأخیر یا خطا شده است.

Distributed Tracing هر مرحله را به‌عنوان یک Span ثبت می‌کند و ارتباط میان مراحل را نشان می‌دهد. بهتر است شناسه Trace در سرویس‌ها و ابزارهای مختلف منتقل شود.

۱۰.۶. Alerting

Alert باید برای مسئله‌ای ایجاد شود که نیازمند بررسی یا اقدام است. هشدارهای بیش‌ازحد باعث خستگی تیم عملیاتی می‌شوند.

نمونه هشدارهای مهم:

  • افزایش ناگهانی نرخ خطای Provider
  • افزایش p95 Latency
  • افزایش مصرف توکن نسبت به الگوی معمول
  • افت محسوس Task Success Rate
  • افزایش شکست Tool Call
  • نزدیک‌شدن به سقف بودجه
  • افزایش نرخ نقض سیاست‌های ایمنی

۱۰.۷. Privacy-aware Observability

ثبت داده برای تحلیل سیستم ضروری است، اما نباید باعث ذخیره بی‌ضابطه اطلاعات حساس شود. باید مشخص باشد چه اطلاعاتی ثبت می‌شوند، چه کسانی به آن دسترسی دارند، چه مدت نگهداری می‌شوند و چگونه حذف یا ناشناس‌سازی می‌شوند.

متن کامل مکالمه، Prompt، خروجی مدل و اسناد بازیابی‌شده را بدون بررسی سیاست داده در Logهای عمومی ذخیره نکنید. در بسیاری از کاربردها، ثبت Metadata و Trace ساختاریافته کافی‌تر و امن‌تر است.

11. AI Security and Privacy

۱۱.۱. چرا امنیت سیستم‌های AI متفاوت است؟

سیستم‌های AI علاوه بر آسیب‌پذیری‌های معمول نرم‌افزار، با خطرهای مرتبط با ورودی‌های زبانی، داده‌های بازیابی‌شده، خروجی غیرقطعی مدل و ابزارهای دارای اختیار عملیاتی مواجه هستند.

در یک Agent، مدل ممکن است به ایمیل، فایل‌ها، پایگاه داده یا APIهای خارجی دسترسی داشته باشد. بنابراین یک تصمیم نادرست یا ورودی مخرب می‌تواند به اقدام واقعی منجر شود.

۱۱.۲. Prompt Injection

Prompt Injection زمانی رخ می‌دهد که ورودی مخرب تلاش کند دستورهای سیستم را تحت تأثیر قرار دهد. این ورودی ممکن است مستقیماً از کاربر بیاید یا داخل سند، صفحه وب، ایمیل و داده بازیابی‌شده قرار داشته باشد.

برای مثال، یک سند ممکن است حاوی متنی باشد که به مدل دستور می‌دهد اطلاعات محرمانه را افشا کند. سیستم نباید محتوای بازیابی‌شده را به‌عنوان دستور معتبر و دارای اختیار تلقی کند.

۱۱.۳. Indirect Prompt Injection

در Indirect Prompt Injection، دستور مخرب از منبعی غیر از پیام مستقیم کاربر وارد سیستم می‌شود. برای مثال، Agent یک صفحه وب را می‌خواند و متن داخل صفحه تلاش می‌کند مسیر تصمیم‌گیری آن را تغییر دهد.

این مسئله برای Agentهایی که وب‌گردی، خواندن فایل یا بازیابی سند انجام می‌دهند اهمیت زیادی دارد.

۱۱.۴. Data Leakage

Data Leakage یعنی اطلاعاتی که نباید در اختیار کاربر یا سرویس دیگری قرار گیرند، به شکلی افشا شوند.

منشأهای رایج نشت داده:

  • بازیابی اسناد بدون کنترل مجوز
  • استفاده مشترک و ناامن از Cache
  • ثبت اطلاعات حساس در Log
  • ارسال داده محرمانه به Provider نامناسب
  • افشای Secretها از طریق خروجی مدل یا ابزار
  • اشتباه در جداسازی داده مشتریان مختلف

۱۱.۵. Least Privilege

اصل Least Privilege می‌گوید هر کاربر، سرویس یا Agent باید فقط به حداقل دسترسی موردنیاز برای انجام وظیفه خود دسترسی داشته باشد.

برای مثال، Agent پشتیبانی ممکن است اجازه مشاهده وضعیت سفارش را داشته باشد، اما نباید بتواند بدون مجوز، سفارش را حذف یا اطلاعات پرداخت را تغییر دهد.

۱۱.۶. Tool Security

ابزارها یکی از حساس‌ترین بخش‌های سیستم‌های Agentic هستند. فراخوانی ابزار باید در یک لایه اجرایی قابل اعتماد کنترل شود.

  • اعتبارسنجی نوع و مقدار پارامترها
  • کنترل دسترسی در سمت سرور
  • محدودکردن عملیات به منابع مجاز
  • جلوگیری از اجرای دستورات دلخواه
  • محدودکردن دسترسی شبکه و فایل‌سیستم
  • ثبت رویدادهای مهم و قابل ممیزی
  • تأیید انسانی برای اقدامات پرخطر

۱۱.۷. امنیت اجرای کد

اگر Agent اجازه تولید یا اجرای کد داشته باشد، باید محیط اجرا به‌شدت محدود شود. اجرای کد تولیدشده توسط مدل روی سیستم اصلی، بدون Sandbox و محدودیت منابع، خطرناک است.

محیط Sandbox باید دسترسی فایل، شبکه، پردازنده، حافظه و مدت اجرا را محدود کند. همچنین نباید Secretهای اصلی سیستم را در اختیار کد تولیدشده قرار دهد.

۱۱.۸. Authentication و Authorization

Authentication مشخص می‌کند چه کسی یا چه سرویسی درخواست را ارسال کرده است. Authorization تعیین می‌کند آن هویت چه کاری می‌تواند انجام دهد.

در سیستم‌های چندمستاجری، Tenant Isolation اهمیت ویژه‌ای دارد. حتی اگر مدل بتواند سندی را پیدا کند، لایه بازیابی باید بررسی کند که کاربر اجازه مشاهده آن را دارد.

۱۱.۹. امنیت داده و حریم خصوصی

  • طبقه‌بندی داده‌ها بر اساس حساسیت
  • رمزنگاری داده در انتقال و در حالت ذخیره‌شده
  • مدیریت امن Secret و کلیدهای API
  • محدودیت نگهداری داده و سیاست حذف
  • ناشناس‌سازی یا حداقل‌سازی داده‌های شخصی
  • بررسی قراردادها و سیاست‌های پردازش Provider
  • کنترل محل پردازش و انتقال داده در صورت نیاز قانونی

۱۱.۱۰. Human Approval برای عملیات حساس

برای عملیات حساس باید میان «پیشنهاد مدل» و «اجرای واقعی» تفاوت وجود داشته باشد. مدل می‌تواند عملیات را پیشنهاد دهد، اما اجرای آن به تأیید یک کاربر مجاز نیاز داشته باشد.

نمونه عملیات حساس شامل پرداخت، بازپرداخت، حذف داده، تغییر دسترسی، ارسال پیام رسمی، انتشار عمومی و تغییر تنظیمات زیرساخت است.

۱۱.۱۱. Threat Modeling

Threat Modeling یعنی پیش از انتشار سیستم، تهدیدها و مسیرهای احتمالی سوءاستفاده را شناسایی کنیم. باید مشخص شود دارایی‌های ارزشمند چیست، مهاجم چه توانایی‌هایی دارد، مرزهای اعتماد کجا هستند و هر آسیب‌پذیری چه پیامدی خواهد داشت.

خروجی مدل را نباید به‌عنوان مرز امنیتی در نظر گرفت. اینکه مدل در Prompt نوشته‌شده قول می‌دهد کاری انجام ندهد، جایگزین کنترل دسترسی، اعتبارسنجی سمت سرور و محدودیت اجرایی واقعی نیست.

12. Cost Optimization

۱۲.۱. چرا هزینه AI باید از ابتدا طراحی شود؟

در سیستم‌های مبتنی بر API، هر درخواست می‌تواند هزینه متغیری ایجاد کند. تعداد توکن‌های ورودی و خروجی، نوع مدل، تعداد دفعات فراخوانی، پردازش تصویر، ابزارهای خارجی و طول زنجیره Agent بر هزینه نهایی تأثیر دارند.

ممکن است یک سیستم در مرحله آزمایش کم‌هزینه به نظر برسد، اما با افزایش کاربران، استفاده از Promptهای طولانی و چندین فراخوانی مدل، هزینه آن به‌سرعت رشد کند.

۱۲.۲. اجزای هزینه

  • هزینه توکن‌های ورودی
  • هزینه توکن‌های خروجی
  • هزینه Embedding
  • هزینه Reranking و Retrieval
  • هزینه اجرای مدل‌های میزبانی‌شده
  • هزینه GPU و زیرساخت
  • هزینه Storage و Database
  • هزینه ابزارها و APIهای خارجی
  • هزینه مانیتورینگ و انتقال داده
  • هزینه پردازش مجدد درخواست‌های ناموفق

۱۲.۳. Cost per Request

یکی از معیارهای مهم، هزینه متوسط هر درخواست است. اما میانگین به‌تنهایی کافی نیست؛ بهتر است هزینه بر اساس نوع وظیفه، مدل، کاربر، تیم و سطح پیچیدگی نیز تحلیل شود.

Total Cost = Input Cost + Output Cost + Tool Cost + Infrastructure Cost

اگر هزینه مدل بر اساس تعداد توکن محاسبه شود، باید تعداد توکن ورودی و خروجی در نرخ مربوط به مدل ضرب شود. نرخ‌ها و واحد قیمت‌گذاری بین Providerها متفاوت‌اند.

۱۲.۴. Prompt Optimization

Promptهای طولانی می‌توانند هزینه ورودی و زمان پردازش را افزایش دهند. حذف دستورهای تکراری، محدودکردن Context غیرضروری و استفاده از ساختار مناسب می‌تواند مصرف را کاهش دهد.

بااین‌حال، کوتاه‌کردن Prompt نباید باعث حذف اطلاعات ضروری یا افت کیفیت شود. هر بهینه‌سازی باید با ارزیابی کیفیت همراه باشد.

۱۲.۵. Model Routing برای کاهش هزینه

یکی از مؤثرترین روش‌ها، استفاده از مدل متناسب با پیچیدگی درخواست است. مدل‌های کوچک‌تر می‌توانند بسیاری از وظایف ساده را انجام دهند و مدل‌های قوی‌تر برای وظایفی استفاده شوند که واقعاً به توانایی بیشتر نیاز دارند.

۱۲.۶. Caching

اگر درخواست‌های مشابه زیاد تکرار شوند، Cache می‌تواند از پردازش مجدد جلوگیری کند. Cache باید با توجه به نسخه مدل، Prompt، داده، سطح دسترسی و تازگی اطلاعات طراحی شود.

در Semantic Cache باید آستانه شباهت با دقت انتخاب شود؛ زیرا دو درخواست با متن مشابه ممکن است از نظر کاربر یا مجوز دسترسی، معنای عملی متفاوتی داشته باشند.

۱۲.۷. Context Optimization

ارسال حجم زیادی از اسناد به مدل همیشه کیفیت را بهتر نمی‌کند. گاهی Context بیش‌ازحد باعث افزایش هزینه، تأخیر و حتی کاهش تمرکز مدل می‌شود.

  • بازیابی فقط اسناد مرتبط
  • حذف تکرارها
  • Reranking نتایج
  • خلاصه‌سازی کنترل‌شده اسناد طولانی
  • محدودکردن تاریخچه مکالمه به اطلاعات مفید
  • استفاده از ساختار Metadata برای فیلترکردن اسناد

۱۲.۸. محدودکردن Agent Loop

Agent ممکن است چندین بار مدل و ابزارها را فراخوانی کند. اگر تعداد مراحل محدود نباشد، یک وظیفه ساده می‌تواند به زنجیره‌ای طولانی و پرهزینه تبدیل شود.

محدودیت‌های پیشنهادی:

  • حداکثر تعداد گام‌ها
  • حداکثر تعداد فراخوانی ابزار
  • حداکثر توکن مصرفی
  • مهلت زمانی کل وظیفه
  • حداکثر تعداد Retry
  • شرط توقف و ارجاع به انسان

۱۲.۹. FinOps برای AI

FinOps به مدیریت و بهینه‌سازی هزینه فناوری با مشارکت تیم‌های فنی و مالی می‌پردازد. در AI، باید هزینه‌ها به سرویس، تیم، پروژه، مدل و نوع وظیفه نسبت داده شوند.

بودجه، سقف مصرف، هشدار هزینه و گزارش‌های دوره‌ای کمک می‌کنند رشد هزینه پیش از تبدیل‌شدن به بحران شناسایی شود.

13. Production-ready Agentic Systems

۱۳.۱. Agentic System چیست؟

یک سیستم Agentic از مدل هوش مصنوعی برای تحلیل هدف، برنامه‌ریزی، انتخاب ابزار، اجرای مراحل و ارزیابی نتایج استفاده می‌کند. برخلاف یک سیستم ساده پرسش‌وپاسخ، Agent ممکن است برای رسیدن به هدف چندین اقدام متوالی انجام دهد.

برای مثال، کاربر می‌گوید: «گزارش فروش ماه گذشته را آماده کن و موارد غیرعادی را مشخص کن.» یک Agent می‌تواند داده‌ها را بازیابی کند، محاسبات را انجام دهد، ناهنجاری‌ها را بررسی کند، نمودار بسازد و در نهایت گزارش تهیه کند.

۱۳.۴. مدیریت چرخه اجرای Agent

Agent باید یک چرخه اجرای مشخص داشته باشد. این چرخه معمولاً شامل دریافت هدف، تحلیل، برنامه‌ریزی، انتخاب اقدام، اجرا، بررسی نتیجه و تصمیم برای ادامه یا توقف است.

مهم است که اجرای Agent بی‌نهایت نباشد. تعداد مراحل، زمان کل، هزینه و تعداد ابزارها باید محدود شود.

۱۳.۵. State Management

Agent ممکن است به اطلاعاتی درباره وضعیت کار نیاز داشته باشد. برای مثال، بداند کدام مرحله انجام شده، کدام ابزار خطا داده و چه داده‌ای هنوز باید بازیابی شود.

State نباید صرفاً در حافظه موقت فرایند نگهداری شود؛ زیرا با Restart یا انتقال کار به Worker دیگر از بین می‌رود. برای کارهای مهم باید وضعیت در یک ذخیره‌ساز پایدار نگهداری شود.

یک State نمونه می‌تواند شامل موارد زیر باشد:

{
  "task_id": "task-123",
  "status": "in_progress",
  "goal": "prepare monthly sales report",
  "completed_steps": [
    "load_sales_data",
    "calculate_monthly_totals"
  ],
  "pending_steps": [
    "detect_anomalies",
    "generate_report"
  ],
  "attempt_count": 2,
  "created_at": "2026-11-02T10:00:00Z"
}

۱۳.۶. Durable Execution

Durable Execution به معنای آن است که اجرای یک وظیفه طولانی بتواند در برابر Restart، قطع ارتباط یا خرابی موقت سرویس ادامه پیدا کند.

برای رسیدن به این هدف باید وضعیت مراحل، نتایج ابزارها، شناسه عملیات و وضعیت فعلی وظیفه ذخیره شوند. همچنین باید بتوانیم پس از بازیابی، از نقطه مناسب ادامه دهیم.

۱۳.۷. Idempotency

یک عملیات Idempotent اگر چند بار با ورودی یکسان اجرا شود، اثر تکراری ناخواسته ایجاد نمی‌کند. این ویژگی در سیستم‌هایی که Retry دارند بسیار مهم است.

فرض کنید Agent برای ثبت سفارش یک درخواست به API ارسال می‌کند، اما قبل از دریافت پاسخ ارتباط قطع می‌شود. Agent نمی‌داند سفارش ثبت شده یا خیر. اگر درخواست را دوباره ارسال کند، ممکن است سفارش تکراری ایجاد شود.

استفاده از Idempotency Key و بررسی وضعیت عملیات می‌تواند از این مشکل جلوگیری کند.

۱۳.۸. Human-in-the-Loop در Agentهای Production

یک Agent قابل اعتماد باید بداند چه زمانی اختیار کافی دارد و چه زمانی باید تصمیم را به انسان بسپارد.

موارد مناسب برای تأیید انسانی:

  • عملیات مالی یا پرداخت
  • حذف یا تغییر داده مهم
  • ارسال پیام به مشتری یا نهاد بیرونی
  • تغییر مجوز و دسترسی کاربران
  • اقداماتی که بازگشت‌پذیری دشواری دارند
  • تصمیم‌هایی که اطمینان مدل در آن‌ها کافی نیست

۱۳.۹. Agent Memory

حافظه Agent به نگهداری اطلاعات موردنیاز برای ادامه وظایف یا شخصی‌سازی رفتار اشاره دارد. حافظه می‌تواند کوتاه‌مدت، بلندمدت یا وابسته به یک وظیفه باشد.

  • Short-term Memory: اطلاعات موردنیاز در مکالمه یا وظیفه جاری.
  • Long-term Memory: اطلاعات منتخب که برای استفاده‌های بعدی نگهداری می‌شوند.
  • Task State: وضعیت اجرایی و مرحله فعلی یک کار.
  • External Knowledge: اطلاعاتی که از پایگاه داده یا سیستم‌های سازمانی بازیابی می‌شوند.

حافظه باید قابل کنترل، قابل حذف و دارای سیاست دسترسی باشد. نباید هر چیزی که مدل در مکالمه می‌بیند به‌صورت دائمی ذخیره شود.

۱۳.۱۰. Multi-Agent Systems

در سیستم چندعاملی، چند Agent با نقش‌های مختلف برای انجام یک هدف مشترک همکاری می‌کنند. برای مثال، یک Agent وظیفه تحقیق، Agent دیگر تحلیل داده و Agent سوم نگارش گزارش را بر عهده می‌گیرد.

استفاده از چند Agent همیشه بهتر از یک Agent نیست. ارتباط میان Agentها، هماهنگی، مدیریت تعارض، هزینه فراخوانی‌ها و کنترل وضعیت می‌توانند پیچیدگی زیادی ایجاد کنند.

۱۳.۱۱. الگوهای همکاری چند Agent

Supervisor Pattern

یک Agent ناظر وظایف را میان Agentهای تخصصی تقسیم می‌کند و نتایج را جمع‌بندی می‌کند.

Sequential Pattern

Agentها به‌صورت زنجیره‌ای کار می‌کنند؛ خروجی Agent اول ورودی Agent بعدی است.

Parallel Pattern

چند Agent بخش‌های مستقل کار را هم‌زمان انجام می‌دهند و سپس نتایج تجمیع می‌شوند.

Debate یا Review Pattern

یک Agent نتیجه را تولید می‌کند و Agent دیگر آن را نقد یا بررسی می‌کند. این الگو می‌تواند برای یافتن خطا مفید باشد، اما تضمین‌کننده صحت نیست.

۱۳.۱۳. Failure Handling در Agentها

خطا در سیستم Agentic می‌تواند در مراحل مختلف رخ دهد: انتخاب اشتباه ابزار، پارامتر نامعتبر، Timeout، خطای Provider، پاسخ ناقص، شکست سرویس خارجی یا ناتوانی در رسیدن به هدف.

باید برای هر دسته خطا رفتار مشخصی تعریف شود. بعضی خطاها قابل Retry هستند، برخی به Fallback نیاز دارند و برخی باید فوراً به انسان ارجاع داده شوند.

۱۳.۱۴. کنترل اختیار Agent

یکی از اصول مهم طراحی Agentهای Production، محدودکردن دامنه اختیار آن‌هاست. Agent باید فقط ابزارهایی را ببیند که برای وظیفه فعلی لازم‌اند.

بهتر است ابزارها به عملیات کوچک و مشخص تقسیم شوند؛ مثلاً به‌جای یک ابزار عمومی برای اجرای هر نوع دستور روی پایگاه داده، ابزارهای محدود برای خواندن وضعیت سفارش، دریافت فاکتور و بررسی موجودی تعریف شوند.

۱۳.۱۵. Production Readiness Checklist

  • هدف و محدوده مسئولیت Agent روشن است.
  • ابزارها و مجوزهای Agent حداقلی هستند.
  • ورودی و خروجی ابزارها اعتبارسنجی می‌شوند.
  • حداکثر تعداد مراحل و هزینه اجرا مشخص است.
  • Timeout و Retry کنترل‌شده وجود دارد.
  • عملیات حساس به تأیید انسانی نیاز دارند.
  • وضعیت وظایف مهم به‌صورت پایدار ذخیره می‌شود.
  • از اجرای تکراری عملیات جانبی جلوگیری می‌شود.
  • Trace و Log برای مراحل مهم ثبت می‌شوند.
  • ارزیابی وظایف Agent به‌صورت منظم انجام می‌شود.
  • سناریوهای Prompt Injection آزمایش شده‌اند.
  • مسیر ارجاع به انسان و مدیریت خطا مشخص است.
  • Rollback و توقف اضطراری سیستم قابل اجراست.

مرحله ششم: طراحی امنیت

  • هویت کاربر پیش از اجرای عملیات بررسی می‌شود.
  • اسناد فقط در محدوده مجوز کاربر بازیابی می‌شوند.
  • Agent نمی‌تواند مستقیماً مجوزهای کاربر را تغییر دهد.
  • عملیات ثبت نهایی نیازمند تأیید است.
  • اطلاعات حساس در Log عمومی ثبت نمی‌شوند.

مرحله هفتم: ارزیابی

یک مجموعه آزمون شامل پرسش‌های معمول، اسناد ناقص، درخواست‌های غیرمجاز، اسناد متناقض، درخواست‌های خارج از حوزه و تلاش‌های Prompt Injection ایجاد می‌کنیم.

سپس کیفیت پاسخ، صحت ارجاع، رعایت مجوز، نرخ موفقیت ابزارها، هزینه و زمان پاسخ را اندازه می‌گیریم.

  4. انتشار Canary

مرحله نهم: پایش مداوم

پس از انتشار، باید افت کیفیت بازیابی، افزایش هزینه، افزایش خطاهای ابزار، افزایش تأخیر و رفتارهای غیرمنتظره Agent بررسی شوند. بازخورد کاربران نیز باید به چرخه ارزیابی و بهبود بازگردد.

جمع‌بندی نهایی: اصول طلایی Advanced AI Engineering

  1. Model First نیست؛ Problem First است. ابتدا مسئله و معیار موفقیت را تعریف کنید و سپس مدل را انتخاب کنید.
  2. هر مشکلی نیازمند Fine-tuning نیست. گاهی RAG، Prompt یا اصلاح معماری راه‌حل بهتری است.
  3. ارزیابی باید پیش از انتشار وجود داشته باشد. کیفیت را نمی‌توان فقط با چند پاسخ نمونه سنجید.
  4. مدل بخشی از سیستم است، نه تمام سیستم. داده، ابزار، امنیت، زیرساخت و کنترل جریان نیز اهمیت دارند.
  5. خروجی مدل قابل اعتماد مطلق نیست. اعتبارسنجی و کنترل دسترسی باید بیرون از مدل اجرا شوند.
  6. هزینه باید قابل مشاهده باشد. مصرف توکن، ابزار، زیرساخت و اجرای Agent باید اندازه‌گیری شود.
  7. استقرار پایان کار نیست. Monitoring، Feedback، Regression و بهبود مستمر ضروری‌اند.
  8. Agent باید اختیار محدود داشته باشد. هر ابزار و هر عملیات باید مجوز و محدوده مشخص داشته باشد.
  9. Human-in-the-Loop برای اقدامات حساس ضروری است. مدل نباید به‌تنهایی اختیار نامحدود داشته باشد.
  10. Production Readiness یک ویژگی معماری است. نمی‌توان در آخر پروژه فقط با اضافه‌کردن چند Log سیستم را آماده Production کرد.

سؤالات مرور و سنجش یادگیری

سؤالات مفهومی

  1. چه زمانی Fine-tuning نسبت به RAG انتخاب بهتری است؟
  2. چرا استفاده از یک مدل برای تمام درخواست‌ها همیشه بهینه نیست؟
  3. AI Gateway چه مسئولیت‌هایی دارد و چرا می‌تواند به نقطه شکست واحد تبدیل شود؟
  4. تفاوت Monitoring و Observability چیست؟
  5. چرا ارزیابی یک سیستم Agentic با ارزیابی یک پاسخ متنی تفاوت دارد؟
  6. چرا خروجی معتبر JSON الزاماً به‌معنای خروجی درست نیست؟
  7. Prompt Injection مستقیم و غیرمستقیم چه تفاوتی دارند؟
  8. چرا Idempotency برای ابزارهای دارای عملیات جانبی اهمیت دارد؟
  9. چه تفاوتی میان Canary Release و Shadow Deployment وجود دارد؟
  10. چرا تعداد مراحل Agent باید محدود شود؟

تمرین‌های عملی

  1. برای یک دستیار پشتیبانی، یک Model Router ساده طراحی کنید.
  2. یک Golden Dataset شامل حداقل ۳۰ سؤال برای یک RAG بسازید.
  3. برای یک AI API، معیارهای p95 Latency، Error Rate و Cost per Request تعریف کنید.
  4. یک طرح امنیتی برای Agent دارای دسترسی به ایمیل و فایل‌ها تهیه کنید.
  5. یک معماری Human-in-the-Loop برای عملیات بازپرداخت طراحی کنید.
  6. برای یک Agent چندمرحله‌ای، State Machine و سیاست Retry تعریف کنید.
  7. یک برنامه Canary Release همراه با معیارهای توقف و Rollback بنویسید.
  8. هزینه یک وظیفه Agent را با تعداد فراخوانی‌های مختلف مدل محاسبه و مقایسه کنید.
